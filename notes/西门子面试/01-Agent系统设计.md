# Q1｜如何设计一个生产级 Agent 系统（规划 / 工具调用 / 记忆 / 安全）

> 对应面试环节：第 1 小时「Agent 设计题」+ 追问；也是第 2 小时「系统设计、并发、流量控制」的通用骨架。

## 30 秒版答案

我会把 Agent 拆成**五层 + 两条横切能力**：

- 五层：**编排层（Loop）/ 模型层 / 工具层 / 记忆层 / 执行沙箱**
- 两条横切：**资源与限流**、**可验证性与可回滚**

核心判断：Agent 的难点从来不是"能不能调通模型"，而是**在不可信输出之下保证系统状态正确、可审计、可回滚**。

## 展开：分层与每层的关键设计

### 1. 编排层（Agent Loop）
- 状态机而非死循环：`Plan → Act → Observe → Reflect`，每轮必须产生**可观测的状态变化**，否则触发熔断（防止 ReAct 空转）。
- 每轮有预算：最大轮数、最大 token、最大墙钟时间，超限降级为"给出现状 + 建议"而不是硬撑。
- 幂等：同一任务带 `task_id`，重入时先查是否已完成。

### 2. 模型层
- 供应商抽象：统一 `chat(messages, tools)` 接口，屏蔽 OpenAI/Anthropic/本地模型差异。
- **降级链**：主模型 → 备用模型 → 规则兜底（关键词/模板），任何一层不可用都不阻塞任务。
- 输出契约：要求结构化 JSON（intent + 参数 + 叙述），不合契约直接判失败重试，**绝不把自由文本当指令执行**。

### 3. 工具层（最关键）
- 工具 = 声明式 schema（name / params / 副作用等级 / 超时 / 幂等性）+ 实现。
- **权限分级**：只读 / 可写 / 危险（删除、支付、迁移）。危险工具必须人工确认或双人审批。
- 参数校验在**服务端**做（JSON Schema + 白名单枚举），不信任模型给的参数。
- 每个工具调用有超时、重试策略（仅幂等工具允许自动重试）、结果大小上限（防上下文爆掉）。
- 工具返回结构化结果 + 摘要，长输出落盘给路径，不整段塞回上下文。

### 4. 记忆层
- 分三层：**工作记忆**（当前会话窗口）、**情节记忆**（历史会话摘要，可检索）、**语义记忆**（长期事实，如用户偏好、项目约定）。
- 写入策略比读取更重要：只把**稳定事实**写长期记忆，过程性内容进日志；记忆有 TTL 和容量上限，满了做合并/淘汰。
- 检索用混合方案（BM25 + 向量），避免纯向量召回不稳。

### 5. 执行沙箱
- 代码执行必须在隔离环境（容器/独立进程 + cgroup 限制 CPU/内存/时间 + 网络默认禁）。
- 文件系统最小挂载：只挂任务需要的目录，**写操作限定在 workspace 内**。
- 所有产物留痕（diff、日志、产物路径），供事后审计。

### 横切 1：资源与限流（面试官大概率追这点）
- **准入控制**：任务开始前采样真实 CPU/内存/磁盘，分档（green/yellow/orange/red）决定并发度；红灯直接跳过本轮。
- **并发上限按"重活名额"控制**：跨项目共享一个租约（lock + TTL），避免三个项目 × 4 车道把 4 核打满。
- **背压**：队列满时拒绝新任务而不是无限堆积；任务排队时间超过阈值就降级为异步通知。
- 连接管理：HTTP 用连接池 + keep-alive，超时分层（连接 3s / 读 60s / 总 120s），长任务走异步 + 轮询/回调，不占用长连接。

### 横切 2：可验证性与可回滚（我最看重的一条）
- **每条功能自带验收断言**（可执行命令），Agent 干完必须跑通才算完成——不做"自我声明完成"。
- **回归门禁**：改动后跑全量 E2E，失败自动回滚，不允许带病上线。
- **原子发布**：构建到新目录 + 软链接原子切换，切换瞬间旧版本仍在服务，避免构建期白屏。
- 全程可审计：谁改的（哪个模型/哪条任务）、改了什么（diff）、验证结果、部署版本。

## 追问预案

**Q：模型输出不可靠，你怎么防止它破坏数据？**
A：三道闸。① 输出必须是结构化契约，服务端校验；② 数值类改动（余额、库存、等级）一律由**确定性引擎**计算，模型只给意图不给结果；③ 危险操作分级 + 人工确认，且所有写操作可回滚（软删除 + 版本表）。

**Q：多 Agent 并行怎么保证不互相踩？**
A：隔离 + 串行化关键路径。隔离用 git worktree（每个任务独立工作区、独立分支）；串行化用部署锁（同一时刻只允许一个部署）。合并时逐条 `merge` 并立刻跑验证，失败只回滚这一条，不影响其它已合入的。

**Q：怎么控制成本？**
A：① 上下文压缩（只发状态摘要 + 最近 N 条，不发全量历史）；② 缓存命中优先（prompt caching / 结果缓存）；③ 分层用模型——调度和验收用便宜模型，重活交给免费/低成本通道；④ 每任务预算硬上限。

**Q：Agent 卡死/无限循环怎么办？**
A：轮数、时间、token 三重预算 + "状态无变化"熔断 + 心跳超时（超过 N 分钟无进展直接终止并汇报）。终止时保留现场（日志 + 中间产物）供人工接手。

**Q：连接建立与中断怎么处理？**
A：客户端侧——连接池复用、指数退避重连、超时分层；服务端侧——请求级超时 + 取消传播（context cancel 沿调用链下传），长任务与连接解耦（先返回 task_id，客户端轮询/订阅），避免一个慢请求占住连接。

## 一句话收尾（可以主动说）

> 我做的 Agent 系统里，"能跑"是最容易的部分；真正花时间的是**让它不敢乱来、出错能退回、每步都可验证**——这三件事决定了它是玩具还是生产系统。
