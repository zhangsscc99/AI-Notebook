# Q6｜项目深挖 + 行为面（第 2 小时）

> 面试官：2 位。重点：项目细节、实现思路、难点、可优化点、求职原因、基础开发能力（类设计/结构设计/并发/流控）。

## 一、项目介绍的"三段式"（每个项目都按这个讲，90 秒）

1. **一句话定位**：这个产品是什么、给谁用、解决什么问题。
2. **技术骨架**：栈 + 部署形态 + 一个关键技术决策（为什么这么选）。
3. **我的角色与结果**：我负责哪部分、最难的技术点、量化结果。

**示例（AI-Notebook）**：
> 这是一个面向 Agent 系统研究的可检索知识站，24 个专题 192 篇长文，方便我系统性复习 Agent 架构。技术上 React 19 + TS + Vite，内容由自建管线从源文件生成，服务端做 Brotli 压缩、immutable 缓存和 SPA 回退。我负责全部设计与实现，最有价值的是把"内容与代码"彻底分离，以及用真实浏览器做全路由回归。

## 二、必答的五个追问

### Q6.1 这个项目最难的地方是什么？
**答法**：选一个"有取舍"的技术难点，不要说"没遇到过"。
> 最难的是一致性问题：Agent 自动改代码时，多个任务并行修改同一仓库会互相踩。我的解法是 git worktree 隔离工作区 + 独立分支 + 部署锁串行化关键路径，合并逐条验证、失败只回滚单条。真正的难点不是技术实现，而是**定义"什么叫验证通过"**——我后来给每条功能加了可执行断言，Agent 自称完成不算数。

### Q6.2 如果流量涨 100 倍，你怎么改？
分层回答（这是系统设计标准结构）：
1. **接入层**：加负载均衡（Nginx/云 LB），静态资源上 CDN，开 HTTP/2 或 HTTP/3。
2. **应用层**：无状态化 + 水平扩容；会话状态外置到 Redis；热点数据本地缓存 + 分布式缓存两级。
3. **数据层**：读写分离、按业务分库、热点表加缓存；写多就批量 + 异步（消息队列削峰）。
4. **成本控制**：限流 + 降级 + 异步化，把非核心功能降级为「稍后处理」。
5. **可观测**：先上指标（QPS、P99、错误率、饱和度），否则扩容是盲目的。

### Q6.3 你怎么保证代码质量？
- 分层测试：单测覆盖核心逻辑、集成测覆盖接口契约、E2E 覆盖关键用户路径。
- **可执行验收**：每个功能自带验证命令，交付即验证。
- 门禁：CI 不过不合入；改动后跑全量回归，失败自动回滚。
- 代码评审：重点看"变更影响面"和"是否有更简单的写法"，而不是风格。

### Q6.4 你和团队/其他人怎么协作？
- 强调**契约先行**：接口/数据结构先定，再并行开发。
- 强调**可观测的沟通**：进度用"已完成/进行中/阻塞"三态 + 阻塞点具体到人。
- 有冲突时用数据决策（压测结果、错误率），而不是个人偏好。

### Q6.5 求职原因 / 离职原因（这个必问，别说前公司坏话）
**结构：认可对方 → 我的方向 → 匹配点**
> 我在现在的环境里主要做全栈交付和 Agent 系统落地，技术深度够但业务场景相对单一。西门子医疗吸引我的是两点：一是医疗场景对**可靠性和合规**的要求极高，这正好是我擅长的方向（可验证、可回滚、可审计）；二是这里有真实的、规模化的临床工程问题，能把我的系统设计能力用在有实际影响的地方。我希望能在一个「质量门槛高」的环境里继续做深。

**离职原因的通用安全答法**：寻求更大的技术挑战与更复杂的业务场景，而不是抱怨管理/同事/加班。

## 三、类设计与结构设计（第 2 小时的"基础开发能力"）

准备一个能现场画的小设计题，比如「设计一个文件上传服务」：

- **接口**：`initUpload`（返回分片上传凭证）→ `uploadChunk`（幂等，带分片号）→ `completeUpload`（合并 + 校验哈希）
- **类**：`UploadSession`（状态机：INIT→UPLOADING→MERGING→DONE/FAILED）、`ChunkStore`（存储抽象）、`HashVerifier`（策略：MD5/SHA256）
- **并发点**：分片并行上传（限制并发数）、断点续传（记录已上传分片）、合并时单写
- **流量控制**：单用户并发上传数限制、单文件大小上限、分片大小自适应
- **中断处理**：会话超时回收、客户端重连后按 `uploadId` 恢复

**加分点**：主动说出"幂等键"和"状态机"这两个词——它们直接对应真实工程里的坑。
