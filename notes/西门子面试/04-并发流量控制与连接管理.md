# Q4｜并发 / 流量控制 / 连接建立与中断

> 对应：笔试设计题与第 2 小时「并发、流量控制、连接建立与中断」。这是纯八股 + 容易答出深度的地方。

## 一、并发

### Q4.1 线程 / 进程 / 协程怎么选？
- **一句话**：按"阻塞类型"选。CPU 密集用多进程（绕开 GIL、隔离好）；IO 密集用协程/异步（上下文切换便宜、内存占用小）；需要共享内存状态且阻塞短用线程。
- **落地**：Agent 系统里工具调用是 IO 等待（模型 API、HTTP），我用异步并发 + 信号量限并发数，而不是开线程池。
- **追问·"协程的代价？"**：不能有阻塞调用（一个阻塞会卡住事件循环）、调试栈不直观、CPU 密集任务反而更慢。

### Q4.2 线程池参数怎么定？
- 公式：`核心线程数 ≈ CPU 核数 × (1 + 平均等待时间/平均计算时间)`。
- IO 密集（如 HTTP 调用）可以远大于核数；CPU 密集设为核数或核数+1。
- 队列要有界——无界队列会把内存吃光，掩盖背压问题。
- 拒绝策略：`CallerRuns`（让调用方执行，天然降速）或直接拒绝并上报，不要静默丢弃。

### Q4.3 怎么保证并发安全？
- 优先**无共享**（不可变对象、每个任务独立上下文、线程局部存储）。
- 必须共享时：细粒度锁 → 原子操作 → 乐观锁（CAS/版本号）按顺序选，锁的粒度越小越好。
- 数据库层面：`UPDATE ... WHERE version = ?` 乐观锁 + 重试；或者行锁 `SELECT ... FOR UPDATE`。
- **讲一个真实例子**：回购查询接口的 5 分钟内存缓存，用读写锁（读多写少），刷新时只让一个请求回源，其余等待或返回旧值（缓存击穿保护）。

### Q4.4 死锁怎么避免？
- 四个必要条件：互斥、占有并等待、不可剥夺、循环等待。
- 工程做法：**统一加锁顺序**、设置锁超时（`tryLock(timeout)`）、避免持锁调用外部服务、用无锁结构替代。
- 排查：jstack/pprof 看线程栈，找互相等待的环。

## 二、流量控制

### Q4.5 限流算法有哪几种，怎么选？
| 算法 | 特点 | 适用 |
|---|---|---|
| 固定窗口 | 实现最简单，边界双倍流量问题 | 粗粒度配额 |
| 滑动窗口 | 平滑，边界准确，内存稍大 | 大多数 API 限流 |
| 漏桶 | 恒定速率流出，抗突发 | 保护下游固定处理能力 |
| 令牌桶 | 允许一定突发，平均速率受控 | **最常用**，用户体验好 |

- 落地：我们的 Agent 任务有"准入控制"——开工前采样 CPU/内存/磁盘分档，红灯直接跳过本轮；devin 进程数 ≥3 也直接跳过。这是**系统级限流**而不是接口级。
- 上游 API 限流（如每分钟 200 次）用令牌桶 + 客户端侧预算，接近上限时降级/排队。

### Q4.6 背压（backpressure）怎么做？
- 核心：**让生产速度感知下游能力**，而不是无限堆积。
- 手段：有界队列 + 拒绝策略；响应式流（Reactive Streams 的 request(n)）；生产者限速（下游返回 429/水位信号）；异步任务用"排队超时"降级为稍后重试。
- 我的做法：任务队列满 → 拒绝新任务并明确告诉调用方"当前繁忙，稍后重试"，而不是排队到超时。

### Q4.7 熔断、降级、隔离的区别？
- **熔断**：下游连续失败超过阈值 → 直接快速失败一段时间（半开试探），避免雪崩。
- **降级**：主逻辑不可用时返回备用结果（缓存旧值、默认值、简化功能）。
- **隔离**：不同依赖用不同线程池/连接池/信号量，避免一个慢依赖拖垮全部。
- 三者通常组合：超时 → 重试（仅幂等）→ 熔断 → 降级。

## 三、连接建立与中断

### Q4.8 TCP 三次握手 / 四次挥手要点
- 三次握手：SYN → SYN+ACK → ACK。为什么不是两次？防止历史重复连接请求造成资源浪费，确认双方收发能力。
- 四次挥手：FIN → ACK → FIN → ACK。为什么四次？TCP 全双工，两个方向要分别关闭。
- **TIME_WAIT**：主动关闭方等待 2MSL，保证最后的 ACK 能到达、并让旧连接的重复包在网络中消亡。大量 TIME_WAIT 说明短连接太多 → 改连接池/keep-alive。

### Q4.9 连接池怎么设计？
- 关键参数：最大连接数、最小空闲、获取超时、空闲回收时间、最大存活时间、健康检查（`SELECT 1` / ping）。
- 最大连接数要与下游承载能力匹配（数据库 max_connections、服务端线程数），否则只是把排队挪到服务端。
- 泄漏防护：借出必须归还（try-with-resources / defer），加借用超时告警。

### Q4.10 超时怎么分层设置？
- 连接超时 3s、读超时 60s、整体请求超时 120s（经验值，按业务调整），**外层超时必须大于内层**，否则外层先断、内层还在跑，浪费资源。
- 重试只对幂等操作 + 网络类错误，指数退避 + 抖动，且总重试次数有上限（常见 2–3 次）。

### Q4.11 长连接怎么保活与重连？
- 保活：应用层心跳（30s）+ TCP keepalive；服务端空闲超时略大于心跳间隔。
- 重连：指数退避（1s→2s→4s…上限 30s）+ 随机抖动，避免大量客户端同时重连打垮服务端（惊群）。
- 断线期间的请求：区分幂等（可重放）和非幂等（必须查询确认状态，不能盲重试）。

### Q4.12 WebSocket / SSE 场景怎么处理中断？
- 每条消息带序号 + 服务端保留最近 N 条，重连时按 `last_seq` 增量补发；
- 客户端本地队列缓存未确认消息，重连后重放；
- 服务端侧重连要校验会话 token，避免旧连接残留写冲突。

## 四、能被追问到的量化经验（准备两个数字）

1. **Agent 并发**：4 核机器并行 4 个工作树 × 各 1 个 devin 进程；超过就排队，靠"重活名额"租约 + 进程数上限控制，避免 CPU 打满影响交互服务。
2. **接口超时分层**：Tushare 数据源 30s 超时 + 1 次重试（仅网络错误），整体接口 120s；递归分段查询把大区间拆成多次小请求，避免单次 2000 行截断。

## 五、一句话收尾（可主动说）

> 并发和流控的本质是同一件事：**让系统在过载时的降级行为是可预测的**——宁可明确拒绝，也不要静默变慢或雪崩。
