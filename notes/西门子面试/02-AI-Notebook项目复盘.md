# Q2｜AI-Notebook 项目复盘（Agent Systems Field Guide）

> 对应面试环节：第 2 小时「项目细节 / 实现思路 / 有哪些优化空间」。

## 30 秒版

AI-Notebook 是一个**面向 Agent 系统研究的可检索知识站**：把 24 个研究专题、192 篇长文做成可按需加载的单页应用，配套练习记录、熟练度评分和学习计划。技术上用 React 19 + TypeScript + Vite，内容由自己的管线从源文件生成，服务端做了 Brotli 压缩、immutable 资源缓存和 SPA 路由回退，并用 Chromium 对全部文章路由做了桌面/移动端回归。

**它解决的问题**：Agent 领域资料散落在论文、博客、代码库里，且长文阅读成本高——我用「专题 → 文章 → 练习」的结构把它变成可复习的知识库。

## 结构与关键设计

### 1. 内容与代码分离（内容管线）
- 源内容集中在一处，`npm run content` 生成 24 个专题、192 篇文章的结构化数据 + 搜索元数据。
- 好处：加内容不用碰 React 代码；改版式不影响内容；构建可校验（内容不合法直接构建失败）。
- 取舍：牺牲了"所见即所得"的编辑体验，换来内容可批处理、可去重、可生成索引。

### 2. 性能：按需加载 + 缓存分层
- **文章正文按路由懒加载**，搜索索引只在打开搜索时才拉取——首屏不为 192 篇文章买单。
- 构建产物名带 content hash → 服务端给静态资源 `immutable` + 一年缓存，`index.html` 走 `no-cache`，保证发版后立即生效。
- 服务端开启 **Brotli / Gzip**，长文文本压缩收益很大。
- 字体用 `@fontsource` 自托管可变字体（Newsreader + IBM Plex Mono），避免第三方字体请求阻塞首屏。

### 3. 路由与 SEO / 深链
- SPA 路由回退：任何深链都返回 `index.html`，由前端路由解析，刷新不 404。
- 用 Chromium 对**每条文章路由**做自动化回归（桌面 + 移动视口、搜索、深链、console error 检查），避免"首页好看、深链白屏"。

### 4. 数据层
- 练习记录、熟练度、学习计划用 SQLite（`practice_records` / `practice_attempts` / `proficiency_scores` / `study_plans`）。
- 写入用事务，熟练度用增量更新而不是全量重算，保证并发做题时数据不打架。

## 难点与解决办法（面试官最爱追这里）

**难点 1：内容体量大、首屏慢**
- 现象：192 篇长文如果全量打包，主包会有几 MB。
- 做法：正文与搜索索引**双懒加载**（路由级 + 交互级），主包只留框架与路由表。
- 结果：首屏只加载必要资源，搜索打开时才付索引的代价。

**难点 2：发版后用户看到白屏**
- 根因：`index.html` 缓存住了旧版本，引用的 JS 哈希已不存在。
- 做法：资源与入口分离缓存策略——入口 `no-cache` 每次校验，资源 `immutable` 长缓存；发布用"新目录 + 原子切换"而不是覆盖旧目录。
- 这条经验后来复用到别的项目：**构建期覆盖目录 = 必然有白屏窗口，必须原子发布**。

**难点 3：回归覆盖不足**
- 单测测不到"页面能不能打开"。
- 做法：用真实浏览器跑全路由冒烟（Chromium headless），检查标题、正文长度、console error、移动端横向溢出。
- 结果：改版/发版前能自动拦住"深链 404""白屏""样式溢出"这类问题。

## 可讲的量化数据

- 24 个专题 / 192 篇文章；内容管线一键生成
- 全路由 Chromium 回归：桌面 1440×900 + 移动 390×844
- 服务端：Brotli 压缩 + immutable 缓存 + SPA fallback
- 首屏只加载框架与路由，正文与搜索索引按需加载

## 还可以怎么优化（主动说出，显示深度）

1. **内容层**：把文章做成"可增量更新 + 版本化"，支持 diff 式复习（同一篇内容更新时高亮变化）。
2. **搜索**：现在 Fuse.js 是纯前端模糊匹配，可以换成预生成倒排索引（BM25）+ 向量召回的混合检索，提升长文召回。
3. **可观测性**：接入前端性能指标（LCP / INP / CLS）与错误上报，按路由维度看真实用户性能。
4. **测试**：把全路由冒烟扩成"视觉回归"（截图基线比对），覆盖样式退化。
5. **架构**：如果文章量再上一个量级，正文可以考虑预渲染（SSG）按专题出静态页，进一步降低首屏 JS 成本。

## 高频追问与答法

**Q：为什么不用 Next.js 做 SSG？**
A：这个站的交互重心是「检索 + 练习记录」，不是内容分发；SPA + 按需加载已经能满足首屏，SSG 会引入构建时长和内容管线的重复。如果内容要面向搜索引擎大规模曝光，我会切 SSG。

**Q：为什么 SQLite？**
A：单机、数据量小、需要强一致的事务（做题记录、熟练度增量更新）。SQLite 零运维、事务可靠，比引入 Postgres 划算。真要多实例再换。

**Q：内容管线怎么保证不出错？**
A：生成阶段做结构校验（必填字段、专题-文章引用完整性、重复检测），不合法直接失败阻断构建；产物进 git 便于 diff 审阅。

**Q：如果现在重做，你会改什么？**
A：两件事——① 一开始就把"原子发布 + 全路由冒烟"作为基础设施做掉，而不是后期补；② 内容模型一开始就带版本号，方便后续做增量复习和变更追踪。
