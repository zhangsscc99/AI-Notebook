UML 类图精讲：从商城订单模块一步步画（符号逐个击破）

笔试让你"画类设计"时，最容易丢分的不是结构想不出来，而是符号画错。这篇不画流程图，只用商城订单模块一步步搭类图——每一步最多 2-3 个类，每个新符号出现就立刻讲透。

核心原则：先画 2 个类的最小骨架，再加接口，最后补领域对象。跟面试官说"我先画最小闭环"是加分话术。

Q：给商城订单模块画类图，并说明用到的符号

第一步：最小骨架 —— 2 个类，学 3 个符号

订单模块最小闭环：OrderService 干活，OrderDao 存数据。Service 把 Dao 当成员变量长期持有 → 关联关系。

符号笔记：- orderDao : OrderDao 读作"私有字段 orderDao，类型 OrderDao"。Service 持有 Dao 是关联（实线箭头）——代码特征就是成员变量。这一步面试官若问"为什么是关联不是依赖"，答：orderDao 是字段级长期持有，不是方法参数路过。

第二步：加缓存接口 —— 2 个新节点，学 2 个符号

商品热点数据要缓存。关键设计：OrderService 面向接口 CacheService 编程，Redis 只是实现之一——这就是依赖倒置在类图上的样子。

符号笔记：«interface» 是构造型标记，手写时漏标会让接口被当成类。实现 = 虚线 + 空心三角，指向接口（对比：继承是实线三角指向父类）。追问预案："换 Memcached 怎么办？" → 再加一个实现类，OrderService 一行不改——开闭原则。

第三步：补领域对象 —— 2 个新节点，学菱形

Order 和 OrderItem（订单明细）：明细不能脱离订单存在 → 组合。OrderService 只是方法参数里用一下 Order → 依赖。

符号笔记：组合 = 实线 + 实心菱形在整体端，语义"同生共死"。对比聚合（空心菱形）：购物车◇——商品，商品离开购物车照常在。追问："Order 和 User 什么关系？" → 关联：订单引用用户，但用户删了订单历史还在，反过来也不共生。

符号速查表（默画前看一遍）

符号含义判定口诀
+ - # ~public / private / protected / package 可见性字段一律 -，方法对外 +
«interface»构造型：这框是接口接口必须标，不标当类
实线箭头 -->关联：成员变量级持有"字段里有没有它"
虚线箭头 ..>依赖：参数/局部变量临时用"方法里路过一下"
实心菱形 *--组合：部分依附整体，同生共死菱形在"主人"端
空心菱形 o--聚合：弱拥有，可分离购物车—商品
虚线三角 <|..实现接口三角指向接口
实线三角 <|--继承三角指向父类
1 / 0..* / *重数：关系两端数量写在被指对象那一端

笔试口诀 + 避坑

三角 = 血统，指向爹：实线三角找父类，虚线三角找接口。
菱形 = 拥有，画主人端：实心同生共死，空心好聚好散。
普通箭头 = 用：实线当字段（关联），虚线路过（依赖）。
拿不准用关联兜底：实线箭头画错概率最低，画错菱形三角反而扣分。
每个符号要能讲动机："这里用组合因为明细依附订单"——符号是设计理由的载体。
练习：默画这三步 → 让朋友随机指一条线问"什么关系、为什么" → 自己再加一个类（如 GoodsService 聚合进 OrderService）继续练。本地 uml-practice/ 里有 PlantUML 源码可改参数重渲染验证。
