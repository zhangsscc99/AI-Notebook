CT3

Claude Code 里多工具都能完成同一子任务时怎么选择，是否有打分或排序模块

结论先说：Claude Code 没有一个通用的“多工具候选打分器/排序器”来替模型决定用哪个工具完成子任务。大多数情况下，工具选择发生在模型侧：Claude 看到系统提示、工具描述、tool schema、当前上下文，然后自己发出某个 tool_use。Claude Code 运行时主要负责“暴露哪些工具、约束哪些工具、校验和执行工具”，而不是在本地为同一子任务做全局最优工具路由。

一句话：Claude Code 的工具选择策略是 prompt/schema 引导 + 工具池过滤 + ToolSearch 局部检索排序 + 权限/失败反馈纠偏，不是一个独立 planner/ranker 模块。

1. 真正选工具的是模型，不是本地 router

query.ts 收到模型输出的 tool_use 后，只是收集 ToolUseBlock，再交给 runTools() / runToolUse() 执行。

runToolUse() 的第一步是 findToolByName(tools, toolUse.name)。也就是说：模型已经给出了工具名，本地不是在多个候选里重新选择一个，而是按名字查找并执行。

2. 工具池会先被过滤，但不是按任务打分

tools.ts 里 getAllBaseTools()、getTools()、assembleToolPool() 决定本轮有哪些工具能出现在模型上下文里。

过滤条件包括 simple mode、REPL mode、feature flag、工具 isEnabled()、permission deny rules、MCP 工具合并去重等。这是在决定“模型能看见哪些工具”，不是对当前子任务计算“哪个工具最好”。

如果抽象成流程，是这样：

getAllBaseTools() 收集内置工具：Bash、Read、Edit、Write、Grep、Agent、Todo、WebFetch 等。
getTools() 根据模式、feature、deny rule、是否启用过滤工具。
assembleToolPool() 合并内置工具和 MCP 工具，并按名称排序，主要为了 prompt cache 稳定。
toolToAPISchema() 把每个工具的描述和 schema 发给模型。
模型根据工具描述和任务上下文生成 tool_use.name。
runToolUse() 按名字执行该工具；失败则返回错误 tool_result，下一轮模型纠偏。
没有看到这种通用模块：
subtask = "搜索某个函数定义"
candidates = [Grep, Glob, Bash(rg), Agent, LSP]
scores = rank(candidates, subtask)
chosen = argmax(scores)
execute(chosen)

源码里更接近这样：
tools = assembleToolPool(permissionContext, mcpTools)
toolSchemas = tools.map(toolToAPISchema)
assistant = callModel(messages, toolSchemas)
for toolUse in assistant.tool_use_blocks:
  tool = findToolByName(tools, toolUse.name)
  runToolUse(tool, toolUse.input)

3. 有排序，但不是语义工具选择排序

assembleToolPool() 会把 built-in tools 和 MCP tools 各自按 tool.name.localeCompare() 排序，再用 uniqBy(..., 'name') 去重。

源码注释说明这个排序主要是为了 prompt-cache 稳定：built-ins 保持连续前缀，避免 MCP 工具插入导致缓存 key 抖动。它不是“Read 比 Bash 分高”这种任务语义排序。

4. 有打分，但只在 ToolSearch 里

真正有 score 的地方是 ToolSearchTool。它只解决一个问题：当工具太多或 MCP 工具被 deferred 时，模型先用 ToolSearch 按关键词找可能相关的 deferred tools。

searchToolsWithKeywords() 会对工具名、MCP server/action 名、searchHint、工具 prompt description 做关键词匹配并加分，然后按 score 降序返回前 N 个匹配。

5. ToolSearch 的分数怎么来的

大致权重是：工具名 part 精确命中分最高，MCP 工具名命中权重更高；part 包含次之；searchHint 命中再加分；description 命中加较低分。还支持 +term 表示 required term，必须匹配才进入候选。

但这个分数只用于“找出哪些 deferred 工具 schema 应该加载”，不是用于执行时在 Read/Grep/Bash/Agent 之间做最终选择。

6. select: 是直接选择，不是排序

ToolSearch 支持 select:Read,Edit,Grep 这种形式。源码里会按名字找 deferred tools 或已加载工具，找到就返回 tool_reference。

这相当于模型明确说“我要加载这些工具”，不是 Claude Code 本地判断“这个子任务最适合这些工具”。

所以，Claude Code 处理“多个工具都能做”的主要方式是把选择策略写进 prompt，而不是写成算法 ranker：

7. 系统提示里有偏好规则

constants/prompts.ts 里有非常直接的偏好：读文件用 Read 而不是 cat/head/tail/sed；编辑文件用 Edit 而不是 sed/awk；创建文件用 Write 而不是 heredoc/echo；找文件用 Glob，搜内容用 Grep。

这类规则本质是给模型的 tool-use policy。模型遵守得好，就会优先用专用工具；遵守不好，本地权限、校验和错误结果再纠偏。

8. 各工具 prompt 也写了适用边界

例如 AgentTool/prompt.ts 写明：如果只是读某个明确文件路径，用 Read，不要用 Agent；如果只在 2-3 个文件里搜，也用 Read；开放式多轮搜索才考虑 Agent。

GlobTool / GrepTool prompt 也提示：开放式搜索、可能需要多轮 grep/glob 时，用 Agent。WebFetchTool prompt 说 GitHub URL 优先用 Bash 里的 gh CLI，若 MCP web fetch 可用则优先 MCP。

9. 权限系统会间接改变选择

如果某个工具被 deny rule 过滤掉，模型根本看不到；如果某个工具调用被用户拒绝或 hook 拒绝，Claude Code 会返回错误 tool_result，系统提示还要求不要重复同一个被拒绝调用，而要调整 approach。

这不是预先打分，而是运行时反馈驱动：工具不可用或失败后，下一轮模型重新选择。

10. 并发调度也不是选择策略

toolOrchestration.ts 会用 isConcurrencySafe() 把工具分成并发安全批次和串行批次；StreamingToolExecutor 也会控制流式工具并发。

这解决的是“已经选好的多个工具怎么执行”，不是“同一子任务多个工具谁更好”。

一个具体例子：要找 runToolUse 的实现，候选看起来有 Grep、Bash(rg)、Agent、LSP。Claude Code 不会本地给四个候选打分。它会把工具说明发给模型；系统提示告诉模型搜内容用 Grep 而不是 shell grep，开放式多轮调查可用 Agent；如果模型调用 Grep，运行时执行 Grep；如果模型误用 Bash，也主要靠 prompt、权限和失败反馈纠正，而不是本地强行改成 Grep。

最短总结：Claude Code 有“工具发现排序”而没有“通用工具选择打分器”。ToolSearch 会给 deferred tools 做关键词打分排序；但普通 Read/Grep/Bash/Agent/Edit 之间的选择，主要由模型根据工具描述和系统提示决定，Claude Code 本地只做可用性过滤、schema 校验、权限控制、执行调度和失败反馈。
