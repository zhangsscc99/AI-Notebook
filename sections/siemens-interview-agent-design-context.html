Agent 跑十分钟就崩，八成是上下文问题：要么塞满了，要么丢了关键信息。这一层解决的就是"给模型的提示词里应该有什么"——它决定了 Agent 能不能做长任务。

一句话定义：上下文管理 = 在有限窗口内做成本与信息的权衡：哪些压成摘要、哪些保留原文、哪些去检索、哪些只留引用。记忆则分三层：会话（短）、情节（可检索的历史）、语义（稳定事实）。

Q1：上下文与记忆的类怎么分

ContextManager：唯一的"组 prompt"入口

三样东西拼起来：系统提示 + 最近 N 轮原文 + 检索到的相关片段。所有拼装逻辑集中在这一个类，而不是散在各个 Agent 里——否则你会发现有五处不同的 token 预算算法。

TokenCounter：别用字符数估算

中文、代码、JSON 的 token 密度差异极大。用真实 tokenizer 计数（或 provider 返回的 usage 反推），并且预留输出空间——窗口 100k、输入 98k，模型就没有空间回答。

Compressor：压缩 ≠ 截断

截断会丢掉"为什么这么改"的决策链。正确做法是分层压缩：早期对话→结构化摘要（决策、已排除方案、未完成项）；工具大输出→只留结论与 artifactUri；失败尝试→保留失败原因（避免重复踩坑）。

MemoryStore 三实现，别混用

SessionMemory 有 TTL（一次任务的生命周期）；EpisodicMemory 是 SQLite + FTS5 + 向量，用于"上次改这个模块遇到过什么"；SemanticMemory 存稳定事实（项目约定、架构决策），带 LRU 淘汰。

Retriever：混合检索而不是纯向量

纯向量对函数名、错误码这类精确 token 很差。用 BM25（FTS5）+ 向量并行召回再融合（RRF 或加权），召回到的 Ref 只放"片段 + 路径"，让模型自己决定要不要读全文。

Embedder 独立出来

换模型（本地 → API）时不影响检索逻辑；批量 embedding 与在线查询的路径也不同。抽象出来还能做"同一份数据两套索引"的 A/B。

Q2：上下文快满时到底发生什么（时序图逐段读）

在 80% 就动手，不要等 100%。阈值留出 20% 给输出和工具结果；到 100% 才压缩，只能砍掉最需要的内容。
压缩是有结构的。摘要必须包含三样：做过的决策、排除的方案与原因、未完成的 TODO。缺了第三项，Agent 会忘记自己还要干什么。
近期轮次保留原文。最近 3–5 轮是"工作记忆"，压缩会让它丢失精确参数（文件路径、行号、错误码）。原则：近处不压，远处才压。
检索按当前目标走。用当前 step 的 intent 做查询，而不是整个任务目标——任务目标太宽，召回会发散。
并行查两路再融合。FTS5 关键词 + 向量语义，结果去重后按分数融合取 Top-K（K 通常 5–8）；再多就是噪声。
引用而不是全文。片段 + 路径给模型，需要时它自己用 read 工具去读。这样"上下文只付一次便宜的钱"。

Q3：失败模式与对策

压缩后反复做同一件事

现象：摘要丢了"已尝试失败"的信息。
对策：摘要模板里强制字段 attempts[]（尝试 + 失败原因），并在 system 提示里声明"不要重复已失败的方案"。

工具输出淹没上下文

现象：一次测试跑出 3000 行日志。
对策：工具侧就截断（前 50 行 + 后 50 行 + 摘要），全文落盘；ContextManager 只认 artifactUri。

检索召回不相关

现象：查"部署失败"召回三年前的目录结构。
对策：加时间衰减与来源权重（本项目 > 全局笔记），并限制候选池；召回后做一次 rerank。

记忆污染

现象：把临时结论写进长期记忆，之后一直被误导。
对策：写入只允许显式事实（用户偏好、架构决策），并带 TTL 与置信度；过程性内容只进 Trace，不进 SemanticMemory。

Q4：指标

上下文效率：平均输入 token / 每步、压缩触发率、压缩后任务成功率（压缩质量的核心指标）；检索：召回命中率（被引用片段是否真被用到）、Top-K 使用分布（K 太大没人用就是浪费）；记忆：写入量 / 淘汰量、检索延迟 P99；成本：缓存命中率（同样的前缀重复计费很常见）。

Q5：面试追问

"为什么不直接上 1M 上下文大模型？"

三个理由：贵（token 线性计费）、慢（长上下文首字延迟显著上升）、注意力退化（关键信息在中间位置时召回明显下降）。窗口大不等于该塞满。

"摘要由模型生成，会不会丢关键细节？"

会，所以摘要只压"叙述性内容"，不压"机器可校验的东西"：文件路径、命令、错误码、diff 哈希一律原样保留在结构化字段里，只压缩推理过程。

"多轮会话怎么记住用户偏好？"

偏好属于 SemanticMemory：抽取成键值对（如 prefers: concise），带来源与时间；注入位置固定在 system 提示末尾，避免被长上下文冲淡。

"怎么评估上下文策略好坏？"

离线用固定任务集 A/B（同一任务，压缩 vs 不压缩），比较成功率、步数、token；线上看"压缩后是否重复劳动"这个代理指标。不看指标的策略优化都是玄学。

收尾句：「上下文管理的目标不是'把窗口塞满'，而是让每一步只看见此刻真正需要的那一小块——这跟人做长任务的注意力管理是同一件事。」
