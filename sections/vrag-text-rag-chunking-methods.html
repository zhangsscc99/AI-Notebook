文本 RAG 的切块一般有几种方法

文本 RAG 的“切块”不是随便把文章切短。它的核心目标是：让每个 chunk 足够小，能被 embedding / reranker / LLM 处理；又足够完整，保留回答问题所需的语义单元。切太小会丢上下文，切太大会召回不准、上下文浪费。

一句话：文本切块的本质是在“语义完整性”和“检索粒度”之间折中。常见方法可以分成：固定长度、重叠滑窗、结构化切分、语义切分、递归切分、问答/命题化切分、层级切分。

1. 固定长度切块

按字符数或 token 数硬切，比如每 500 tokens 一块。这种方法最简单、稳定、容易控制长度。

缺点是可能从句子中间、表格中间、代码中间切断，导致 chunk 语义不完整。适合脏数据初版、海量网页、低成本 baseline。

2. 滑动窗口 + overlap

固定长度基础上加重叠区域，比如 chunk size 800 tokens，overlap 100 tokens。这样前后文不会完全断裂。

优点是召回更稳；缺点是索引膨胀、重复内容多、reranker 和 LLM 容易看到重复证据。

3. 按结构切块

按 Markdown 标题、HTML 节点、PDF 章节、段落、表格、代码块、列表项切分。它优先保留作者写作结构。

这是工程里非常常用的方法，因为标题、章节、段落天然就是语义边界。缺点是不同文档格式质量不一，PDF 解析尤其容易乱。

4. 递归切分

先按大边界切，比如章节；太长再按段落；还太长再按句子；最后才按 token 硬切。

它比单纯固定长度更稳：尽量保留结构，只有超长时才退化到更细粒度。

5. 语义切分

用 embedding 或模型判断相邻句子的语义相似度，在话题变化处切开。比如一段从“产品功能”转到“价格政策”，相似度下降，就作为切点。

优点是更接近人类阅读边界；缺点是成本更高，而且对 embedding 模型质量敏感。

6. 命题化 / atomic facts 切分

把长段落改写成多个原子事实或 QA 对。例如“公司 A 在 2020 年收购 B”变成一个独立 proposition。

这种方法适合高精度知识库、法律/金融/医疗条款，但构建成本高，且需要额外模型做信息抽取。

7. 父子 chunk / 层级切分

小 chunk 用于检索，大 chunk 或父文档用于回答。比如用句子级 chunk 召回，再把它所在的整段或整节返回给 LLM。

它解决了“小块召回准但上下文少”的矛盾，是实际 RAG 系统里很常见的优化。

8. 表格、代码、公式的专门切法

表格最好按行/列语义、表头和单位一起保留；代码按函数/类切；公式要保留定义、变量解释和上下文。

这些内容不能简单按 token 切，否则 embedding 能召回但 LLM 看不懂。

常见选择：
- 通用文档：递归切分 + overlap
- Markdown/HTML：按标题层级切，超长再递归
- 高精度知识库：结构切分 + proposition/QA 化
- 长报告/PDF：页/段/标题混合切分，保留页码和章节 metadata
- 代码库：按函数、类、文件符号切分
- 表格：按表格对象或带表头的行组切分
最短总结：文本 RAG 切块不是一个固定答案。粗略 baseline 用固定长度 + overlap；更好的系统会利用文档结构；再高级会做语义切分、父子 chunk、命题化和领域专门切分。
