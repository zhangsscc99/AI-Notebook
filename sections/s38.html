OpenClaw 记忆的 sync 是什么时候触发的

OpenClaw memory sync 不是只有一个入口。源码里它是多触发器机制：搜索时兜底、文件变化时触发、会话 transcript 增量触发、session start 预热、定时触发、手动/CLI/status 触发。不同触发器的目的不一样。

一句话：第一次搜索没索引会同步强制建；memory 文件变化会 watcher 延迟建；session transcript 变化会 debounce + delta 阈值后建；配置了 interval 会定时建；session-start 和 search 也会做后台预热/刷新。

1. 首次搜索兜底触发

MemoryIndexManager.search() 先检查 hasIndexedContent()。如果 chunks / FTS 里没有内容，会执行 sync({ reason: "search", force: true })。这是同步阻塞式 bootstrap，目的是第一次读记忆不要空查。

2. 搜索时异步刷新

如果已经有索引，但 dirty 或 sessionsDirty，搜索时会走 startAsyncSearchSync()，用 reason="search" 后台刷新。当前搜索可以先用旧索引返回，避免每次搜索都卡住。

3. memory 文件 watcher 触发

ensureWatcher() 监听 MEMORY.md、memory/ 和 extraPaths。文件 add/change/unlink/unlinkDir 后设置 dirty=true，再按 watchDebounceMs 延迟调用 sync({ reason: "watch" })。

4. session transcript 增量触发

如果 sources 包含 sessions，ensureSessionListener() 会监听 transcript update。它不会每行 JSONL 都立刻 sync，而是 5 秒 debounce，再看 deltaBytes / deltaMessages 是否达到阈值，达到才 sync({ reason: "session-delta" })。

5. session-start 预热触发

warmSession() 在配置 sync.onSessionStart 开启时，会对每个 sessionKey 触发一次 sync({ reason: "session-start" })。它是预热，不是每轮对话都强制重建。

6. interval 定时触发

如果配置了 sync.intervalMinutes，ensureIntervalSync() 会 setInterval 定时跑 sync({ reason: "interval" })。这是兜底补偿，防 watcher 漏事件或外部批量修改。

可以按这张触发图理解：

memory_search
  ├─ no indexed content -> sync(reason="search", force=true)  # 首次强制建索引
  └─ dirty/sessionsDirty -> async sync(reason="search")       # 后台刷新

MEMORY.md / memory/ / extraPaths changed
  -> watcher mark dirty
  -> debounce
  -> sync(reason="watch")

session transcript updated
  -> onSessionTranscriptUpdate
  -> 5s debounce
  -> deltaBytes / deltaMessages threshold
  -> sync(reason="session-delta")

new session starts
  -> warmSession
  -> sync(reason="session-start") if enabled

interval configured
  -> setInterval
  -> sync(reason="interval")

sync 触发后一定重建全部吗

不一定。runSync() 会先判断是否需要 full reindex。只有 force、provider/配置变化、sources/scope/chunk 参数变化等情况才会全量重建。普通 watcher sync 会比较 hash，只重建新增或变化文件。

watch 为什么要 debounce

一次编辑可能产生多次 add/change 事件；写文件也可能先写临时文件再 rename。debounce 可以把一串文件系统事件合成一次 sync，避免频繁重建索引。

session 为什么有 delta 阈值

session transcript 是持续追加的 JSONL。如果每条消息都立即 reindex，成本太高。deltaBytes / deltaMessages 用来等积累到一定变化量再同步。

什么时候最确定会同步建索引

最确定的是“第一次 memory_search 且索引为空”：源码直接 force sync。其他触发多是配置和 dirty 状态驱动。

结论：OpenClaw memory sync 是“按需 + 事件 + 定时”的组合。它不是每次对话都全量重建，也不是只有搜索时才建；它用首次搜索兜底保证可用，用 watcher/session delta/interval 保持索引新鲜。
