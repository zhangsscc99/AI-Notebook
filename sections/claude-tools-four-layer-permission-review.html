Claude Code 权限四层详细解读：规则过滤、工具自检、模式兜底、AI 分类器动态审查

你记的“四层”方向是对的，但源码里要稍微校正一下：这四层不是唯一的全部链路。在它们之前还有 schema / validateInput / PreToolUse hook；在它们之后才是 permission UI / SDK host / coordinator / swarm leader 审批和真正 tool.call()。

更准确的一句话：Claude Code 工具权限核心是：先用规则和工具自检做确定性拦截，再用 permission mode 改变 ask/allow/deny 的默认策略；如果进入 auto mode 或 Bash prompt classifier 场景，再用 AI classifier 对“本次具体动作”做动态审查。

先看总入口：工具不是直接执行

src/services/tools/toolExecution.ts 的 checkPermissionsAndCallTool() 是总闸门。它先做 Zod schema 校验，再调用工具自己的 validateInput()，然后跑 runPreToolUseHooks()，最后通过 resolveHookPermissionDecision() 进入 canUseTool / hasPermissionsToUseTool()。只有最终 permissionDecision.behavior === "allow" 才会调用 tool.call()。

// toolExecution.ts 简化逻辑
parsedInput = tool.inputSchema.safeParse(input)
if (!parsedInput.success) return InputValidationError

isValidCall = await tool.validateInput?.(parsedInput.data, context)
if (isValidCall?.result === false) return tool_use_error

hookPermissionResult = await runPreToolUseHooks(...)
resolved = await resolveHookPermissionDecision(
  hookPermissionResult,
  tool,
  processedInput,
  context,
  canUseTool,
  assistantMessage,
  toolUseID,
)

if (resolved.decision.behavior !== "allow") return permission_denied_result
return await tool.call(resolved.input, context)

四层模型怎么对应源码

规则过滤层。permissions.ts 先查整工具 deny / ask：getDenyRuleForTool()、getAskRuleForTool()。Bash 还会在 bashPermissions.ts 里查 Bash(command)、Bash(prefix:*)、wildcard、子命令 deny/ask/allow。
工具自检层。通用入口调用 tool.checkPermissions(parsedInput, context)。Bash 会解析 AST、拆 subcommands、检查 command injection、重定向、cd+git、路径约束；Edit/Write 会检查目标路径、敏感目录、symlink resolved path、.claude/.git/shell config 等。
模式兜底层。工具自检没有 deny/ask 后，通用权限流才处理 bypassPermissions、整工具 allow rule、passthrough → ask。外层 hasPermissionsToUseTool() 再把 dontAsk 的 ask 转 deny，把 headless / async agent 的 ask 转 PermissionRequest hook 或 auto-deny。
AI 分类器动态审查层。auto mode 下，如果前面结果是 ask，源码会调用 classifyYoloAction()，把当前 transcript、工具列表、动作文本一起交给 side query 分类。Bash 还有 prompt-rule classifier：classifyBashCommand() 可基于用户写的自然语言 allow/ask/deny 规则判断具体命令。

第一层：规则过滤不是简单 allowlist

规则来源包括 settings、CLI arg、command、session。整工具规则先判断，比如 Edit deny 会直接拒绝。内容级规则在工具内部处理，比如 Bash(rm:*)、Read(/tmp/**)、Edit(src/**)。

关键优先级：deny 优先于 ask，ask 优先于 allow。Bash 对 deny/ask 还会更激进地 strip env vars，防止 FOO=bar rm ... 绕过 deny。

第二层：工具自检懂具体风险

通用规则不知道 cd evil && git status、sed、输出重定向、symlink、Windows NTFS stream、.claude/settings.json 哪些危险。所以每个工具实现 checkPermissions()，把业务语义变成 allow / ask / deny。

例子：checkWritePermissionForTool() 会先查 edit deny，再允许内部 plan/scratchpad 路径，再做 checkPathSafetyForAutoEdit()，然后才考虑 acceptEdits、allow rule、默认 ask。

第三层：模式兜底改变默认行为

bypassPermissions 在源码里不是第一优先级，而是在 deny、工具自检 deny、requiresUserInteraction、content ask rule、safetyCheck 之后才 allow。因此它不是“完全无安全”。

acceptEdits 会让工作目录内的文件写入、部分 Bash 文件系统命令更容易自动 allow；dontAsk 会把 ask 变 deny；headless/async agent 没有弹窗时会先跑 PermissionRequest hook，否则自动 deny。

第四层：AI classifier 是动态审查，不是固定规则

auto mode 下，前面如果得到 ask，Claude Code 不直接弹窗，而是构造 action：formatActionForClassifier(tool.name, input)，再调 classifyYoloAction(messages, action, tools, permissionContext)。分类器返回 shouldBlock、reason、usage、model、duration。

如果 block：返回 deny，并记录 denial tracking；如果 allow：返回 allow。classifier 不可用时是否 fail closed 由 tengu_iron_gate_closed 控制。

实际源码优先级：你的四层要这样排

// permissions.ts 简化后的真实顺序
if (wholeToolDenyRule) return deny              // 规则过滤
if (wholeToolAskRule && !sandboxAutoAllow) return ask

toolResult = await tool.checkPermissions(...)   // 工具自检
if (toolResult.behavior === "deny") return deny
if (tool.requiresUserInteraction?.() && toolResult.behavior === "ask") return ask
if (contentAskRule || safetyCheck) return ask   // bypass 也绕不过

if (mode === "bypassPermissions") return allow  // 模式兜底
if (wholeToolAllowRule) return allow

result = toolResult.passthrough ? ask : toolResult

// hasPermissionsToUseTool 外层
if (result.ask && mode === "dontAsk") return deny
if (result.ask && mode === "auto") return classifyYoloAction(...) // AI 动态审查
if (result.ask && shouldAvoidPermissionPrompts) return hook_or_auto_deny
return result

拿两个具体例子串起来

例子 A：Edit .claude/settings.json

第一层先看有没有 Edit 或路径 deny。第二层进入 checkWritePermissionForTool()，命中 checkPathSafetyForAutoEdit() 的 Claude config safety check，返回 ask。第三层即使是 bypassPermissions，safetyCheck 仍在 bypass 前生效。第四层如果 auto mode 且该 safetyCheck 标记 classifierApprovable，才可能交给 classifier；否则必须人工确认或拒绝。

例子 B：Bash FOO=1 rm -rf build

第一层 Bash 内容规则会用更强 env stripping 检查 deny/ask，所以 Bash(rm:*) 不会被 FOO=1 绕过。第二层 Bash 解析 AST / legacy parser，查 operator、subcommand、重定向、路径、command injection。第三层如果没有规则也没有危险，read-only 可 allow，否则 passthrough 变 ask。第四层 auto mode 下才由 classifier 判断这次 rm 是否应该 block。

结论：你说的四层可以作为讲解框架，但要补一句关键 nuance：AI 分类器不是所有工具调用的“最后一道必经审查”，它只在 auto mode 或 Bash prompt-rule 场景介入；确定性 deny / safetyCheck / requiresUserInteraction 仍然优先。
