Hermes 支持哪些沙箱方案：技术选型优劣对比

Hermes 的“沙箱方案”分两层：第一层是 Terminal Backend，决定命令在哪里跑；第二层是 工具执行沙箱，比如 execute_code，决定多步工具过程怎么被压缩、限制和返回。做技术选型时，不要只问“哪个最安全”，要问：任务是本地开发、云端长期任务、HPC、RL rollout、还是上下文压缩。

一句话选型：本地快速任务用 local；真实项目开发优先 Docker；HPC 用 Singularity/Apptainer；远端机器/GPU 用 SSH；云端持久 agent 用 Modal / Daytona；前端/Node 云运行可看 Vercel Sandbox；上下文工程用 execute_code。

1. local：最快，但不是隔离沙箱

是什么：命令直接在宿主机执行，cwd 就是本机目录。

优点：最快、最简单、没有容器启动成本；最适合读文件、轻量脚本、你完全信任的项目。

缺点：隔离最弱。agent 装依赖、删文件、启动进程都会影响宿主机。

适合：个人临时任务、小脚本、低风险 repo、只读分析。

2. Docker：默认推荐的工程沙箱

是什么：Hermes 创建 Docker 容器，在容器里跑 shell；可选择是否把当前项目 bind mount 到 /workspace。

优点：依赖隔离好、可用镜像复现环境、支持 CPU/内存/磁盘限制，适合跑测试、构建、安装依赖。

缺点：需要 Docker；bind mount 后项目目录是真实暴露的；Docker Desktop / Linux 权限细节可能影响文件 owner。

适合：代码修改、SWE 任务、真实项目测试、避免污染宿主环境。

3. Singularity / Apptainer：HPC 场景更合适

是什么：面向 HPC/科研集群常见的容器运行方案，Hermes 可通过 singularity_image 使用 Docker 格式镜像源。

优点：更适合共享集群、GPU/HPC 管理环境；很多机构不允许 Docker daemon，但允许 Apptainer/Singularity。

缺点：本地开发生态不如 Docker 普遍；镜像、挂载、权限模型和 Docker 不完全一样。

适合：科研集群、GPU 队列、企业/学校 HPC 环境。

4. SSH：把执行放到远端机器

是什么：Hermes agent 逻辑还在本地/服务端，但命令通过 SSH 在远端服务器执行。

优点：可用远端 GPU、大内存、内网资源；不需要把 agent 整个部署过去；适合已有服务器。

缺点：它不是容器隔离，隔离强弱取决于远端账号权限；网络延迟和 SSH 可靠性会影响体验。

适合：远端开发机、GPU server、公司内网构建环境、VPS 长任务。

5. Modal：云沙箱 / serverless 执行

是什么：命令跑在 Modal 云沙箱里。Hermes 支持 direct Modal，也有 managed Modal gateway 的选择逻辑。

优点：云端运行、可持久化文件系统、空闲可休眠；适合无需用户电脑常开的 agent。

缺点：依赖 Modal 凭据或 managed gateway；文件同步/项目来源要设计好；成本和冷启动需要考虑。

适合：云端长期 agent、批量任务、RL rollout、需要弹性资源的执行。

6. Daytona：云 workspace 型沙箱

是什么：命令在 Daytona cloud sandbox / workspace 里执行，需要 Daytona SDK 和 API key。

优点：更像远端开发 workspace；适合保存项目状态、长期任务、跨会话继续。

缺点：依赖外部服务；磁盘/资源有平台限制；项目同步、凭据管理要额外规划。

适合：远程 coding workspace、长期工程任务、agent 不依赖本地电脑的场景。

7. Vercel Sandbox：偏 Web / Node 云运行

是什么：Hermes 支持 vercel_sandbox backend，在 Vercel Sandbox 云环境里执行命令。

优点：适合 Web/Node 生态、前端预览、serverless 风格任务；和 Vercel 平台集成思路接近。

缺点：需要对应 runtime / SDK / 平台配置；不一定适合复杂系统级构建或任意 Linux 工作负载。

适合：前端项目、Node/Web demo、预览型工作流。

8. execute_code：不是机器隔离，主要是上下文隔离

是什么：Hermes 生成受控 hermes_tools.py，让 Python 脚本在受限工具集合里做多步调用、过滤、聚合、摘要。

优点：减少主模型上下文污染；可把 20 次工具调用压缩成一个结构化结果；有 timeout、stdout cap、工具调用次数限制和 secret redaction。

缺点：它不是替代 Docker 的安全边界；脚本执行在哪里，仍取决于当前 terminal backend 和 execution mode。

适合：上下文工程、批处理工具调用、日志压缩、批量文件分析。

只想最快完成低风险任务：选 local。
要改真实代码且不想污染电脑：选 Docker，必要时 bind mount 项目到 /workspace。
在学校/公司 HPC 或 GPU 集群：优先 Singularity / Apptainer，或者 SSH 到集群登录节点/开发节点。
有现成远端机器：选 SSH；但要把远端账号权限当作安全边界。
想让 agent 云端长期运行：选 Modal / Daytona，重点设计项目同步、凭据、成本和持久化。
工具输出太长：不要只换 Docker；用 execute_code / worker 做上下文压缩。
Hermes sandbox selection matrix

local
  best for: fast trusted tasks
  risk: affects host directly

docker
  best for: real coding + tests + dependency isolation
  risk: mounted project is real

singularity / apptainer
  best for: HPC / research clusters
  risk: more cluster-specific behavior

ssh
  best for: remote GPU / VPS / internal servers
  risk: remote account permissions define blast radius

modal
  best for: cloud sandbox, elastic jobs, RL rollouts
  risk: service credentials, sync, cost, cold start

daytona
  best for: persistent remote workspace
  risk: external service dependency, resource limits

vercel_sandbox
  best for: Web / Node / preview-style tasks
  risk: platform/runtime constraints

execute_code
  best for: context engineering and multi-tool compression
  risk: not a replacement for OS/container isolation
推荐默认策略：个人 coding agent 先用 Docker；大规模/云端 agent 用 Modal 或 Daytona；HPC 用 Singularity；上下文污染问题用 execute_code。不要把所有问题都叫“沙箱问题”：安全隔离、运行位置、持久化、成本、上下文压缩是不同维度。
