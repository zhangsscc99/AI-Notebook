项目里的 reward 每个部分到底是什么意思：updated / exact / similarity / tag_format / no_extra_prose / syntax

这次只看项目里的 reward。代码位置是 /root/rlhf/fastapply_pipeline/rewards.py。它把模型输出拆成 5 个分项，再加权成总分：

total = 0.55 * exact
      + 0.20 * similarity
      + 0.10 * tag_format
      + 0.05 * no_extra_prose
      + 0.10 * syntax

updated 标签是什么

<updated>...</updated> 是这个 FastApply 任务规定的输出容器。模型不能随便解释，必须把最终更新后的完整代码放在这个标签里：

<updated>
def add(a, b):
    return a + b + 1
</updated>

项目先用 extract_updated_tag(output) 把标签内部代码抽出来。如果抽到了，就拿标签里的内容当 candidate；如果没抽到，就把整个 output 当 candidate。

为什么要用 updated 标签

因为代码 Apply 场景后面通常要自动接机器流程。如果模型输出“好的，我帮你修改如下：```python ...```”，人能看懂，但程序不好直接 apply。updated 标签就是机器可解析边界。

  • 标签内：真正要应用的代码。
  • 标签外：最好什么都没有。
  • 没有标签：格式分会扣，后续自动化风险变高。

exact 是什么意思

exact 就是“抽出来的 candidate 是否和标准答案 expected_source 完全一致”。项目里会先做很轻的归一化：

normalize_code(text) = text.replace("\r\n", "\n").strip()
exact = normalize_code(candidate) == normalize_code(expected_source)

所以它主要忽略首尾空白和 Windows 换行，但不会宽容代码内容差异。少一行、多一个注释、把 +1 写成 +2，一般都是 exact=0。

exact 为什么权重最高

FastApply 的目标不是“答案大概对”，而是 patch 合并后的代码要能精确落地。exact 权重 0.55 最高，表示训练最想鼓励完整、准确、无遗漏地生成目标代码。

如果 exact=1，通常说明核心任务已经完成；其他项更多是在约束格式、语法和输出洁净度。

similarity 的 difflib 是什么

similarity 用的是 Python 标准库 difflib.SequenceMatcher。它会比较两个字符串序列有多少可对齐的相同片段，返回一个 0 到 1 的相似度：

similarity = SequenceMatcher(None, candidate, expected).ratio()
  • 1.0：两个文本几乎完全一样。
  • 0.8：大部分相同，但有一些插入、删除或替换。
  • 接近 0：内容基本不像。

similarity 有什么用

它是“软分”。如果只用 exact，错一个字符就 0 分，GRPO 早期会很稀疏。similarity 让“接近正确”的输出也有一点信号，比如函数主体大体对但漏了缓存逻辑，它 exact=0，但 similarity 可能还能给 0.7 左右。

注意：difflib 只是文本相似，不懂程序语义。两个代码文本很像，不代表行为一定正确；两个代码文本不同，也可能语义等价。

tag_format 啥意思

tag_format 只检查能不能抽到 <updated>...</updated>：

extracted = extract_updated_tag(output)
tag_format = 1.0 if extracted is not None else 0.0

也就是说，只要标签存在且能被正则抽取，就给 1。它不判断代码对不对，只判断“有没有按协议把代码放进 updated 标签”。

tag_format 和 exact 的区别

  • tag_format：看包装格式。有没有 updated 标签。
  • exact：看标签里的代码内容。是否等于标准答案。

所以可能出现：标签写对但代码错，tag_format=1、exact=0；或者代码内容对但没标签，exact 可能因为整个 output 混了文本而变差，tag_format=0。

no_extra_prose 啥意思

no_extra_prose 是“没有额外废话”。项目里这样判断：

stripped = output.strip()
no_extra = stripped.startswith("<updated>") \
        and stripped.endswith("</updated>")

它要求整个输出去掉首尾空白后，开头就是 <updated>，结尾就是 </updated>。

哪些会扣 no_extra_prose

好的，修改如下：
<updated>...</updated>
<updated>...</updated>
解释：这里修复了缓存逻辑。
```python
<updated>...</updated>
```

这些都可能 tag_format=1，因为能抽到 updated；但 no_extra_prose=0，因为标签外有解释、Markdown fence 或其他文本。

syntax 怎么验证

syntax 调用 analyze_source(language, candidate)。目前项目里 Python 和 JS/TS 的逻辑不同：

  • Python：用 ast.parse(candidate)。能 parse 就 parse_ok=True，有 SyntaxError 就 false。
  • JavaScript / TypeScript：现在是轻量 regex，抽 function、const/let/var 等顶层符号，默认 parse_ok=True。
  • 其他语言：当前也默认 parse_ok=True。

syntax 能验证代码是否运行报错吗

不能。当前 syntax 主要验证“语法能不能解析”，不是运行时测试。

  • 能发现：Python 缩进错、括号没闭合、非法语法。
  • 不能发现：变量未定义、接口返回错、单测失败、逻辑错误、除零、网络请求失败。
  • JS/TS 当前更弱，因为还没接 tree-sitter / tsc / eslint，只是结构占位。
所以 syntax=1 只表示“看起来像合法代码”，不表示“运行一定不报错”。要验证运行正确，需要加 unit tests、执行沙箱、type checker 或真实项目测试。
模型输出原文 output。
抽取 updated 标签得到 candidate。
candidate 和标准答案算 exact / similarity / syntax。
output 原文算 tag_format / no_extra_prose。
最终理解：exact 管正确性，similarity 给平滑信号，tag_format 管机器可解析边界，no_extra_prose 管别说废话，syntax 管最基本的语法合法性。 但当前 reward 还不是完整代码执行验证器，不能替代单测和真实运行。
