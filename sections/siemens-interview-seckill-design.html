笔试高频题："设计一个秒杀/抢购系统，先画核心类设计，再画下单流程。"一道题同时考类图（结构设计）、时序图（流程）、并发与流量控制。下面是一份能拿高分的参考答案——重点不是背图，是每个设计选择都能说出为什么。

答题策略：先画主干再补细节，主动跟面试官说"我先画核心结构，细节边讲边补"——粗粒度不是缺陷，是给追问留接口。

Q1：设计一个秒杀系统，画出核心类设计和下单时序图

第一部分：类图

分层思路：Controller → 编排服务 → 可替换的基础设施（库存/消息/落库）。三个关键决策先想好再动笔：

StockService 做成接口

Redis 预减、DB 乐观锁、Lua 原子扣三种实现可替换 → 依赖倒置 + 开闭原则，是给"换实现"追问埋的钩子。

MiaoshaService 做编排

并发预减、发消息这些秒杀特有逻辑集中在这，不污染 OrderService → 单一职责。

MQSender ◆ Message

消息对象生命周期依附发送动作 → 组合（实心菱形）。对比：购物车和商品是聚合，商品独立存在。

Controller - -> Service

Spring 注入本质是关联，画依赖（虚线箭头）也合理——被问到能讲"注入算长期持有，我画关联/依赖都说得通"即可。

第三部分：每一步的"为什么"（追问预案）

步骤设计动机面试官追问
Redis 预减挡掉 99% 流量，DB 只承担真实库存量级的写入"并发扣成负数怎么办？" → Lua 脚本保证原子性，check+decr 一步完成
MQ 异步下单削峰：瞬时 10w QPS 摊平成匀速落库；用户秒级拿到响应"用户不知道结果？" → 前端轮询订单状态 / 服务端推送
立即返回"排队中"异步体验权衡，秒杀场景用户可接受"能不能同步返回结果？" → 可以但失去削峰意义
incrBack 回滚消费失败要回补 Redis 库存，否则库存被"幽灵扣减""消息丢了怎么办？" → 持久化 + 手动 ack + 死信队列兜底
DB 乐观锁兜底update where stock>0 双保险，Redis 是缓存不是真相"Redis 挂了？" → 降级直查 DB + 限流，或本地库存标记

第四部分：现场话术

动笔前定调："秒杀的核心是并发和削峰，我把扣库存抽象成接口，MQ 做异步排队，落库单独一个服务。"
画完递话头："我留了几个扩展点：StockService 可换实现，流程上画了失败回滚，实际还要考虑消息可靠性。"
被问优化：接口限流（令牌桶）、库存本地标记（内存挡 Redis）、队列分片、消费端批量落库、秒杀链接动态化防刷。
被挑细节不慌："为什么是组合不是聚合？" → "消息的生命周期依附发送方，订单和商品那种独立存在的才是聚合。"
练习路径：① 照着抄一遍理解每个箭头 → ② 合上书默画 → ③ 自己加细节（token 校验、GoodsService）→ ④ 画完截图找人挑刺。画得漂亮不重要，每条线能讲出动机才重要。
