JoyAgent 工作流编排怎么讲才容易记住：设计类似系统的思路

JoyAgent 的工作流编排看起来难，是因为它同时包含产品入口、Agent 模式、工具系统、并行任务、文件产物、流式输出。讲的时候不要一上来讲类名，要先讲一个简单模型：它像一个项目经理带团队交付报告。

最容易记的版本：JoyAgent = 前台接单员 + 项目经理 + 执行员工 + 工具仓库 + 汇报员。用户给任务，前台建工单，项目经理拆计划，执行员工调用工具干活，汇报员把过程和最终文件流式交给用户。

1. 用“公司干活”来讲

把 JoyAgent 想成一个小公司：

  • 前台：GenieController，接用户请求，开 SSE 通道。
  • 工单：AgentContext，记录 query、文件、工具、输出样式、任务状态。
  • 派单员：AgentHandlerFactory，决定走 ReAct 还是 Plan-Solve。
  • 项目经理：PlanningAgent，拆任务、更新计划。
  • 执行员工：ExecutorAgent / ReactImplAgent，调用工具完成任务。
  • 工具仓库：ToolCollection，管理搜索、代码解释器、报告、文件、MCP 工具。
  • 汇报员：SummaryAgent + SSEPrinter，总结结果并推给前端。

2. 只记两种工作模式

JoyAgent 的工作流可以先压缩成两种模式：

简单任务：走 ReAct。一个 agent 边想边调用工具，直到完成。

复杂任务：走 Plan-Solve。先由规划器拆计划，再由执行器做子任务，执行结果再反馈给规划器，循环直到 finish。

简单任务：
用户问题 -> ReActAgent -> 工具调用 -> 总结

复杂任务：
用户问题 -> PlanningAgent -> ExecutorAgent(s)
        -> 结果反馈给 PlanningAgent -> 继续/结束
        -> SummaryAgent

3. 讲给别人时，按 5 句话讲

  1. JoyAgent 先把用户请求包装成一个 AgentContext 工单。
  2. 系统根据任务类型选择 ReAct 或 Plan-Solve 处理器。
  3. ReAct 适合一步步试工具；Plan-Solve 适合先规划、再执行、再反馈。
  4. 执行器不自己硬编码能力，而是通过 ToolCollection 调搜索、代码解释器、报告、文件、MCP 工具。
  5. 所有过程通过 SSE 流式推回前端，最后由 SummaryAgent 汇总结果和交付文件。

4. 最核心的设计思想

JoyAgent 的关键不是“有很多 agent 类”，而是把复杂任务拆成四层：

  • 产品层：接请求、SSE、前端展示、输出样式。
  • 状态层：AgentContext 保存一次任务的公共状态。
  • 编排层：Handler + PlanningAgent + ExecutorAgent 控制流程。
  • 能力层：ToolCollection + genie-tool 提供真实工具能力。

这四层分开后，系统才容易扩展：换工具不动 UI，换 agent 策略不动工具，换输出样式不动底层执行。

5. 为什么 Plan-Solve 更像真实项目管理

复杂任务不能只靠一个 agent 一路 ReAct 到底，因为上下文会变乱，任务边界不清楚。Plan-Solve 的优势是把“想清楚怎么做”和“具体去做”分开。

PlanningAgent 像项目经理：决定下一批任务。ExecutorAgent 像员工：完成具体任务。SummaryAgent 像秘书：把过程和产物整理成用户能看的结果。

6. 为什么它能并行

规划器返回多个任务时，用 <sep> 分隔。系统看到多个任务，就复制多个 ExecutorAgent 并发跑，等全部完成后把结果和 memory 合并回主执行器。

讲法很简单：项目经理一次派多个活，多名员工同时干，干完统一汇总。

接单。用户在 UI 提任务，后端创建 SSE 连接和 AgentContext。
选模式。HandlerFactory 判断走 ReAct 还是 Plan-Solve。
规划。复杂任务由 PlanningAgent 生成当前要做的 task；简单任务跳过规划直接 ReAct。
执行。ExecutorAgent / ReactImplAgent 调用 ToolCollection 里的工具。
反馈。工具结果写入 memory，并反馈给模型继续思考或给规划器更新计划。
交付。SummaryAgent 整理 taskSummary 和 fileList，SSEPrinter 推回前端。
One-minute explanation

JoyAgent is a productized multi-agent workflow.

It does not start from "one agent answers everything".
It starts from a work order:
  AgentContext = query + files + tools + output style + product files

Then it chooses a workflow:
  REACT      = one worker thinks and uses tools repeatedly
  PLAN_SOLVE = planner creates tasks, executors do tasks, planner checks again

Tools are not hardcoded inside the model:
  ToolCollection = built-in tools + MCP tools

Outputs are not only text:
  SummaryAgent returns task summary + generated files

Frontend does not wait blindly:
  SSE streams thoughts, plan, tool results, task summaries, final result

如果你要设计类似系统，按这个模板做

Step 1：先定义任务状态

不要先写 agent prompt。先定义类似 AgentContext 的状态对象：用户问题、会话 id、可用工具、文件列表、当前任务、产物、输出风格、stream 通道。

Step 2：再定义模式路由

把任务分成几类：简单问答走 ReAct；复杂交付走 Plan-Solve；数据分析走 DataAgent；固定流程走 Workflow。不要所有任务都塞进一个超级 agent。

Step 3：把工具做成注册表

工具不要散落在 prompt 里。做一个 ToolCollection：工具名、描述、参数 schema、执行函数、权限/日志/错误处理。这样模型只负责选择工具，不负责工具实现。

Step 4：把复杂任务拆成 Planner / Executor / Summarizer

Planner 管“下一步做什么”；Executor 管“怎么调用工具做”；Summarizer 管“怎么交付给用户”。这三个角色分开，复杂系统才不会混乱。

Step 5：设计流式事件

产品级 agent 不能黑盒等待。至少要输出 plan、当前 task、tool thought、tool result、task summary、final result。JoyAgent 的 SSEPrinter 就是在做这件事。

Step 6：最后再考虑并行和恢复

先把单任务跑通，再支持多个 task 并行。更进一步可以引入 LangGraph/checkpoint，把 JoyAgent 现在的 while loop 显式状态机化，方便恢复和人审。

记忆口诀：一张工单，一个派单员，两种模式，三个角色，一组工具，一个流式交付。工单是 AgentContext；派单员是 HandlerFactory；两种模式是 ReAct / Plan-Solve；三个角色是 Planner / Executor / Summary；工具是 ToolCollection；交付是 SSE。
