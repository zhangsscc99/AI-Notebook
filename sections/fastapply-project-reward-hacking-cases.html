在我们的 FastApply 项目场景里，有什么 reward hacking 情况

我们的任务是 source + patch → updated code。reward 由 exact、similarity、tag_format、no_extra_prose、syntax、rule/judge correctness 组成。这里面每一项都有可能被钻空子。

1）similarity hacking

模型复制大部分原始 source，让文本相似度很高，但关键 patch 没应用。尤其长文件里，只改一两行时，不改也可能和 reference 很像。

source 和 reference 99% 相同
模型直接复制 source
similarity 很高，但功能没修

2）format hacking

模型学会稳定输出 <updated> 标签，拿 tag_format / no_extra_prose 分，但标签里的代码不一定对。格式分不能替代 correctness。

3）syntax hacking

syntax=1 只说明语法能过，不代表逻辑正确。模型可能输出能 parse 的代码，但漏改 patch、删掉边界逻辑、返回错误值，仍然通过 syntax。

4）validity 低保分

RL-master 环境里 reward = 0.8 * correctness + 0.2 * validity。如果模型发现“只要输出非空 updated 就有 0.2”，可能早期偏向稳定输出模板，而不是真正提高 correctness。

5）judge hacking

如果 LLM judge 太宽松，模型可能输出看似合理、带解释性或语义模糊的代码，让 judge 误判 PASS。尤其是 reference 和 candidate 差异不大时，LLM judge 可能被“无害差异”说服。

6）多 updated 标签歧义

如果输出多个 <updated>，不同 extractor 取 first / last 的策略可能不同。训练时得分和部署时解析不一致，就会形成隐藏漏洞。

我们项目里最危险的 hacking 是：高 similarity + 格式正确 + syntax 可解析，但关键 patch 没真正应用。 因为这种样本看起来很像正确答案，却在真实工程里会失败。
