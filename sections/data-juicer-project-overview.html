概览介绍 Data-Juicer 数据清洗项目

Data-Juicer 是阿里开源的面向基础模型时代的数据处理 / 数据清洗系统。它不是一个单独的“去重脚本”，而是一套可配置、可组合、可扩展、可分布式运行的数据操作系统：用 YAML 或 Python 把一串算子组织成 pipeline，对文本、图像、音频、视频、多模态、Agent 轨迹、RAG 数据做清洗、过滤、去重、转换、分析和导出。

一句话：Data-Juicer = 数据加载/格式化 + 200+ 清洗算子 + pipeline 配方 + 本地/Ray 分布式执行器 + 监控/追踪/缓存/断点续跑 + 导出。它解决的是“把原始脏数据变成 AI-ready 数据”的工程问题。

2. 它的定位

README 里把它叫做“基础模型时代的数据操作系统”。它服务的不是某一种单点任务，而是整个 AI 数据生命周期：预训练语料清洗、SFT/RL 数据整理、Agent 交互轨迹清洗、多模态数据处理、RAG 索引前处理、数据质量分析等。

整体 pipeline：从原始数据到清洗后数据集

写配置。用户在 YAML 里指定 dataset_path、export_path、executor_type、process 算子列表。示例在 demos/process_simple/process.yaml。
启动任务。入口脚本 tools/process_data.py 调 init_configs() 读取配置，然后根据 executor_type 选择 DefaultExecutor、RayExecutor 或 PartitionedRayExecutor。
加载数据。DatasetBuilder 根据配置加载本地文件、目录、HuggingFace 数据集、JSON/CSV/Parquet/Text 等数据源，并包装成 NestedDataset。
加载算子。load_ops() 根据 YAML 里的 process 列表，从 OPERATORS registry 里实例化具体算子。
执行算子链。NestedDataset.process() 按顺序运行每个 OP：mapper 修改样本，filter 过滤样本，deduplicator 去重，selector 选择高质量样本，aggregator/grouper/pipeline 做更高层处理。
优化和容错。执行器支持 OP fusion、adaptive batch size、cache、checkpoint、skip_op_error、resource monitor、tracer，处理大规模数据时能提速、追踪、恢复。
导出结果。Exporter 把处理后的数据写到 export_path，支持分片、并行导出、S3 等场景。

核心设计：一切围绕 Operator 算子组织

Data-Juicer 的核心抽象是 OP / Operator。源码里 data_juicer/ops/base_op.py 定义了统一基类和注册表：

OPERATORS = Registry("Operators")

OP
  ├── Mapper       # 修改/转换样本
  ├── Filter       # 根据质量规则过滤样本
  ├── Deduplicator # 去重
  ├── Selector     # 按排序选样本
  ├── Grouper      # 分组
  ├── Aggregator   # 汇总
  └── Pipeline     # 数据集级 pipeline 操作

用户在 YAML 里写的算子名，例如 language_id_score_filter、text_length_filter、document_minhash_deduplicator，最终都会通过 OPERATORS.modules[op_name](**args) 实例化。

它有哪些数据清洗能力

文本清洗

包括长度过滤、语言识别、困惑度过滤、重复率过滤、特殊字符过滤、停用词比例、HTML 清理、链接/邮箱/IP 清理、Unicode 修复、句子切分、表格/参考文献/版权删除等。

去重

支持文档级 exact match、line-level 去重、MinHash LSH、SimHash、Ray 分布式去重、图像/视频去重等。适合大规模预训练语料去重。

多模态处理

覆盖图像、音频、视频：图像美学/NSFW/水印/尺寸/图文相似度，视频时长/分辨率/运动分数/水印/NSFW/OCR 面积，视频抽帧、caption、深度估计、目标分割、姿态估计等。

LLM/VLM 辅助清洗

有 LLM quality score、LLM difficulty score、LLM task relevance、VLM caption/tagging、API 模型 mapper、Ray+vLLM pipeline 等，用模型本身参与数据打分、改写、标注和筛选。

Agent 数据清洗

源码里有 agent_bad_case_signal_mapper、agent_trace_coherence_mapper、agent_tool_relevance_mapper、agent_tool_type_mapper 等，说明它也在覆盖 Agent 轨迹质量分析和工具调用数据清洗。

RAG / 数据分析

支持文本分块、实体/关系/事件/关键词抽取、数据画像、数据可视化、数据质量洞察。它可以作为 RAG 入库前的数据标准化和质量控制层。

执行层：为什么它能跑大规模数据

源码入口 tools/process_data.py 显示它有三类 executor：

  • default：本地执行，适合小中规模数据和开发调试。
  • ray：Ray 分布式执行，适合大规模数据并行处理。
  • ray_partitioned：分区 Ray 执行器，面向更大规模、更强容错和 OP 级隔离环境。

DefaultExecutor.run() 的流程很清楚：加载 dataset → load_ops() 准备算子 → 可选 OP fusion / adaptive batch size → dataset.process() 执行 → exporter 导出。这个结构让同一套清洗 recipe 可以从笔记本扩展到 Ray 集群。

一个最小使用例子

README 里给的最小 Python 用法如下：先构造数据集，再串两个算子：一个长度过滤，一个空白符归一化。

from data_juicer.core.data import NestedDataset
from data_juicer.ops.filter import TextLengthFilter
from data_juicer.ops.mapper import WhitespaceNormalizationMapper

ds = NestedDataset.from_dict({
    "text": ["Short", "This passes the filter.", "Text   with   spaces"]
})
res_ds = ds.process([
    TextLengthFilter(min_len=10),
    WhitespaceNormalizationMapper()
])

对应到工程上，就是“先过滤掉太短文本，再把保留下来的文本空格归一化”。复杂任务只是把这个算子链扩展成几十个 OP，并换成 Ray 执行。

和手写清洗脚本的区别

手写脚本

通常是一次性逻辑：读取文件、写几条规则、输出结果。问题是难复现、难复用、难追踪、难扩展到多模态和分布式。

Data-Juicer

把清洗流程变成 recipe 和 operator。每一步可配置、可版本管理、可测试、可追踪、可并行、可插拔模型，也能沉淀成团队共享的数据处理资产。

最短总结：Data-Juicer 是一个面向大模型数据生产的“算子化数据清洗平台”。它把传统数据清洗、去重、质量过滤、多模态处理、LLM/VLM 标注、Agent/RAG 数据整理和 Ray 分布式执行统一到一套 pipeline 里。
