Claude Code 上下文压缩策略详解：不是简单 75% 滑动窗口

你的原认知里有一半是对的：Claude Code 确实有一层LLM 摘要压缩，也确实会在上下文接近预算时自动触发压缩。但把它理解成“到 75% 后用滑动窗口保留最近 token”会误导。源码里更准确的模型是：多层上下文治理 pipeline + 动态阈值 + 摘要边界 + 工具结果瘦身 + post-compact 状态重建。

一句话：Claude Code 不是简单 FIFO 丢旧消息，也不是固定 75% 触发；它先尽量清理高成本工具结果，再按模型上下文窗口计算阈值，必要时调用一个 forked compact agent 生成详细工程摘要，然后用 compact boundary、summary、附件、文件状态、plan mode、hooks 和工具/MCP 状态重新拼出下一轮上下文。

1. 为什么不是“滑动窗口算法”

滑动窗口的直觉是：只保留最后 N 个 token，前面的都丢掉。Claude Code 不是这样。query.ts 每轮会先调用 getMessagesAfterCompactBoundary()，也就是说上次 compact 前的原始历史不再原样发送；它被一个 compact summary 代表。

这是一种语义压缩边界：旧历史被“摘要消息 + 边界元数据”替换，近期消息和运行时附件继续保留。它有点像保留 recent tail，但不是机械 token 滑窗。

2. 为什么不是固定 75%

autoCompact.ts 里阈值不是写死 75%。它先算 getEffectiveContextWindowSize(model)：模型上下文窗口减去摘要输出预留，摘要最多预留 20,000 tokens。然后自动压缩阈值是 effectiveContextWindow - 13,000。

所以真实触发点随模型窗口、最大输出、环境变量覆盖和 feature flag 变化。75% 更像某些 UI 警告或经验数字，不能当成 Claude Code auto compact 的核心规则。

3. 压缩前先做 tool result 瘦身

在真的总结整段对话之前，Claude Code 会先处理最容易爆上下文的部分：工具输出。microCompact.ts 只针对 Read、Bash、Grep、Glob、WebFetch、WebSearch、Edit、Write 等 compactable tools，把旧 tool_result 内容清掉或通过 cache editing 删除。

这一步不是 LLM 摘要，而是结构化删减工具输出。很多 coding agent 的上下文爆炸不是来自用户文字，而是来自文件读取、grep、大段 shell 输出。Claude Code 先处理这里，避免过早把整段会话压成摘要。

4. compact summary 的提示词很工程化

prompt.ts 的 compact prompt 不是简单说“总结一下”。它要求摘要保留用户意图、技术概念、读过/改过的文件、关键代码片段、错误和修复、问题解决过程、所有非工具用户消息、待办、当前工作和下一步。

这说明 Claude Code 的摘要目标不是聊天摘要，而是让下一个模型回合能继续工程任务。它会刻意保留文件路径、函数签名、具体代码、用户反馈和未完成动作。

从源码看，一轮模型调用前的上下文治理顺序大致是：

原始 messages
  → getMessagesAfterCompactBoundary()
     只取上次 compact 边界之后的消息
  → applyToolResultBudget()
     对过大的工具结果做预算控制
  → snipCompactIfNeeded()
     可选历史 snip，释放估算 tokens
  → microcompactMessages()
     清理或 cache-edit 旧工具结果
  → applyCollapsesIfNeeded()
     可选 context collapse，保留更细粒度上下文
  → autoCompactIfNeeded()
     超过动态阈值才做 LLM compact
  → buildPostCompactMessages()
     boundary + summary + kept messages + attachments + hooks
  → 下一次 Anthropic API 请求

5. compact 后会重建状态，不只是塞摘要

compact.ts 里的 compactConversation() 成功后会创建 boundaryMarker 和 summaryMessages，然后重新注入一批附件：最近读过的文件内容、异步 agent 状态、plan 文件、plan mode 指令、已调用 skill、deferred tools、agent listing、MCP instructions、session start hooks。

buildPostCompactMessages() 的顺序是 boundaryMarker → summaryMessages → messagesToKeep → attachments → hookResults。这就是为什么它不是“一层摘要完事”：压缩后还要恢复能继续工作的运行时上下文。

6. prompt too long 还有兜底恢复

如果 compact 请求本身都因为 prompt too long 失败，truncateHeadForPTLRetry() 会按 API round 分组，从最旧的组开始丢，最多重试几次，并插入 [earlier conversation truncated for compaction retry] 这样的元消息。

这才比较像“丢旧上下文”，但它是异常兜底，不是日常主策略。正常路径优先是 microcompact、context collapse、LLM summary 和状态重建。

7. context collapse 会和 autocompact 分工

源码注释里提到 context collapse 有自己的 90% commit-start 和 95% blocking-spawn 逻辑。开启 context collapse 时，shouldAutoCompact() 会避免 proactive autocompact 抢先触发，因为它会“nuke”掉 collapse 正准备保留的细粒度上下文。

所以 Claude Code 不是只有一个 compact 机制，而是多套上下文治理策略互相避让：collapse 负责更细粒度保留，autocompact 负责传统大摘要，reactive compact 负责 API 报错后的恢复。

8. 失败会熔断，避免无限压缩

autoCompact.ts 里有连续失败计数，默认连续失败 3 次后就不再反复尝试自动 compact。原因也写在注释里：有些 session 已经不可恢复地超过限制，继续每轮 compact 只会浪费 API 调用。

这说明上下文压缩在 Claude Code 里是运行时系统的一部分，要考虑失败恢复、成本、缓存命中和用户体验，而不是一个单纯算法函数。

所以可以把你的旧模型升级成下面这个版本：

旧理解：
到 75% 上下文
  → 启动 LLM 摘要
  → 滑动窗口保留最近内容

更接近 Claude Code 源码：
每一轮 query 前
  → 先尊重 compact boundary，不重复发送已摘要旧历史
  → 工具结果按预算瘦身，旧 Read/Bash/Grep 输出优先被清理
  → 可选 snip / microcompact / context collapse
  → token 超过模型相关动态阈值 effectiveWindow - 13000 才 autocompact
  → forked compact agent 生成面向工程续作的详细摘要
  → compact 后重建 boundary、summary、文件附件、plan 状态、skill、MCP、agent/tool 状态
  → 如果 API 仍报 prompt-too-long，再走 reactive/truncate 兜底
最终心智模型：Claude Code 的上下文压缩不是“摘要层 + 滑动窗口层”，而是缓存友好的上下文操作系统。它把对话历史、工具输出、文件状态、计划状态、子 agent 状态、hook 结果和模型窗口预算分开管理；该清工具输出就清工具输出，该生成语义摘要才生成摘要，该保留运行时状态就重新注入附件。
