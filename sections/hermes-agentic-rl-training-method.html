Hermes agentic RL 的训练方法是什么：是不是 GRPO，reward 谁定义

源码里最准确的说法是：它是 GRPO 风格的 group-relative policy optimization，但实现上是 Tinker 的 importance_sampling loss + 组内 baseline 的 advantage 训练，而不是 repo 里直接写死一个“GRPO 算法类”。也就是说，方法论上接近 GRPO，工程落地上是“分组采样 + 相对优势 + 策略梯度式更新 + LoRA 微调”。

短结论：不是纯 SFT，也不是只做 reward model；核心是每个 prompt 采一组 rollout，先在组内算相对好坏，再只把更好的行动轨迹往上推。
先采样一组轨迹。同一个 item 会用 group_size 采多条 rollout。Hermes 这套代码里，环境层通过 collect_trajectories() 收集每条 trajectory 的 tokens、logprobs、messages 和 score。
每条轨迹先拿到标量 reward。reward 不是模型自己凭空“定义”的，而是环境里的 compute_reward() 给出来的。比如 GSM8K 是对答案；SWE 环境是跑测试；更复杂的 agentic 环境会把多信号合成一个分数。
组内做 baseline。TinkerAtroposTrainer.pad_data_to_good_offset() 里直接算 advantages = scores - mean(scores)。这就是典型的 group-relative 训练逻辑。
生成 token 才有梯度。prompt token 的 advantage 被置 0，只有模型自己输出的 token 参与更新。训练目标不是“把题目背下来”，而是“把行动策略调好”。
用 importance sampling 更新 LoRA。forward_backward_async(data, loss_fn="importance_sampling") 配合 optim_step_async() 做参数更新。更新对象是 LoRA client，不是每次全量改 base model。

为什么说它像 GRPO

因为它和 GRPO 的核心直觉一致：同一 prompt 采多个答案，在组内比较，不依赖单独训练一个 value model 也能形成相对优势信号。源码里最明显的证据就是 score - group_mean 这一步。

为什么又不该说成“标准 GRPO”

因为仓库里的实际训练入口没有暴露一个独立的 GRPO optimizer API，而是走 Tinker 的 importance_sampling loss。对读代码来说，更稳妥的描述是“GRPO-like group-relative RL”。

不同 pipeline 怎么训练

训练方法骨架不变，变的是环境和 reward。数学题 pipeline 主要是正确性 reward；SWE pipeline 是测试通过率；更 agentic 的环境会把过程信号、部分成功、工具轨迹质量一起纳入 reward。

reward 是 AI 自己定义的吗

不是。reward 由环境作者或 verifier 定义，Hermes agent 只是在这个定义下试行动、拿反馈、更新策略。AI 可以参与评分器的一部分实现，比如 LLM judge 或抽取器，但那是 reward 设计的一部分，不是训练中的 agent 自己给自己打分。

不同 pipeline 的 reward 形状，决定了训练重点会偏向哪里：

1. GSM8K / math pipeline
   reward = 1 if boxed answer correct else 0
   目标：推高正确推理和答案格式

2. SWE / coding pipeline
   reward = tests pass ? 1.0 : partial credit / 0.0
   目标：推高读文件、改代码、跑测试、最小修复这类行动序列

3. 更复杂的 agentic pipeline
   reward = correctness + process + safety + tool success
   目标：推高完整任务完成率，而不是只学最终输出文本
最重要的边界：Hermes agent 不会“自己发明 reward 规则再训练自己”。它会自己生成轨迹，但 reward 的定义来自外部环境/验证器；真正的自我改进来自“自己行动产生数据，再按外部 reward 更新自己”。
