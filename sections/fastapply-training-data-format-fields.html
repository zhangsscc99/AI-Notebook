MinT / FastApply 训练数据格式：几个字段分别是什么意思

这个项目里“训练数据格式”有三层，不要混在一起：原始代码变更样本、转换后的 prompt 训练样本、真正送进 MinT API 的 token-level Datum。训练最终用的是第三层；第二层是人类可读、可保存、可复查的数据集格式。

一句话：原始样本描述“旧代码 + patch → 新代码”；prompt 样本描述“给模型看的 prompt + 标准答案/奖励答案”；MinT Datum 描述“token 序列 + target_tokens + weights + logprobs/advantages”。

第一层：原始 / 清洗后的 FastApply 样本

来源是 Git diff 或 tiny fixture，目标是保留一条可验证的代码修改任务。典型 JSONL 长这样：

{
  "id": "py-search-replace-cache",
  "language": "python",
  "old_source": "def fetch_user(...): ...",
  "patch": "<<<<<<< SEARCH ... ======= ... >>>>>>> REPLACE",
  "new_source": "def fetch_user(..., cache=None): ...",
  "change_kind": "search_replace",
  "origin": "tiny_test_fixture"
}

id

样本唯一标识。训练报告、rollout、debug 时用它把 prompt、response、reward 对回同一个任务。

language

代码语言，比如 python / javascript。用于渲染 prompt，也会传给 reward / syntax checker 做语言相关判断。

old_source / source

修改前的完整或片段代码。模型看到的是这份旧代码。

patch / diff / update

要应用到旧代码上的变化说明。可能是 SEARCH/REPLACE patch，也可能是 unified diff 或 structured JSON changes。

new_source / reference

标准答案：应用 patch 后应该得到的新代码。reward 会拿模型输出和它比。

metadata / repo / file

追踪字段。真实 Git 数据会记录来自哪个仓库、哪个文件、哪个 commit；训练本身不一定直接用，但排查数据质量很重要。

第二层：转换后的 prompt 训练样本

rl_master/applications/fastapply/build/convert.py 会把清洗样本转成 RL / SFT 都能读的 prompt row。核心字段是 6 个：

{
  "data_source": "apply",
  "prompt": "You are a coding assistant... <source>...</source> <patch>...</patch>",
  "ability": "fast_apply",
  "reward_model": {
    "style": "rule",
    "ground_truth": "应用 patch 后的新代码"
  },
  "extra_info": {
    "id": "样本 id",
    "repo": "来源仓库，可为空",
    "file": "来源文件，可为空",
    "language": "python"
  },
  "response": "<updated>
标准新代码
</updated>"
}

data_source

任务来源/任务类型。这里固定是 apply，reward 函数用它知道这是 FastApply 应用补丁任务。

prompt

真正喂给模型的输入文本。由 system prompt + instruction + <language> + <source> + <patch> 组成。

ability

能力标签。这里是 fast_apply，用于统计、路由、混合多任务训练时区分能力。

reward_model

奖励配置。style="rule" 表示先走规则比较；ground_truth 是标准新代码。

extra_info

额外元信息。reward 里会读 language，debug 时用 id/repo/file 追踪数据来源。

response

SFT 的标准输出格式，必须包在 <updated> 标签里。GRPO 时它可作为 oracle rollout 或验证参考。

第三层：真正送进 MinT 的 types.Datum

MinT 训练 API 不直接吃上面的 JSON 字符串字段，而是吃 token 化后的 types.Datum。SFT smoke 里每条 Datum 主要有 2 个顶层字段：

types.Datum(
  model_input=types.ModelInput.from_ints(tokens=all_tokens[:-1]),
  loss_fn_inputs={
    "target_tokens": all_tokens[1:],
    "weights": [0.0] * prompt_len + [1.0] * response_len
  }
)

model_input.tokens

模型实际输入 token。训练 next-token prediction，所以输入是完整 token 序列去掉最后一个 token：all_tokens[:-1]。

target_tokens

监督目标 token。它是完整 token 序列右移一位：all_tokens[1:]，让模型预测下一个 token。

weights

loss mask。prompt 部分权重是 0，不训练模型复述 prompt；response 部分权重是 1，只训练模型生成答案。

loss_fn

SFT 用 cross_entropy；GRPO/importance sampling 用 importance_sampling，字段会更多。

GRPO / importance_sampling 时多出来的字段

GRPO 不是只有标准答案，而是同一个 prompt 采样多条 response，给每条 response 打 reward，再算组内 advantage。因此 loss_fn_inputs 会多两个关键字段：

loss_fn_inputs={
  "target_tokens": full[1:],
  "weights": [0.0] * prompt_prefix + [1.0] * len(response_tokens),
  "logprobs": [0.0] * prompt_prefix + response_logprobs,
  "advantages": [0.0] * prompt_prefix + [advantage] * len(response_tokens)
}

logprobs

采样时旧策略对每个生成 token 的 log probability。importance sampling 要用它和当前策略概率做 ratio。

advantages

这条 response 相对同组其他 response 的好坏。reward 高于组平均，advantage 为正；低于组平均，为负。它会复制到该 response 的每个 token。

prompt_id / traj_group_id

在 RL-master smoke 的 RolloutSample 里用于分组。GRPO 必须知道哪些 rollout 属于同一个 prompt，才能算组内 advantage。

reward / metadata

reward 是规则/裁判给分；metadata 记录 index、validity、rule_correctness 等分析字段，帮助排查为什么某条 rollout 好或坏。

最短记忆法：保存到磁盘的人类可读数据是 prompt + reward_model.ground_truth + response + extra_info；真正训练时会变成 model_input.tokens + target_tokens + weights，GRPO 再加 logprobs + advantages。
