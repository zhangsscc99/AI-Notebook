Docker 沙箱到底防住了哪些危险，哪些防不住

可以把 Docker 沙箱理解成：给 agent 一个“临时小房间”。agent 可以在房间里跑命令、装依赖、删文件、启动服务；但默认情况下，它不应该直接碰到你整台宿主机。它防的不是“模型说错话”，而是模型执行错命令、跑了脏代码、污染环境、耗尽资源、误删文件这些真实工程危险。

最短答案：Docker 沙箱能显著降低“误操作伤到宿主机”的概率，但它不是绝对保险箱。没挂载宿主目录时，很多破坏只发生在容器里；一旦你 bind mount 了项目目录，agent 就可以真实修改这个项目目录；如果你再把 token、SSH key、Docker socket 暴露进去，风险会继续变大。

危险 1：误删文件

没有沙箱时，agent 如果执行：

rm -rf node_modules dist
rm -rf /tmp/some-path
rm -rf ~/.cache

这些命令直接作用在宿主机。更糟糕的是路径变量写错，可能删到你不想删的目录。

Docker 能防什么：如果没有 bind mount 宿主目录，删除主要发生在容器文件系统里。容器删坏了，可以直接销毁重建。

防不住什么：如果你把 /root/myapp bind mount 到 /workspace，agent 在容器里删 /workspace/src，宿主项目的 src 也会被删。

危险 2：依赖污染

真实 coding agent 经常会跑：

pip install -U package
npm install
apt-get install ...
python setup.py develop

没有沙箱时，这些可能改掉宿主机 Python、Node、系统依赖或全局缓存，让你原来的项目环境坏掉。

Docker 能防什么：依赖装在容器里，污染的是容器环境，不是宿主机。失败了直接换镜像或重建容器。

意义：agent 可以大胆试错，比如升级依赖、装编译工具、跑临时服务，而不用把你的主机环境搞脏。

危险 3：执行不可信代码

比如 agent 从 GitHub clone 一个 repo，然后跑：

npm test
pip install -e .
python scripts/setup.py
bash install.sh

这些脚本可能有副作用：写文件、读环境变量、开网络连接、启动后台进程。

Docker 能防什么：脚本在容器里跑，默认看不到宿主机大部分文件；即使脚本乱写，也主要写容器内部。

防不住什么：如果你把敏感 token forward 进容器，脚本仍然可能读到它；如果网络没关，它仍然可能访问外网。

危险 4：后台进程乱跑

agent 可能启动：

npm run dev
python server.py
pytest -n auto
celery worker

没有沙箱时，这些进程直接留在宿主机，端口、CPU、内存都可能被占用。

Docker 能防什么：进程在容器 namespace 里，Hermes 可以按 container / sandbox 追踪和清理。容器销毁时，里面的进程一起消失。

意义：长任务、测试服务、临时 server 不容易把宿主机搞成一堆残留进程。

危险 5：资源打爆机器

agent 可能误跑超重任务：

pytest -n 64
npm run build in a huge monorepo
python train.py
yes > bigfile

Docker 能防什么：Hermes Docker backend 支持 CPU、memory、disk 配置；代码里会把这些变成 Docker 的 --cpus、--memory、storage limit 等参数。还有限制 PID 数量和 tmpfs 大小的安全参数。

防不住什么：磁盘限额依赖 Docker storage driver 支持；网络流量、外部 API 花费也不是 Docker 自动解决的，需要额外策略。

危险 6：权限提升和容器逃逸

Hermes Docker backend 做了一些基础加固：--cap-drop ALL、no-new-privileges、PID limit、临时目录 tmpfs 限制等。意思是尽量不给容器多余 Linux capabilities，降低容器内进程升级权限的机会。

Docker 能防什么：普通脚本更难直接获得宿主机 root 权限，也更难随便操作宿主系统资源。

防不住什么：如果你用 privileged container、挂 Docker socket、挂宿主根目录，或者遇到内核 / Docker 漏洞，隔离边界就会弱很多。

不挂载项目。最安全，agent 基本只破坏容器内部；缺点是改动不会自动回到宿主项目。
挂载项目目录。适合真实 coding：依赖和进程在容器里，项目文件真实改动；风险是 agent 可以删/改这个项目目录。
只挂必要目录。不要把 /、~、Docker socket、SSH 私钥目录随便挂进去。
只转发必要环境变量。docker_forward_env 是显式 opt-in；token 进容器后，容器内命令就可能读到。
给资源上限。设置 CPU、memory、disk，避免 agent 错误命令拖垮宿主机。
用 git 做最后防线。即使用沙箱，真实项目改动也要靠 git diff、测试、commit review 来确认。
Docker sandbox protects well against:
  - dependency pollution
  - accidental writes outside mounted dirs
  - leftover processes after container cleanup
  - many resource abuse cases when limits are set
  - unsafe test/build scripts damaging the whole host

Docker sandbox does NOT automatically protect against:
  - deleting files inside bind-mounted project dirs
  - leaked tokens explicitly forwarded into the container
  - network/API abuse if network and credentials are available
  - host compromise if Docker socket / root filesystem is mounted
  - all possible container/kernel escape vulnerabilities

Practical rule:
  unmounted container = disposable experiment room
  bind-mounted project = safer build room, but the project itself is real
真正要记住：Docker 沙箱不是让 agent “绝对安全”，而是把风险从“整台机器和所有私人文件”缩小到“容器 + 你主动挂进去的目录 + 你主动给进去的凭据”。这个风险缩小，就是它最大的意义。
