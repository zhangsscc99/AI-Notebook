OpenClaw 整个 memory 的检索和存放 pipeline 是怎么样的，什么时候会存东西

先把结论说清楚：OpenClaw durable memory 不是每次对话结束后都自动写一条长期记忆。每轮对话通常会进入 session transcript；但真正可长期维护的 memory，是 MEMORY.md、memory/YYYY-MM-DD.md、extraPaths 或可选 session index 这些源数据经过 sync 后形成的检索体系。

一句话：OpenClaw memory 有两条链路：检索链路是 startup context / memory_search → sync/index → FTS/vector/QMD → memory_get；存放链路是 人工/模型/flush/hook 写 Markdown 或 transcript → sync → chunks/embedding/FTS/QMD。写入长期记忆是选择性的，不是“每句话自动记住”。

1. 先区分三种“存”

长期记忆存储：写到 MEMORY.md 或 memory/*.md，这是 source of truth。

检索索引存储：sync 把文件切块后写进 SQLite files/chunks/chunks_fts/chunks_vec，或 QMD collection。这是派生缓存，可重建。

会话 transcript 存储：对话写进 session JSONL；如果启用 sessions source，才会进入 memory_search 的检索语料。

2. 检索入口在哪里

memory-core/index.ts 注册 memory_search 和 memory_get。工具说明要求模型在回答历史工作、决策、偏好、todo 等问题前先搜索记忆，再按需读取原文。

所以用户问“以前我说过什么”时，模型不是靠脑补，而是应该走 tool：先 search 找候选，再 get 读原文行。

3. 启动时也会加载一小段记忆

startup-context.ts 会在新 session / reset 时读取最近几天 memory/YYYY-MM-DD*.md 的有限内容，作为启动背景注入。注意这是“读”，不是“写”。

4. 第一次 search 会兜底建索引

MemoryIndexManager.search() 里如果发现没有 indexed content，会同步触发 sync({ reason: "search", force: true })。这一步会“存索引”，但不会创造新的长期 Markdown 记忆。

完整检索 pipeline 可以按这个顺序记：

用户问题命中历史信息场景，例如“之前那个部署 repo 是什么”。系统提示要求模型先调用 memory_search(query)。
memory_search 解析 query/maxResults/minScore/corpus，通过 getMemorySearchManager() 选择 QMD 后端或 builtin SQLite 后端。
builtin 后端会检查索引是否存在；没有索引就强制 sync；有 dirty 文件时可在 search 时异步 sync，避免长期用旧索引。
sync 扫描 MEMORY.md、memory/、extraPaths，以及可选 session transcript，算 hash，只重建新增或变化文件。
每个文件被切成 chunks；写 files、chunks、FTS 表；如果 embedding provider 可用，再写向量表或 QMD 索引。
搜索时走 FTS-only、vector-only 或 hybrid：关键词 BM25 + 向量召回 + MMR / temporal decay 等排序，返回 path、行号、snippet、score、source。
模型看到命中坐标后，继续用 memory_get(path, from, lines) 回读 Markdown 原文 excerpt，再基于原文回答。

完整存放 pipeline 则是另一条链：

某条信息被判断为值得保存：用户明确要求记住、模型在维护任务中写入、compaction 前 flush 捕获长期事实，或 session-memory hook 在 /new、/reset 时保存最近会话。
长期事实写到 Markdown：通常是 memory/YYYY-MM-DD.md 追加；更稳定的偏好/身份/长期规则可以人工整理进 MEMORY.md。
flush-plan.ts 对 memory flush 有硬提示：只写 memory/YYYY-MM-DD.md，已有文件只能 append，不要覆盖 MEMORY.md、SOUL.md、AGENTS.md 等 bootstrap 文件。
watcher 监听 MEMORY.md、memory/ 和 extraPaths；文件 add/change/unlink 后标 dirty，延迟触发 sync。
syncMemoryFiles() 重新列文件、算 hash、跳过未变化文件；变化文件重新 indexFile()，删除已经不存在的 stale rows。
之后这条记忆才能稳定被 memory_search 找到，并可被 memory_get 回读验证。

什么时候会写长期 memory？

主要有四类时机：人工或模型显式编辑 memory 文件；用户明确要求“记住”；上下文接近 compaction 阈值时触发 memory flush；session-memory hook 在 /new 或 /reset 命令时把最近会话写成 dated memory 文件。

是不是每次对话后都写？

不是。普通每轮对话会进入 session transcript，但不等于进入 durable Markdown memory。OpenClaw 还会用阈值、hook、flush、人工整理来决定哪些内容值得长期保存。

索引更新是不是每次写文件后立即完成？

不一定。watcher 会 debounce；session transcript 也有 deltaBytes / deltaMessages 阈值，避免每写一行都重建索引。search 时如果索引空，会同步 bootstrap；dirty 时可异步 sync。

为什么不每句话都长期保存？

因为长期记忆需要可审计、低噪音、可维护。每轮都写会导致垃圾记忆、检索污染、embedding 成本上升、隐私风险变大。OpenClaw 的设计更接近“选择性落盘 + 可重建索引”。

拿一个具体例子讲：

用户说：以后这个网页项目的 GitHub repo 用 zhangsscc00/knowledge_management。

如果当前任务很重要，模型/用户可以把它追加到：
  memory/2026-05-21.md

之后：
  watcher 标 dirty
  -> syncMemoryFiles() 看到文件 hash 变化
  -> chunk + embedding + FTS/QMD 更新
  -> 下次问“网页 repo 是哪个”
  -> memory_search 命中 memory/2026-05-21.md
  -> memory_get 读原文
  -> 模型回答 zhangsscc00/knowledge_management

如果当时没人写 memory，也没有 flush/hook 把它保存，
它可能只在当前 session transcript 里；是否能跨会话检索，取决于 session indexing 是否启用。
最终答案：OpenClaw memory 的核心不是“每次聊天自动记忆”，而是把值得保留的信息写进可审计 Markdown / transcript，再通过 sync 建成可检索索引。检索时先 search 定位，再 get 回读原文；存放时先落盘，再索引。长期记忆是选择性写入，索引是派生缓存。
