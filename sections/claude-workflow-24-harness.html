Claude Code 的 harness 是什么

这里的 harness 不应该理解成“模型思考模块”。在 Claude Code 源码语境里，它更接近外部自动化执行外壳：通过 settings、hooks、权限和运行时事件，把“当某件事发生时自动做什么”变成确定性的工程配置。

一句话：模型负责推理；harness 负责在固定事件点执行确定性动作，例如工具前检查、工具后记录、权限请求、停止前校验、压缩前处理。

1. 配置入口是 settings.json

src/skills/bundled/updateConfig.ts 里明确把“配置 Claude Code harness”指向 settings.json。自动行为需要写成 hooks；执行这些 hook 的是 harness，不是 Claude 模型自己。

常见配置层包括 ~/.claude/settings.json、项目内 .claude/settings.json 和本地 .claude/settings.local.json。

2. Hook event 是 harness 的插槽

src/schemas/hooks.ts 定义了可挂载事件：PreToolUse、PostToolUse、PostToolUseFailure、PermissionRequest、Stop、SessionStart、PreCompact、PostCompact、Notification、UserPromptSubmit。

这相当于 agent 主循环暴露出的固定生命周期点。

3. matcher 用权限规则语法

Hook matcher 可以写类似 Bash(git *)、Read(*.ts) 的规则。也就是说，它可以只对某些工具、某些命令或某些文件类型生效。

这比在 prompt 里写“每次 git 前请检查”可靠，因为 hook 是运行时强制匹配和执行。

4. 输出可以反向影响主循环

src/utils/hooks.ts 会执行 command / prompt / agent / http / function hooks，并解析 JSON 输出。hook 可以增加 systemMessage、阻止动作、修改 updatedInput、给出 permission decision。

所以 harness 不是旁路日志系统，它可以真正改变工具执行和权限流。

典型例子：

模型想调用 Bash("git push")
  → PreToolUse hook matcher 命中 Bash(git push*)
  → harness 执行项目配置的检查脚本
  → hook 返回 block / ask / systemMessage
  → Claude Code 根据 hook 输出决定拒绝、请求权限或继续
  → 如果继续，才进入工具权限和真正 Bash 执行
核心区别：prompt 是“建议模型这么做”；harness 是“运行时在固定事件点强制执行”。因此真正需要稳定、可审计、可复用的自动化策略，应该放在 hooks / settings / permissions 里，而不是只写进对话提示。
参考文件：src/skills/bundled/updateConfig.ts、src/utils/hooks.ts、src/schemas/hooks.ts、src/commands/hooks/*、src/setup.ts。
