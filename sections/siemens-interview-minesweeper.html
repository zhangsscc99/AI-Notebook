SI16

设计题：扫雷引擎与规则系统（类图 + 状态图 + 流程图 + 设计模式）

这是扫雷模拟卷的第二题，也是整套卷子里 UML 分量最重的一题：在一个人人都懂的业务里，同时考类设计、状态建模、流程图和"规则可组合"的扩展性。按笔试顺序整理：先看题、问需求，再依次是类图 → 设计模式 → 流程图 → 状态图 → 撤销 → 规则组合，最后是追问预案。

一句话主线：把"会变的东西"拆成独立的插槽——邻居怎么算（拓扑）、雷怎么布（布雷策略）、踩雷怎么办（踩雷策略）、当前能做什么（状态）、做过什么（命令）、谁需要知道（观察者）。核心引擎只依赖这些接口，规则怎么组合都不用改它。

Q：设计一个单机扫雷引擎，实现基础规则，并支持可自由组合的规则变体

基础规则（R1–R8）：

编号规则
R1 棋盘W×H 方格、N 颗雷；初级 9×9/10、中级 16×16/40、高级 30×16/99；自定义 W∈[9,30]、H∈[9,24]、10 ≤ N ≤ (W−1)(H−1)
R2 首击安全第一次左键的格子及其 8 个邻居都没有雷（雷在首击之后才生成）
R3 左键翻开雷 → 失败；数字 → 显示周围雷数；0 → 自动展开相连区域，直到数字边界
R4 右键未翻开 → 旗 → 问号 → 未翻开，循环切换；旗格不能被左键翻开
R5 Chord在已翻开的数字格上，周围旗数等于该数字时，翻开其余邻居；旗插错会翻到雷而失败；旗数不等则无效果
R6 胜负所有非雷格翻开即胜（不必插完旗）；翻开任一雷即负；结束后棋盘锁定，失败时亮出所有雷并标出错旗
R7 计时与计数首击开始计时、结束停表；剩余雷数 = N − 旗数（可以为负）
R8 排行榜每个难度保留最快的 10 次胜利，自定义难度不入榜

规则变体（V1–V5，可任意组合）：

  • V1 问号开关：关闭后右键只在"旗"和"未翻开"之间切换。
  • V2 生命模式：k 条命，踩雷扣一条命，该雷标记为已爆并对所有人可见，游戏继续。
  • V3 无猜模式：生成的棋盘必须能纯靠逻辑解开。
  • V4 拓扑：方格（8 邻居）、六边形（6 邻居）、环面（上下、左右边界首尾相连）。
  • V5 练习模式：允许撤销，包括撤销一次踩雷、撤销一次展开了 300 格的 flood fill。

作答要求：2.1 类图（至少 6 个类，标关系类型和多重性，解释至少 2 条组合关系）；2.2 至少 3 种设计模式；2.3 左键点击流程图；2.4 Game 与 Cell 状态图；2.5 撤销设计；2.6 规则组合与冲突校验。

第零步：先问清需求（30 秒）

  • 单机还是联机？决定引擎要不要线程安全、操作要不要能序列化（联机见第三题）。
  • 自定义棋盘最大多大？决定 flood fill 能不能递归、撤销存快照还是存差量。
  • 要不要回放？要的话，布雷必须能由种子复现，操作必须是可记录的对象。
  • 规则组合是运行时选，还是发版时定？运行时选就只能靠组合 + 策略，不能靠继承。
  • 排行榜存哪里？本地文件还是云端，都必须抽象成接口（呼应第一题的依赖倒置）。

第一部分：类图（拆成四块，每块不超过 6 个类）

笔试时画在一张图上即可。这里按"模型 → 规则 → 状态 → 命令与通知"拆开，方便逐块讲符号和设计动机。

① 核心模型：Game / Board / Cell + 拓扑策略

符号笔记：

  • Game ◆— Board（实心菱形 = 组合，多重性 1）：Board 由 Game 开局时创建，一局结束就跟着销毁；"再来一局"是新建 Game 和 Board，不复用旧盘。两者同生共死，所以画组合。
  • Board ◆— Cell（组合，多重性 W×H）：Cell 离开这张棋盘就没有意义（它的 adjacent 只对这张盘成立），也不会被别的棋盘共享。
  • Board → BoardTopology（实线箭头 = 关联，指向接口）：拓扑对象无状态，可以做成单例被所有棋盘共享，所以不是组合。neighbors() 是全系统唯一定义"邻居"的地方：雷数计数、flood fill、chord、首击安全区都调用它，加六边形只需加一个实现类。
  • 没有 MineCell 子类：雷只是 Cell 的一个属性。第一题里 MineCell.adjacentMines() 抛异常是 LSP 违例，这里从结构上消除了。Cell 的显示状态用枚举 CellMark，原因见下文"为什么 Cell 不用状态模式"。

② 规则与布雷：RuleSet + 两个策略 + 一个装饰器

  • RuleSet 是不可变值对象，用建造者创建：参数多、组合多，直接写构造函数会有 10 个参数。Builder 的 build() 是统一校验点（见 2.6）。preset(Difficulty) 是静态工厂，返回三档标准配置。UML 里 static 成员用下划线表示。
  • MineLayoutStrategy（策略）：首击之后才调用 generate(rules, first, rng)，rng 由外部注入——测试时传固定种子或直接换成 FixedLayout；联机和回放时用同一个种子复现同一张图。
  • NoGuessLayout（装饰器）：它既实现 MineLayoutStrategy，又聚合一个 MineLayoutStrategy（inner）。先让 inner 生成，再用 Solver 验证能否纯逻辑解开，不行就重试，次数有上限。"无猜"可以叠加在任何布雷算法上，不需要 NoGuessSquareLayout、NoGuessHexLayout 这种组合子类。
  • inner 为什么画聚合（空心菱形）而不是组合：inner 是从构造函数传进来的，可能被别处共享，NoGuessLayout 不负责它的生命周期。
  • MineHitPolicy（策略）：V2 生命模式只影响"踩雷之后怎么办"这一个点，就只把这一个点抽成策略，其余流程完全不变。

③ 状态模式：Game 把操作委托给当前状态

  • Game → GameState 是关联，GameState ⇢ Game 是依赖：Game 把当前状态作为字段长期持有；状态对象只在方法参数里拿到 Game，用完就放，所以反方向画虚线。一张图里同时出现这两种线，最能体现你分得清关联和依赖。
  • ~ changeState(s) 用包可见：只允许同包的状态类切换状态，UI 不能直接改状态。
  • 为什么用状态模式而不是 switch：4 个状态 × 4 个操作是一张行为矩阵。用 switch 时，每个操作方法里都要 switch 一遍状态，加一个 Paused（或联机时的 Reconnecting）就要改所有方法；用状态模式只需加一个类。坦白说，只有 4 个状态时两种写法都能接受，状态模式的价值在于"状态还会增加"。

④ 命令 + 观察者：可撤销的操作、解耦的通知

  • Game ◆— CommandHistory（组合）：撤销历史只属于这一局，局结束就丢弃。
  • CommandHistory ◇— GameCommand（聚合，0..*）：命令由 Game 创建、执行后再交给 history 保管；回放模块或网络层也可能引用同一个命令对象，history 不独占它，所以画聚合。和前面几处组合放在一起讲，就是"组合 vs 聚合"的标准答案。
  • Game → GameListener（关联，0..*）：观察者由外部注册，Game 不创建也不销毁它们。Game 只 emit(event)，不知道听的是控制台、GUI、计时显示还是排行榜记录器——第一题里"Game 直接调 ui.draw、直接写文件"的坏味道就是在这里消掉的。
  • 只有一个 onEvent(e) 方法：新增事件类型不用改接口，已有监听者不受影响；代价是监听者内部要按事件类型分发。另一种做法是按事件拆成几个小接口（接口隔离），两种都能讲，关键是说出取舍。

笔试速写版（纸上 3 分钟画完）

Game ◆── 1 Board ◆── W×H Cell
Board ──> 1 BoardTopology        <|.. Square / Hex / Torus
Game ──> 1 RuleSet               (不可变，Builder 构建 + build() 校验)
RuleSet ──> 1 MineLayoutStrategy <|.. SafeFirstRandomLayout / NoGuessLayout
NoGuessLayout ◇── 1 MineLayoutStrategy   (inner，装饰器)
RuleSet ──> 1 MineHitPolicy      <|.. SuddenDeathPolicy / LivesPolicy(k)
Game ──> 1 GameState             <|.. Ready / Playing / Won / Lost
Game ◆── 1 CommandHistory ◇── 0..* GameCommand  <|.. Reveal / ToggleMark / Chord

第二部分：设计模式（2.2）

模式用在哪应对的变化不用会怎样

反过来也要说清楚：V1 问号开关没有建类。它只是 RuleSet 里的一个布尔参数，传给 Cell.cycleMark(qOn)。变化点只是一个分支时用参数，有独立行为时才用策略——面试官很在意你会不会过度设计。

第三部分：流程图 A · 玩家左键点击（2.3）

UML 活动图。主线在中间；右上是"忽略"和"首击布雷"，右下是踩雷分支，左侧是"只翻一格"和胜利。所有分支最后汇合到"记录命令 + 通知"。

这张图里必须讲出来的四点：

先查状态，再查格子：游戏已结束就直接忽略（R6 棋盘锁定）；旗格和已翻开的格子也忽略（R4）。问号格可以翻。
布雷发生在首击之后：Ready 状态下第一次 reveal 才调用布雷策略并排除首击安全区，然后计算邻居雷数、记开始时间、切到 Playing。首击安全靠"推迟布雷"实现，而不是"踩到了再把雷挪走"。
踩雷交给策略：图上只有一个 mineHit.onMineHit() 动作。还有命就扣命继续，命用完才转 Lost。新增踩雷规则不用改这张图。
胜利判定是 O(1)：Board 维护 revealedSafe 计数，等于 W×H − N 即胜，不用每次扫全盘。展开用 BFS + 队列，Cell 的 REVEALED 状态本身就是 visited 标记。

Chord 不用单独画流程图：它外面多一层"旗数 == 数字?"的判断，然后对每个未插旗的邻居复用"是雷?"之后的流程。插错旗时走的就是同一条踩雷路径，不需要第二套逻辑。

第四部分：状态图（2.4）

状态图记号：圆角矩形是状态，● 是初始状态，箭头上写 事件 [守卫条件] / 动作。

Game 状态图

  • Ready → Playing 只能由 reveal 触发。Ready 下允许插旗，但不触发布雷，也不开始计时。
  • Playing 的自环：普通操作和"踩雷但还有命"都留在 Playing。
  • Lost → Playing（undo） 只在练习模式下存在，这是"撤销踩雷"在状态图上的表达。Won 没有出边，胜利不可撤销。

Cell 状态图

  • Flagged 没有到 Revealed 的边：左键、flood fill、chord 都会跳过旗格。这条"不存在的边"就是 R4，面试时要主动指出来。
  • Questioned 可以直接翻开，所以 flood fill 可能翻开问号格——撤销时要还原成 Questioned 而不是 Hidden（见 2.5）。
  • 为什么 Cell 不用状态模式：Cell 的状态只影响"右键之后变成什么"和"能不能翻开"两件事，枚举加一个 cycleMark() 就够了。Game 的状态会改变所有操作的行为，才值得用状态模式。

第五部分：撤销设计（2.5）

存差量，不存快照：RevealCommand 记录本次翻开的格子列表（连同原来的标记，因为可能翻开了问号格）、旧命数和旧状态。undo 时把这些格子恢复成原标记，revealedSafe 减回去，命数和状态复原。
算一下内存：一次展开 300 格，每格存 4 字节下标 + 1 字节原标记，约 1.5 KB。整盘快照在 30×16 上只有 480 格、约 480 B，反而更小；但在 1000×1000 的自定义盘上，每步快照是 1 MB，而差量始终只和改动量成正比。
为什么还是选命令：差量大小跟着改动走，不跟着棋盘走；同一个命令对象还能用于回放和联机同步；opened 列表正好就是 UI 增量重绘需要的数据。标准盘上快照更省，这一点可以主动承认。
计时器不倒回：计时是真实流逝的时间，不是游戏状态。开启撤销的规则 isRanked() 返回 false，成绩不入榜，所以没必要倒回计时。
首击不可撤销：最多撤回到首击之后。否则要回到 Ready 并丢掉布局，玩家就能靠反复撤销首击来刷布局，计时也要跟着重置。
派生值不存：剩余雷数 = N − 旗数 − 已爆雷数，每次现算，撤销后自然正确。只有 revealedSafe 这种为性能而维护的计数需要在撤销时一并回滚。

Chord 怎么撤销：ChordCommand 是复合命令，内部持有若干 RevealCommand，undo 时倒序撤销子命令，一次撤销就能撤回整个 chord。

第六部分：规则组合与冲突校验（2.6）

避免类爆炸：每个变化维度一个插槽。五个维度如果靠继承组合，需要 2 × 2 × 2 × 3 × 2 = 48 个子类；改用组合方式，每个维度一个接口或参数，总共十来个类，任意组合都不用新增类。

维度承载方式可选值
V1 问号RuleSet 布尔参数开 / 关
V2 生命MineHitPolicy 策略SuddenDeathPolicy / LivesPolicy(k)
V3 无猜NoGuessLayout 装饰器包 / 不包
V4 拓扑BoardTopology 策略Square / Hex / Torus
V5 撤销CommandHistory 或 NoOpHistory开 / 关

冲突由谁裁定：

组合冲突点规则裁定谁来校验
无猜 + 首击安全如果首击只保证单格安全，首击翻出一个数字后，下一步就可能只能猜无猜模式强制 safeZone = NEIGHBORHOOD，保证首击翻出 0 并展开Builder.build() 直接拒绝不兼容的组合
无猜 + 高密度雷越密，随机布局越难通过求解器验证，生成时间不可控无猜模式设密度上限；重试有上限，超过就报错并提示降低雷数build() 预检 + NoGuessLayout 兜底
生命 + 撤销撤销踩雷要不要还命要还：RevealCommand 存了 prevLives命令自身
生命 + 胜负 / 计数已爆的雷算什么已爆雷不计入安全格；剩余雷数 = N − 旗 − 已爆Board 的派生计算
六边形 / 环面 + 雷数上限R1 的 (W−1)(H−1) 是方格专用的经验值，换拓扑就不成立硬上限 = 格子总数 − (1 + maxNeighbors)，保证安全区放得下；方格再与 R1 取较小值build() 调用 topology.maxNeighbors()
六边形 + chord / 安全区邻居数从 8 变成 6不需要特殊处理，都走 topology.neighbors()结构本身保证
任意非标准组合 + 排行榜成绩不可比只有标准难度 + 方格 + 一条命 + 关闭撤销才入榜RuleSet.isRanked()

校验怎么实现：Builder 内持有一组 RuleConstraint，每个约束只检查一条规则并返回违例原因。build() 把所有约束跑完，一次性返回全部违例，而不是遇到第一个错就停。新增约束只需加一个类。UI 用同一组约束把不兼容的选项置灰，保证规则只在一个地方定义。

追问预案

面试官追问答法要点
为什么 Game 和 RuleSet 不画组合？RuleSet 不可变，可以被"再来一局"和多个对局共享，Game 不负责它的生命周期，所以是关联。
flood fill 为什么不用递归？自定义大盘上一个 0 区可能有几十万格，递归深度等于区域大小，会栈溢出。BFS 用显式队列，空间 O(区域大小)；用 REVEALED 状态做 visited，不需要额外数组。
首击安全怎么测？注入固定种子的 rng，或直接注入一个 FixedLayout 实现；断言首击格及其邻居都不是雷、雷数等于 N。能这样测，就是依赖倒置的收益。
计时器会不会有线程问题？引擎是单线程的，不开计时线程，只记 startedAt / endedAt，时间来源是注入的 Clock。UI 每秒自己读 elapsed() 刷新；测试时用 FakeClock。
无猜模式生成太慢怎么办？重试有上限；后台预生成一个小的棋盘池；求解器先做单格约束和子集推理，搞不定再对前沿连通分量做回溯。
Chord 插错旗时流程怎么走？ChordCommand 对每个未插旗的邻居执行 reveal，碰到雷就走 MineHitPolicy，和直接左键踩雷是同一条路径。
要支持回放怎么做？存 seed + RuleSet + 带时间戳的命令序列；回放时用同一个种子生成同一张图，再按时间顺序重放命令。前提是布雷和命令都是确定性的。
改成联机对战（第三题），哪些能复用？Game 搬到服务端；命令对象序列化成网络消息；Listener 换成广播器；GameState 加一个 Reconnecting；opened 列表直接作为增量广播内容。引擎本身基本不用改。

现场答题顺序

澄清需求（30 秒）：单机还是联机、最大棋盘多大、要不要回放。
先画核心三件套：Game ◆ Board ◆ Cell，再挂上 BoardTopology 接口。
逐个挂插槽：每加一个接口，就说出它对应哪条变体规则。
