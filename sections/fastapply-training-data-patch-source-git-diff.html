训练数据的 patch 是怎么得到的，用 git diff 吗

结论要分清两层：真实数据挖掘阶段会用 git diff 拿原始 unified diff；但真正喂给 FastApply / MinT 的 patch 通常不是原样的 git diff，而是从 diff 或 old/new 代码里再转换出来的 SEARCH/REPLACE patch。

一句话：git diff 是“原料”，SEARCH/REPLACE 是“训练输入格式”。训练让模型学的是：看到旧代码 source 和可定位的 SEARCH/REPLACE 修改块，输出完整更新后的代码。

1. RL-master/FastApply 真实挖数据：先跑 git diff

/root/rlhf/rl_master/applications/fastapply/build/extract.py 是 Git 仓库抽取入口。它先用 git rev-list --first-parent 找 commit，只保留单父提交；再用 git diff-tree --name-only -r commit 找变更文件；最后对每个代码文件跑：

git diff commit^ commit -- path

这个命令得到的是标准 unified diff，里面有 @@ -old,+new @@ hunk、上下文行、- 删除行、+ 新增行。

2. 同时取 old_source / new_source

同一个 extract.py 还会用 git show commit^:path 取旧文件，用 git show commit:path 取新文件。也就是说，一条原始样本不是只有 diff，而是三件套：

{
  old_source: 修改前完整文件,
  new_source: 修改后完整文件,
  diff: git diff 结果
}

这很关键：后面可以验证 patch 是否真的能把 old_source 变成 new_source。

3. parse.py 把 git diff 转成 changes

build/parse.py 会按 @@ hunk 拆 diff。对每个 hunk，保留旧侧的上下文行和删除行，形成 old；保留新侧的上下文行和新增行，形成 new。

所以它不是让模型直接读复杂 unified diff，而是把每个 diff hunk 抽象成：

{"old": "SEARCH 片段", "new": "REPLACE 片段"}

4. make.py 再渲染成 SEARCH/REPLACE patch

build/make.py 的 build() / build_search_replace_patch() 会把 changes 变成训练 prompt 里的 patch：

<<<<<<< SEARCH
旧片段
=======
新片段
>>>>>>> REPLACE

这就是模型最终看到的 patch 形态。它比原始 git diff 更适合训练“应用补丁”：SEARCH 是要在 source 中定位的旧片段，REPLACE 是替换后的新片段。

完整链路可以这样记：

Git commit
  → git diff commit^ commit -- file
  → old_source = git show commit^:file
  → new_source = git show commit:file
  → parse.py 解析 unified diff hunks
  → changes = [{old: SEARCH片段, new: REPLACE片段}, ...]
  → make.py 渲染 SEARCH/REPLACE patch
  → generate/filter 校验可重放、语法、AST、长度、去重
  → convert.py 写成 prompt + ground_truth
  → MinT/GRPO 使用 source + patch 采样 updated

当前 tiny MinT smoke 不是从 git diff 来的

/root/rlhf/fastapply_pipeline/test_data.py 里的两个 tiny 样本是手写 fixture：Python 样本直接手写 SEARCH/REPLACE；JavaScript 样本用 structured JSON changes。build_dataset.py 只是读取这些 tiny examples，跑过滤和 prompt 转换。

所以当前 smoke test 的 patch 不是现场跑 git diff 得到的，它只用来验证训练链路跑通。

qwen_rlhf 半合成数据：主要从 old/new 用 difflib 造 patch

/root/OpenClaw/src/qwen_rlhf/src/qwen_edit/dataset_builder.py 读取 CommitPackFT 样本里的 old_contents / new_contents，然后调用 make_hunks()。

make_hunks() 在 patching.py 里用的是 Python difflib.SequenceMatcher，不是执行 git diff 命令。它从 old/new 行序列中找差异，加上下文行，再格式化成 FastApply 的 SEARCH/REPLACE patch。

为什么不直接把 git diff 原文喂给模型？主要有三个工程原因：

更容易定位。SEARCH/REPLACE 明确告诉模型“在 source 里找这段旧代码，替换成这段新代码”。unified diff 还要理解行号、加减号和上下文。
更容易校验。apply_search_replace() 可以要求 SEARCH 在 source 中唯一出现；应用后必须等于 new_source。不能唯一命中或不能重放的样本直接丢。
更贴近 FastApply 任务。模型目标不是生成 diff，而是把 patch 合并成完整 updated code；SEARCH/REPLACE 正好服务这个目标。

一个具体例子：

git diff 原始 hunk：
@@ -1,2 +1,4 @@
 def add(a, b):
-    return a + b
+    result = a + b
+    return result

parse.py 抽成：
old = "def add(a, b):\n    return a + b"
new = "def add(a, b):\n    result = a + b\n    return result"

make.py 渲染为训练 patch：
<<<<<<< SEARCH
def add(a, b):
    return a + b
=======
def add(a, b):
    result = a + b
    return result
>>>>>>> REPLACE
最终答案：用，也不完全用。真实 Git 仓库数据先用 git diff 拿 unified diff；但训练输入里的 patch 通常会被转换成 SEARCH/REPLACE。另一路 qwen_rlhf / CommitPackFT 数据则直接从 old/new contents 用 difflib.SequenceMatcher 生成 SEARCH/REPLACE，不一定执行 git diff 命令。
