为什么 Deep Research Agent 在 GAIA 上更容易打过 Hermes 这类通用 Agent

先把结论说准：从服务器源码看，Open Deep Research Agent 更适合 GAIA，不是因为它抽象上一定比 Hermes 更高级，而是因为它把整个应用链路都按 GAIA 的出题形态做了专门优化。Hermes 的源码重点是通用个人/云端 agent、skills、memory、gateway、terminal backend 和 Atropos RL 环境；它有 WebResearchEnv，但默认训练集是 google/frames-benchmark，目标是训练多步网页研究能力，不是直接做 GAIA 评测 harness。

一句话：GAIA 不是普通“会上网就行”的 benchmark。它经常要求网页查证、文件读取、图片理解、历史网页、精确短答案格式。Open Deep Research Agent 把这些点做成了专门的双层 agent + 文本浏览器 + 附件预处理 + 最终答案重写器；Hermes 更像一个通用 agent/RL 基座，默认 web research 环境没有这些 GAIA 专用补丁。

1. 目标不同：ODR 是 GAIA 应用，Hermes 是通用 Agent/RL 基座

Open Deep Research 的 README.md 明确说它是 Deep Research 的开源复刻，并直接报告 GAIA validation 表现。run_gaia.py 也直接加载 gaia-benchmark/GAIA 或 smolagents/GAIA-annotated，保存 prediction、true_answer、intermediate_steps。

Hermes 的 environments/web_research_env.py 则写的是“RL Environment for Multi-Step Web Research”，默认 dataset 是 google/frames-benchmark，reward 是 correctness、tool usage、efficiency、source diversity。它适合训练研究能力，但不是 GAIA 定制提交器。

2. 架构不同：ODR 双层分工，Hermes 默认单循环工具调用

ODR 在 run.py / run_gaia.py 里创建两层：上层 CodeAgent 是 manager，负责全局推理、调用视觉/文档工具、整合答案；下层 ToolCallingAgent 叫 search_agent，专门负责搜索和网页导航。

Hermes 的 HermesAgentLoop 是标准 OpenAI tool calling 循环：每轮把 tools= 传给模型，模型返回 tool_calls，框架校验工具名、解析 JSON 参数、执行工具、把 tool result 放回 messages。这个架构很通用，但默认没有“研究经理 + 搜索专家”的强分工。

真正拉开 GAIA 表现的关键点可以拆成下面几类：

GAIA 附件处理。ODR 的 scripts/run_agents.py 会按扩展名处理图片、pdf、xls/xlsx、doc/docx、xml、音频、zip。zip 会先解压，再逐个文件生成描述。很多 GAIA 题不是纯网页题，而是“问题 + 附件”。这一步直接提高命中率。
视觉 + 文档双工具。ODR 用 visualizer 做图片问答，用 TextInspectorTool 把文档转成 markdown/text 并让模型围绕问题摘要或回答。Hermes 有视觉、文件、浏览器工具，但 WebResearchEnv 默认只启用 web、file，并没有 GAIA 附件预处理链路。
文本浏览器更贴合长网页查证。ODR 的 SimpleTextBrowser 维护 address、history、title、viewport_pages、当前页，并提供 page_down、page_up、find_on_page_ctrl_f、find_next。它让 agent 像人查网页：搜索 → 打开 → 页内 Ctrl+F → 翻页定位。
历史网页能力。ODR 有 ArchiveSearchTool，输入 URL 和日期去 Wayback Machine 找接近日期的历史快照。GAIA 题经常问过去某个时间点的事实，普通 live search 容易查到现在状态而答错。
搜索任务被封装成 managed agent。ODR 明确告诉 search_agent：需要浏览网页的问题都交给你；调用时要给完整自然语言任务，不要只给关键词；如果需要时间范围要给上下文。这样 manager 不必每次自己决定底层搜索动作，降低全局推理被网页细节污染的概率。
最终答案格式重写。GAIA scoring 很看最终短答案。ODR 的 scripts/reformulator.py 会读取完整 agent 轨迹，然后强制输出 FINAL ANSWER: ...，并要求数字用数字、尽量少词、逗号列表按要求、不带多余标点。Hermes WebResearchEnv 的 prompt 要求“2-4 sentences”和 cite sources，这对训练研究能力合理，但直接拿去 GAIA exact answer 可能吃亏。

ODR 的强项：benchmark harness 做满

它的问题增强很硬：run_gaia.py 会把原题改成“必须找到正确答案、不要 None found、必要时验证”，然后把附件描述拼进去。跑完 agent 后再用 prepare_response() 从轨迹里抽取最终答案。这相当于前处理、执行、后处理都围绕 GAIA 优化。

Hermes 的强项：训练和系统能力更强

Hermes 更强的是长期系统工程：skills、自我改进、memory、gateway、多平台通信、terminal sandbox、tool result persistence、Atropos RL。比如 tool_result_storage.py 会把超大工具结果写进 sandbox，只给模型返回 preview + 文件路径，防止上下文爆掉。

Hermes 在 GAIA 上的默认短板

默认 WebResearchEnv 是通用 web research RL：要求查至少两个来源、引用来源、2-4 句回答，并用 LLM judge 打分。这和 GAIA 的“短答案/精确匹配/附件多模态/历史网页”不完全同构。不是 Hermes 不能做，而是源码里的默认路径还没把 GAIA 特化做到 ODR 这种程度。

ODR 的代价

ODR 更像一个比赛/评测定制系统：依赖 Serper/SerpAPI、OpenAI 或 LiteLLM 模型、HF token、GAIA 数据集权限、手工/半手工附件增强。它没有 Hermes 那种长期个人 agent、skills 生态、gateway、多 terminal backend 的完整平台能力。

如果用一个具体 GAIA 题来理解，差异很明显：

题目带一个 pdf 或 xlsx 附件。ODR 先在 get_single_file_description() 里判断文件类型：如果有同名 png 截图，优先走视觉描述；否则用 TextInspectorTool.forward_initial_exam_mode() 转文本并生成与问题相关的 5 句说明。
manager CodeAgent 拿到“原题 + 附件说明”，决定哪些信息来自附件，哪些需要网页核验。
需要网页时，manager 把任务交给 search_agent。search_agent 用搜索、visit_page、Ctrl+F、翻页、Wayback 归档等工具找证据，并返回 summary。
manager 汇总附件证据和网页证据，得到候选答案。然后 prepare_response() 根据完整轨迹二次抽取成 GAIA 想要的最短最终答案。
Hermes 默认 web research 路径更可能是：模型在单个 tool-calling loop 里调用 web_search / web_extract，输出带来源的几句研究答案。这个答案对人类可读，但未必符合 GAIA scorer 的短答案格式。
最终判断：ODR 在 GAIA 上更容易好，是任务适配胜利：专门数据集入口、附件预处理、多模态工具、文本浏览器、Wayback、搜索子 agent、答案 reformulator。Hermes 的优势是平台和训练基建：如果要让 Hermes 打 GAIA，应把 ODR 这套 GAIA harness 移植进去，再用 Hermes 的 RL 环境对 GAIA/GAIA-like 任务做 reward training，而不是直接拿通用 web research prompt 去比。
