H4

Hermes Agent 的 skills 是怎么做的：如何自发展新 skills、如何管理

Hermes 的 skills 不是“模型权重训练”，而是应用层的程序化经验系统：把一次任务里验证过的做法，沉淀成下次可加载的操作手册。它让 agent 形成一种外层学习闭环：做任务 → 发现套路 → 写成 skill → 下次先加载 skill → 如果 skill 过期就补丁更新。

一句话：Hermes 的 skills 是 procedural memory（程序化记忆）。memory 记“事实 / 偏好 / 背景”，skills 记“某类任务应该怎么做、按什么步骤做、用哪些工具、避开什么坑”。
agent 启动或构建 prompt 时，扫描 ~/.hermes/skills/ 和配置的 external skill dirs，只把 skill 名称、描述、分类放进上下文。
模型先根据任务判断哪些 skill 相关；如果相关，系统提示要求它必须调用 skill_view(name) 加载完整 skill。
执行任务时，skill 变成具体工作流、命令、工具顺序、约束和坑点清单，影响 agent 的下一步决策。
如果任务复杂、工具调用很多、修了一个难错、发现了可复用流程，agent 用 skill_manage(action="create") 新建 skill。
如果加载的 skill 错了、旧了、缺步骤，agent 直接用 skill_manage(action="patch") 修它，不等用户单独要求。
后台 curator 根据使用记录维护 agent-created skills：标记 stale、归档、合并、补丁，但只碰 agent 创建的 skill，不随便动 bundled / hub skills。

1. skill 的物理形态是什么

Hermes 的一个 skill 本质上是一个目录，主文件是 SKILL.md，旁边可以挂支持文件：

~/.hermes/skills/
  my-skill/
    SKILL.md
    references/
    templates/
    scripts/
    assets/

SKILL.md 必须以 YAML frontmatter 开头，至少要有 name 和 description。后面的正文才是真正给 agent 看的操作流程、注意事项、命令模板和决策规则。

2. 为什么说它是 procedural memory

skill_manager_tool.py 里直接把 skills 定义成 procedural memory：它保存的是怎么做某类任务，不是泛泛的知识。比如：

  • memory 适合记：用户喜欢中文解释、某项目用 pnpm、某 API key 在哪里配置。
  • skill 适合记：如何排查一个失败的部署、如何做代码审查、如何按项目规范新增一个功能。

这也是 Hermes 外层“拟 agentic RL”的核心：不改模型参数，但会改运行时可调用的经验库。

3. Hermes 怎么发现和加载 skills

Hermes 不是把所有 skill 全量塞进上下文，那样会爆 token。它用了渐进式披露：

  • skills_list 只返回 name / description / category 等轻量元数据。
  • prompt builder 会把可用 skill 索引插入 system prompt，并要求模型先扫描。
  • 如果某个 skill 相关，模型必须调用 skill_view(name) 读取完整内容。
  • 如果还需要支持文件，再调用 skill_view(name, file_path="references/xxx.md")。

所以它的上下文策略是：先给目录，不给全文；相关时再加载全文；需要时再加载附件。

4. 怎么自己发展新 skills

Hermes 在 system prompt 里明确给了触发规则：完成复杂任务、5 次以上工具调用、修复棘手错误、发现非平凡工作流后，要把方法保存成 skill。实际落盘动作由：

skill_manage(action="create", name="...", content="...")

完成。这个工具会创建目录、写入 SKILL.md，并校验名称、frontmatter、内容大小。也就是说，Hermes 的“自发展”不是神秘训练，而是模型在任务结束后把可复用经验写成结构化文件。

5. 怎么自我改进旧 skills

如果 agent 加载了一个 skill，但执行时发现命令过期、步骤不完整、坑点漏了，prompt 明确要求它立刻 patch：

skill_manage(
  action="patch",
  name="...",
  old_string="旧内容",
  new_string="新内容"
)

这就是 skill 层面的学习闭环：这次踩到的坑，不应该只在当前会话里解释一遍，而应该写回 skill，让下一次任务直接避开。

6. Hermes 怎么管理这些 skills

管理动作主要集中在 skill_manage：

  • create：创建新 skill。
  • edit：整篇重写 SKILL.md。
  • patch：对 SKILL.md 或支持文件做局部替换。
  • delete：删除 / 归档用户 skill。
  • write_file：写 references/、templates/、scripts/、assets/ 里的支持文件。
  • remove_file：删除支持文件。

另外 skill_commands.py 会扫描 skill，把部分 skill 暴露成 slash command；调用后还会 bump usage，给 curator 后续维护用。

7. curator 怎么维护 skill 库

agent/curator.py 是后台 skill 维护器。它不是每次都跑，而是按配置周期在 agent 空闲时做维护。它会读取 ~/.hermes/skills/.usage.json 里的使用记录，判断哪些 agent-created skills 应该保留、补丁、合并、标记 stale 或归档。

  • 默认只维护 agent 创建的 skills。
  • bundled / hub-installed skills 受保护，不被 curator 随便覆盖。
  • 不会自动不可恢复地删除；归档是 recoverable 的。
  • pinned skill 可以绕过自动归档 / 删除。

8. 安全和约束怎么做

Hermes 对 agent 写 skill 做了几层约束：

  • skill 名称必须 filesystem-safe，只允许小写字母、数字、点、下划线、短横线等。
  • SKILL.md 必须有 YAML frontmatter，且包含 name / description。
  • 内容有大小限制，避免 agent 写入过大的 prompt 包袱。
  • 支持文件只能写到 references、templates、scripts、assets。
  • 写文件用 atomic replace，避免半写入损坏。
  • 可选打开 skills.guard_agent_created，对 agent-created skill 做安全扫描。
一次任务中的 skills 自学习闭环：

user task
  -> prompt_builder 注入 available skills index
  -> model 判断相关 skill
  -> skill_view(name) 加载完整操作手册
  -> 执行任务 / 调工具 / 发现坑点
  -> 如果是新套路：skill_manage(create)
  -> 如果旧 skill 有问题：skill_manage(patch)
  -> skill_usage 记录 view/use/patch
  -> curator 周期性清理、合并、归档、修补 agent-created skills

结果：
  模型权重没有变
  但下一次 runtime 上下文和可用操作手册变强了
最准确的理解是：Hermes 的 skills 是外层 agentic learning，不是内层 agentic RL。 它不通过 reward 改 LoRA 或 base model 权重，而是通过持续改写 procedural memory，让 agent 的运行时上下文越来越像“经过项目经验训练过”。
