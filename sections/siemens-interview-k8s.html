K8s 了解多少：分层回答框架

"K8s 了解多少"是开放题，面试官想看你的认知边界和实践经验。按解决什么问题 → 核心概念 → 架构 → 你用过多深四层回答，诚实标注深浅即可。

第一层：K8s 解决什么问题

容器编排平台。当服务从几台机器几个容器变成几百上千容器时，手工管理不可能，K8s 负责：调度（容器放哪台机器）、自愈（挂了自动重启/迁移）、弹性伸缩（按负载加减副本）、服务发现与负载均衡、滚动发布与回滚、声明式配置（描述期望状态，系统自动逼近）。

第二层：核心对象

Pod

最小调度单位，一个或多个共享网络/存储的容器。一般不直接创建 Pod，而是由控制器管理。

Deployment / ReplicaSet

无状态服务的标准管理方式：声明副本数，RS 保证数量，Deployment 在其上加滚动更新和回滚。StatefulSet 管有状态服务（稳定网络标识+稳定存储），DaemonSet 保证每节点跑一个（日志/监控 agent）。

Service / Ingress

Pod IP 会变，Service 提供稳定的虚拟 IP 和 DNS 名做服务发现+负载均衡（ClusterIP 内部、NodePort、LoadBalancer）。Ingress 管 HTTP/HTTPS 七层入口路由，统一域名、TLS、路径规则。

ConfigMap / Secret / PV

ConfigMap 存非敏感配置，Secret 存密钥（base64+RBAC）。PV/PVC 把存储抽象成"申请-绑定"模型，Pod 不用关心底层是 NFS 还是云盘。

第三层：控制面架构（追问深挖用）

API Server。唯一入口，所有组件都通过它读写集群状态。
etcd。分布式 KV，存全部集群状态，是集群的"数据库"。
Scheduler。给 Pending Pod 选节点：先过滤（资源够不够、亲和性），再打分选最优。
Controller Manager。一堆控制循环：持续对比期望状态和实际状态，不一致就纠偏——这是 K8s "声明式"的灵魂。
节点侧 kubelet + kube-proxy。kubelet 管本节点 Pod 生命周期、上报健康；kube-proxy 实现 Service 的转发规则（iptables/IPVS）。

第四层：实际使用深度（按真实经历答）

浅层使用：会写 Deployment/Service 的 YAML，会 kubectl apply/get/logs/describe/exec，会把服务部署上去并排查 CrashLoopBackOff。中层：配过 resource request/limit 和 HPA 自动扩缩、liveness/readiness 探针、滚动更新策略；用 Helm/Kustomize 管理多环境；跑过 GPU 训练任务（nvidia device plugin、node selector/taints）。深层：Operator/CRD 自定义资源、网络策略、RBAC、成本与调度优化。

常见追问

"Pod 挂了怎么办？"——restartPolicy 控制 Pod 内重启；Deployment 保证副本数补齐；探针区分"需要重启"（liveness）和"暂时不接流量"（readiness）。"发布怎么做？"——Deployment 滚动更新（maxSurge/maxUnavailable）、金丝雀（两个 Deployment + Service 权重/Ingress canary）、蓝绿。"排查一个服务不通？"——Pod 状态 → describe 看事件 → logs 看应用 → Service endpoints 有没有 Pod → DNS/网络策略。
