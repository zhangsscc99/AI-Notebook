系统设计题：设计一个 LLM 上下文压缩系统（UML/类设计）

以 Claude Code 真实源码（src/services/compact/）为参考的一道设计题：面试官让你设计"对话上下文快满时自动压缩"的子系统，要求先画 UML 类图/时序图，再接受逐层追问。

题目：你的 agent 主循环里消息历史不断增长，模型上下文窗口有限。设计一个上下文压缩（Context Compaction）子系统：监控 token 用量、自动触发压缩、压缩后还能恢复关键文件上下文。画出类图和主流程。

一、先拆需求（答题第一步永远是定边界）

监控：每轮统计 token 用量，区分"警告/错误/必须压缩"三档水位。
压缩：让模型把旧对话总结成摘要，用摘要 + 保留尾部消息替换整段历史。
恢复：压缩后把关键上下文（最近读过的文件、计划、skill）按预算重新注入。
兜底：压缩失败要熔断重试，用户可手动 /compact 也可禁用自动压缩。

二、UML 类图

虚线 = 依赖 «use»/notify，实线箭头 = 关联（注入/创建/调用）。来源：src/services/compact/{autoCompact, compact, microCompact}.ts。

三、UML 时序图（自动压缩一轮）

实线实箭头 = 同步调用，虚线开箭头 = 返回；激活条表示参与者处于执行中。守卫条件用方括号标注在消息上。

四、追问点（面试官按这个套路深挖）

"为什么要两档压缩？"

microCompact 只在白名单工具（Read/Bash/Grep/Glob/WebFetch/WebSearch/Edit/Write）的旧结果上做定点清除，替换成占位符——不动消息结构、不花模型调用，prompt cache 友好；全量 compact 才调模型生成摘要。轻量问题用轻量手段，是分层设计的体现。

"摘要生成为什么用子 agent？"

runForkedAgent 把压缩当一次独立 agent 调用跑：独立上下文、独立权限（createCompactCanUseTool 控制压缩期间能用哪些工具）、失败不污染主循环。组合 + 依赖注入。

"阈值怎么定的？"

三个 buffer 各管一件事：20k 给摘要输出留空间（p99.99 实测 17,387 tokens）、13k 触发缓冲、3k 手动压缩硬上限。全部可用环境变量覆盖做测试——可配置性。

"压缩丢了重要信息怎么办？"

两道保险：① CompactBoundary 记录保留段起点，边界后原文不丢；② PostCompactRestorer 按文件/plan/skill 各自的 token 预算把关键上下文重新注入——压缩是"有损摘要 + 无损关键点重放"的组合。

五、设计原则对应（最后升华一句）

CompactionPolicy 可换 = 策略模式 + 开闭；Summarizer 注入 = 依赖倒置；pre/post compact hooks = 观察者；micro vs full 两级压缩 = 单一职责 + 分层策略；熔断器状态 = 状态机。一句收尾："压缩系统本质是缓存淘汰——消息是不可重算的、工具结果是可重取的，所以前者做摘要、后者直接清。"
