Claude Code 多 agent 机制：Team、Teammate、Mailbox、TaskList 与 Backend

Claude Code 里的“多 agent”不是单一机制，而是两层东西叠在一起：一层是 AgentTool 子代理，用于一次性派发 Explore / Plan / general-purpose 等子任务；另一层是 Agent Swarms / Team Teammates，用于创建长期存在、可命名、可互相发消息、可共享任务列表的团队。

核心结论：Claude Code 的多 agent = TeamCreate 建团队 + Agent(name, team_name, ...) 生成 teammate + SendMessage 发消息 + TaskCreate/TaskList/TaskUpdate 分工 + mailbox 文件做异步通信 + tmux/iTerm2/in-process backend 承载执行。
团队入口：父 agent 调用 TeamCreate，创建 team config 和对应 task list。
生成成员：父 agent 调用 Agent({ name, team_name, prompt, subagent_type, mode })。
分流判断：AgentTool.call() 发现有 teamName && name，不走普通 subagent，而走 spawnTeammate()。
后端选择：registry 选择 tmux、iTerm2 pane，或 in-process backend。
启动 teammate：写 team file，注册 AppState task，给 teammate 分配 agentName@teamName 身份。
初始任务：leader 把 prompt 写入 teammate 的 mailbox，teammate 读取后进入自己的 agent loop。
协作过程：成员通过 SendMessage、共享 task list、idle notification、permission request 互相协调。
收尾：leader 发送 shutdown_request，teammate 决定退出；最后 TeamDelete 清理团队资源。

1. 两种“多 agent”不要混

普通 subagent：父 agent 调 Agent({ subagent_type, prompt })，运行时启动一个子 query()，结果以 tool_result 或 task-notification 回来。它更像“派一个临时专家去做一件事”。

Team teammate：父 agent 先有 team，再调 Agent({ name, team_name, prompt })。有 name 后，这个 agent 变成可寻址的长期成员，能收消息、发消息、查任务列表、进入 idle 等待下一轮任务。

源码分界点在 AgentTool.tsx：如果 teamName && name 成立，就调用 spawnTeammate()；否则才走普通 runAgent() 子代理路线。

2. TeamCreate：团队是文件 + AppState + TaskList

src/tools/TeamCreateTool/TeamCreateTool.ts 创建团队。它会生成 team lead 的 deterministic id，写入 ~/.claude/teams/{team}/config.json，并重置/创建对应任务目录 ~/.claude/tasks/{team}/。

Team file 里有 members 数组，记录每个成员的 name、agentId、agentType、model、cwd、pane id、backendType 等。AppState 里的 teamContext 则让当前 leader 会话知道自己正在管理哪个 team。

这就是为什么源码里一直强调：通信和任务分配要用 teammate 的 name，不要直接用 UUID。

3. spawnTeammate：Agent 工具变成“开新成员”

src/tools/shared/spawnMultiAgent.ts 是 teammate 创建核心。它会：

  • 给重复名字自动加后缀，如 tester-2。
  • 用 formatAgentId(name, teamName) 形成 name@team 身份。
  • 选择模型：支持继承 leader 模型，也支持 agent frontmatter/model 参数覆盖。
  • 写 team file，把新成员追加到 members。
  • 注册 task，让 UI 能显示 teammate 正在运行。
  • 把初始 prompt 写入 teammate mailbox，而不是直接把 prompt 当 CLI 参数塞进去。

所以 teammate 的第一轮输入，实际上是从邮箱里被读到的。这是多 agent 异步通信的关键。

4. Backend：tmux / iTerm2 / in-process 三类承载方式

src/utils/swarm/backends/registry.ts 做 backend detection：

  • 在 tmux 里运行：优先用 tmux split pane。
  • 在 iTerm2 且 it2 CLI 可用：用 iTerm2 native panes。
  • 不在 tmux/iTerm2 但 tmux 可用：创建外部 claude-swarm session。
  • in-process backend：同一个 Node.js 进程内运行 teammate，用 AsyncLocalStorage 做身份隔离。

pane backend 的价值是“每个 teammate 像独立 Claude Code 终端”；in-process backend 的价值是“不依赖外部终端，多 agent 都在同一进程里调度”。

5. Mailbox：多 agent 通信不是共享上下文，而是收发文件消息

src/utils/teammateMailbox.ts 实现文件邮箱。每个 teammate 有一个 inbox 文件，路径类似：

~/.claude/teams/{team_name}/inboxes/{agent_name}.json

writeToMailbox() 写消息，并用 lockfile 防止多个 agent 同时写入时互相覆盖；readMailbox() 读取消息；markMessageAsReadByIndex() 把消息标记为已读。

消息注入到模型上下文时，会被格式化成：

<teammate-message teammate_id="researcher" summary="...">
消息内容
</teammate-message>

这说明多 agent 没有共享隐藏思维链，只有显式消息、共享任务文件和共享项目文件。

6. SendMessage：统一的通信工具

src/tools/SendMessageTool/SendMessageTool.ts 是 leader 和 teammate 通信的主工具。普通文本消息必须带 summary，可以发给具体名字，也可以 to: "*" 广播。

它有几种路由：

  • 如果目标是 in-process local agent/task，就把消息塞进 pendingUserMessages 或尝试从 transcript 恢复。
  • 如果是 team teammate，就写入对方 mailbox。
  • 结构化消息用于 shutdown、plan approval 等控制流。
  • 启用 UDS/bridge 时，还能跨 session 发纯文本消息。

所以多 agent 的“对话”本质是工具调用触发的消息路由，而不是多个模型自动共享同一个聊天窗口。

7. TaskList：团队协作靠任务板解耦

Team 和 TaskList 是 1:1 的。TeamCreate 创建 team 时会创建对应 task list；TaskCreate、TaskList、TaskUpdate、TaskGet 让 leader 和 teammates 共享一块任务板。

in-process runner 里还有 tryClaimNextTask()：teammate idle 时会查看任务列表，找 pending、未分配、未被未完成依赖阻塞的任务，claim 后继续工作。

因此 Claude Code 的多 agent 编排不是只靠聊天，而是 消息 + 任务状态 + owner + blockedBy 组合成一个轻量工作流系统。

8. in-process teammate：长期循环，不是一次性运行

src/utils/swarm/inProcessRunner.ts 的 runInProcessTeammate() 有一个 while loop。每轮它把当前 prompt 交给 runAgent()，也就是复用普通 agent loop；完成后不退出，而是标记 idle，发 idle notification，然后等待下一条 mailbox 消息、shutdown request 或可领取任务。

这和普通 background subagent 最大不同：普通 subagent 完成就结束；teammate 完成一轮后会“挂起等活”，类似团队里的长期 worker。

9. 权限：teammate 不是绕过 leader 的安全边界

in-process teammate 的工具权限通过 createInProcessCanUseTool() 接到 leader 的权限 UI。如果工具需要 ask，它会在 leader 侧显示带 worker badge 的确认对话；没有 UI bridge 时，fallback 到 mailbox permission request/response。

如果 teammate 是 plan_mode_required，启动参数会带 --plan-mode-required 或 in-process state 设成 plan。teammate 需要通过 plan approval 流程，由 team lead 审批后再进入实现。

10. Shutdown / TeamDelete：收尾也协议化

团队成员不是随便 kill。推荐流程是 leader 用 SendMessage 发结构化 shutdown_request；teammate 收到后由模型决定 approve/reject。in-process backend 会设置 shutdownRequested，pane backend 则依赖对应终端/进程通信。

TeamDelete 会检查团队是否还有 active members。如果还有成员没退出，清理会失败，要求先优雅关闭 teammates。这样避免任务、邮箱和终端 pane 资源被半截清掉。

Claude Code 多 agent 总心智模型：

TeamCreate
  -> ~/.claude/teams/{team}/config.json
  -> ~/.claude/tasks/{team}/
  -> AppState.teamContext

Agent({ name, team_name, prompt, subagent_type })
  -> AgentTool.call()
  -> teamName && name ? spawnTeammate() : runAgent()
  -> spawnTeammate()
       生成 name@team agentId
       选择 backend: tmux / iTerm2 / in-process
       注册 task / 写 team file
       prompt 写入 teammate mailbox

Teammate runtime
  -> 读取 mailbox / task list
  -> runAgent() 跑一轮工作
  -> SendMessage 给 leader 或其他 teammate
  -> TaskUpdate 更新任务状态
  -> idle notification
  -> 等下一条消息、下一项任务或 shutdown_request

通信边界
  -> 不共享隐藏推理
  -> 显式 mailbox 消息
  -> 显式 task list 状态
  -> 显式 permission / plan approval
  -> 显式 shutdown 协议
最短总结：Claude Code 多 agent 机制不是“开 N 个模型一起聊天”，而是一个工程化团队系统。 Team file 负责身份注册，Mailbox 负责异步消息，TaskList 负责工作拆分，Backend 负责执行承载，Permission/Plan/Shutdown 负责安全边界和生命周期。
