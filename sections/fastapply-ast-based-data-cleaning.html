minT / FastApply 里的“基于 AST 清洗数据”是什么

基于 AST 清洗数据，不是简单看 diff 里有没有加减号，而是把 old_source 和 new_source 解析成语法树，判断这次代码变更到底动到了什么语义结构：import、class、function、statement、docstring、comment 等。这样可以过滤掉“不适合训练 FastApply 的脏样本”。

一句话：AST 清洗 = 把代码变成 Unit 树 → 把 diff hunk 映射到 Unit 的行号 span → 判断被修改的是不是功能性代码 → 过滤纯注释/纯格式/不可解析/过大/过多 hunk 的样本。

源码里的流程是：

先解析语法树。filter.py 里对 old_source 和 new_source 分别调用 build_ast(language, source)。
AST 被转成 Unit 树。Python 走 ast.parse，把节点转成 import、class、function、docstring、statement 等 Unit；JS/Go/Rust 等在当前复刻里用轻量 regex / brace fallback。
拆 diff hunks。按 @@ -a,b +c,d @@ 把 unified diff 拆成 Hunk，拿到旧文件和新文件里被改动的行号范围。
把 hunk 映射到 Unit。ChangeContext 用 hunk 的行号 span 判断哪个 Unit 被修改；expand_context_to_all_units() 再把修改状态向子节点传播。
跑规则。规则会检查是否有 functional modification、是否只动 function/class/statement、是否要求 import modification、hunk 数是否过多、代码是否超长。
通过才进入训练数据。通过 AST 清洗后，样本才会继续 generate / deduplicate / convert 成 GRPO prompt。

为什么不用纯 diff 清洗

纯 diff 只能看到哪几行变了，看不懂这些行属于函数、类、import、注释还是 docstring。训练 FastApply 时，我们更关心“功能性代码更新”，而不是大量格式化、注释修正、无意义重排。

Unit 是什么

Unit 是源码里的轻量 AST 节点包装，带 type、span、children、parent。比如一个函数 Unit 的 span 是第 10 到 40 行；如果 diff 命中这些行，就能判断这个函数被改了。

functional modification 是什么

functional 在源码里对应 class、function、statement。只要被修改 Unit 落在这些类型里，就说明这条样本至少改到了功能逻辑。

non-functional 会怎样

如果只动 comment、docstring、package、import 这类非功能性范围，可能会被过滤，取决于规则配置。当前 Filter 默认要求有功能性修改，并可选要求 import 修改。

拿一个具体例子：

旧代码：
def calc(x):
    return x + 1

新代码：
def calc(x):
    return x + 2

diff 命中第 2 行
AST Unit:
  function calc span=[1,2]
    statement return span=[2,2]

ChangeContext 发现 statement 被改
=> functional modification = true
=> 样本保留

再看一个会被过滤的例子：

旧代码：
def calc(x):
    """old doc"""
    return x + 1

新代码：
def calc(x):
    """new doc"""
    return x + 1

diff 只命中 docstring Unit
=> 没有真正 statement/function 逻辑变化
=> 对 FastApply 训练价值低，倾向过滤
核心意义：AST 清洗让训练数据从“文本行变化”升级成“语义结构变化”。这能减少格式/注释噪声，让模型主要学习如何把补丁应用到真实代码逻辑里，而不是学一堆低价值 diff。
