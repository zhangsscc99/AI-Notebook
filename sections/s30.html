被问 OpenClaw 怎么搞记忆时怎么答

如果别人问“OpenClaw 是怎么搞记忆的”，不要回答成“它有 RAG”这么浅。更准确的回答是：

OpenClaw 的记忆是文件驱动的长期记忆系统。重要信息先写进 MEMORY.md 或 memory/YYYY-MM-DD.md 这类可审计文件，然后 memory-core 或 QMD 把这些文件切成 chunks、建立 FTS/向量索引。模型需要旧信息时先用 memory_search 检索相关片段，再用 memory_get 按路径和行号回读原文。临近 compaction 时还有 memory flush，把当前会话里值得长期保存的信息追加到当天 memory 文件。

你可以按场景用下面三种说法。

30 秒版本

OpenClaw 不是把记忆藏在模型脑子里，而是把记忆显式写成文件。然后它对这些文件建索引，搜索时召回片段，需要核实时再按行读取原文。所以它的 memory 是“文件落盘 + 索引检索 + 原文回读 + compaction 前保全”。

源码版本

工具入口是 memory_search 和 memory_get。它们通过 getMemorySearchManager 拿到 backend manager。builtin 后端是 MemoryIndexManager，用 SQLite、FTS5、可选 sqlite-vec；QMD 后端是 QmdMemoryManager，把检索交给 qmd sidecar。

和普通 RAG 的区别

RAG 只是其中的检索部分。OpenClaw 还包括启动注入、memory flush、session transcript indexing、dreaming / promotion、memory-wiki、registered corpus supplements，以及 memory_get 这种精确原文读取。

一句话判断重点

问“它记住了吗”时，关键不是模型有没有印象，而是信息有没有落盘、有没有被 sync 建索引、搜索结果能不能通过 memory_get 找回原文。

推荐你实际回答时按这个结构：

1. 先说本质：文件驱动，不是模型内部魔法记忆。
2. 再说流程：写文件 -> sync -> chunk -> FTS/vector/QMD index -> memory_search -> memory_get。
3. 再说后端：默认 builtin SQLite/FTS/vector；也可以切到 QMD。
4. 再说扩展：compaction 前 flush，session memory，dreaming，memory-wiki。
5. 最后强调边界：只有落盘并被允许索引/读取的内容，才算可用记忆。
最稳的短答：OpenClaw memory = durable markdown files + searchable index + exact source readback + lifecycle automation。这个答案比单说“RAG”准确得多。
