如果 reward 很好，但最终 GRPO 效果不好，可能是什么原因

reward 分数高不等于训练效果一定好。GRPO 优化的是 reward 定义下的相对概率，如果 reward、采样分布、advantage、LoRA 容量或数据覆盖有问题，最后可能出现“reward 看着不错，模型真实效果反而一般”。

Reward 本身的问题

  • reward hacking：模型学会讨好 verifier，而不是真正会 Apply。
  • reward 太稀疏：只有 exact match 才给分，绝大多数样本都是 0，advantage 信号很弱。
  • reward 权重错：例如 tag 格式权重太高，模型只学会包装标签，代码合并能力没提升。
  • 离线指标不代表真实场景：tiny fixture 上 reward 高，但真实 Git diff 更长、更乱、上下文更多。

GRPO 训练过程的问题

  • group size 太小：组内比较不稳定，advantage 噪声大。本次 smoke 是 1 policy + 1 oracle，只是跑通链路。
  • 采样温度不合适：温度太低，样本都差不多；温度太高，样本太乱，reward 噪声大。
  • ratio 漂移：新旧策略差太多时，importance ratio 方差变大，训练不稳。
  • 学习率过大：容易把 LoRA 往某些 reward shortcut 上推过头。

数据覆盖问题

FastApply 的难点在长上下文、多 hunk、模糊 SEARCH、跨函数依赖、缩进/注释保留。如果训练数据只有短函数，reward 再高也无法保证长文件 Apply 表现。

模型容量问题

LoRA rank 太小、目标层太少，可能 reward 能推一点格式，但推不动复杂代码编辑能力；rank 太大又可能过拟合 tiny reward。

排查顺序：先看 reward 是否真的覆盖业务目标，再看 group size/温度/学习率，再看数据难度分布，最后看 LoRA rank 和目标层容量。
