多余解释会给训练和下游带来什么风险

在代码 Apply 任务里，多余解释不是小问题。因为这个模型的输出通常不是给人看的，而是要给下游程序自动接上。no_extra_prose 的价值就在这里。

训练侧风险

  • reward hacking：模型可能学会“代码正确 + 外面胡说”，exact 仍高，但行为不干净。
  • 分布污染：GRPO 会提高高 reward 轨迹概率，如果不罚废话，模型会保留聊天习惯。
  • 长度浪费：多余 token 影响采样成本，也挤占长代码上下文。
  • 多标签歧义：如果输出多个 updated 块，不同 extractor 可能取 first 或 last，训练和部署不一致。

下游工程风险

  • 某些接入方可能不是用我们这个鲁棒正则，而是直接拿 raw output 写文件。
  • Markdown fence、解释文本、日志前缀会让 apply / formatter / compiler 直接失败。
  • 额外自然语言可能被当成代码注释或非法 token 混入文件。
  • 安全上也更难控：标签外文本可能携带无关指令、路径、环境信息。
训练时允许抽取，是为了不要因为一点格式噪声完全丢掉内容 reward。
训练时惩罚 extra prose，是为了逐步把模型推向纯机器输出。
上线时最好要求 raw output 本身就是唯一 updated 块。
最终目标：下游可以直接解析、应用、测试，不需要人工清洗。
结论：规则抽取是容错机制，no_extra_prose 是行为约束。 容错不是纵容；训练里两者同时存在，才能既不浪费接近正确的样本，又把模型输出训得足够干净。
