WAN8

Wan2.2 到底是在预测 latent 吗，还是视觉编码器拼接 LLM

结论先说：Wan2.2 主要是在预测视频 latent 的去噪方向，不是“视觉编码器拼接 LLM”。它不是一个把视觉 token 接到语言模型后面继续做文本自回归的大模型，而是一个视频 latent 扩散 / flow matching 系统：文本条件先经 T5 编码，视频或首帧图像先经 VAE 压缩成 latent，然后 WanModel 在 latent 空间里做多步去噪，最后再由 VAE 解码成视频帧。

一句话：Wan2.2 的生成核心是视频 latent denoising。T5 负责文本条件，VAE 负责压缩和解码，WanModel 负责在 latent 空间里迭代更新；它不是“视觉 encoder + LLM”的拼装体。
文本走 T5，不走 LLM decoder。WanT2V 和 WanI2V 都先调用 T5EncoderModel，把 prompt 变成 context 和 context_null。
视觉内容先压成 latent。在 image / text-image / TI2V 路径里，输入图像会先走 vae.encode([img])，变成 latent 条件 y。这一步是进入视频 latent 空间，不是拼到 LLM hidden states 上。
主干是 WanModel。wan/modules/model.py 里的 WanModel 用 Conv3d 做 3D patch embedding，再用 self-attention / cross-attention 在视频 latent token 上建模。
模型预测的是更新量。采样循环中，WanModel 输出 noise_pred 或 latent 的更新方向，scheduler 再把当前 noisy latent 推向更干净的状态。
最后由 VAE 解码。采样结束后，self.vae.decode(x0) 把 clean latent 变成 RGB 视频张量，真正的视频文件在这一步之后才生成。

为什么不是“视觉 encoder 拼接 LLM”

如果是典型 VLM / MLLM，结构通常是 vision encoder 产出视觉 token，再通过 projector 接到 LLM，让 LLM 继续做文本生成。Wan2.2 没有这条路：它不把图像 token 交给语言模型续写，也不让 LLM 逐 token 生成视频。

为什么也不是直接预测像素帧

源码里先算 target_shape，用 torch.randn 初始化视频 latent，再在 latent 空间采样。像素帧只在最后 decode 阶段出现，所以它不是像普通自回归模型那样直接回归 RGB。

视频里真正被预测的是什么

在 diffusion / flow matching 里，模型通常预测噪声方向、velocity 或 latent 更新量。你可以把它理解成“学会把当前 noisy latent 往更像真实视频的方向推”，而不是“预测下一个文本 token”。

图像输入在系统里扮演什么

图像更像条件约束或首帧锚点。它先被 VAE 压缩成 latent 条件，再在去噪过程中约束主体、构图和运动延续，而不是作为视觉 encoder 的输出直接拼进 LLM decoder。

更准确的心智模型：

文本 prompt -> T5 encoder -> context
输入图片/首帧 -> VAE encode -> latent condition y
随机视频 latent -> WanModel / DiT -> 预测 latent 去噪方向
scheduler.step -> 更新 latent
VAE decode -> RGB video

这条链路里：
- 没有把视觉 encoder 输出拼接给 LLM 做续写
- 没有让 LLM 直接生成视频像素
- 核心生成空间是视频 latent，不是文本 token
所以如果你问“Wan2.2 是不是预测 latent”，答案是是，但更精确地说是预测视频 latent 的去噪/更新方向；如果你问“是不是视觉编码器拼接 LLM”，答案是不是，它是一个以 T5 + VAE + Video DiT 组成的条件生成系统。
