Claude Code 怎么避免工具调用参数格式错误

Claude Code 避免工具参数格式错误不是靠一句 prompt 提醒模型“请输出正确 JSON”。源码里它做成了一条完整防线：先把每个工具的 Zod schema 转成 API tool schema 约束模型输出，再在本地用同一套 schema 二次校验；错了不执行工具，而是返回带具体原因的错误 tool_result，让下一轮模型修正。

一句话：Claude Code 把“参数格式正确”从模型自觉行为，变成了 schema 约束 → 本地 parse → 工具级 validate → 错误回传重试 的协议闭环。

1. 每个工具先声明强类型输入

src/Tool.ts 定义统一 Tool 接口，每个工具都有 inputSchema。大部分内置工具用 z.strictObject(...) 定义参数，例如 Bash 必须有 command，Read 必须有 file_path，Edit 必须有 file_path、old_string、new_string。

strictObject 的意义是：不仅缺字段会错，多出来的未知字段也会错。这样模型不能随便塞一个 path、filename、args 之类的非 schema 字段蒙混过关。

2. 发给模型的是 JSON Schema

每次请求模型前，src/services/api/claude.ts 会构造 toolSchemas；具体转换在 src/utils/api.ts 的 toolToAPISchema()。

如果工具没有手写 inputJSONSchema，就调用 zodToJsonSchema(tool.inputSchema)，把 Zod schema 转成 Anthropic API 的 input_schema。这一步让模型在 tool_use 阶段就知道每个工具需要哪些字段、字段类型是什么。

完整链路可以按这个顺序理解：

工具作者在工具文件里写 inputSchema = z.strictObject(...)。
toolToAPISchema() 把 inputSchema 转成 API input_schema，随请求发给模型。
模型返回 assistant.tool_use，里面有 name、id、input。
runToolUse() 找工具名；找不到就返回 No such tool 的错误 tool_result。
checkPermissionsAndCallTool() 先执行 tool.inputSchema.safeParse(input)。
schema parse 失败：不进权限、不执行工具，直接返回 InputValidationError。
schema parse 成功后，才进入 tool.validateInput()、权限、hooks 和真正 tool.call()。
模型输出：
ToolUse(name="Read", input={ "path": "src/index.ts" })

Claude Code 本地执行：
tool = findToolByName(tools, "Read")
parsed = tool.inputSchema.safeParse(input)

if (!parsed.success):
  return tool_result(
    is_error=true,
    content="<tool_use_error>InputValidationError: The required parameter `file_path` is missing; An unexpected parameter `path` was provided</tool_use_error>"
  )

// 只有 parsed.success 才会继续：
validateInput(parsed.data)
checkPermissions(parsed.data)
tool.call(parsed.data)

3. 错误信息专门做成模型可读

src/utils/toolErrors.ts 的 formatZodValidationError() 会把 Zod 原始错误整理成 LLM 更容易修正的句子：缺少哪个 required parameter、哪个参数是 unexpected、哪个参数类型应该是什么但实际给了什么。

所以模型下一轮看到的不是一坨难读的 Zod stack，而是类似：The required parameter `file_path` is missing、An unexpected parameter `path` was provided、expected string but provided number。

4. schema 错误会闭合 tool_use 协议

即使参数错了，Claude Code 也不会简单抛异常结束。它会构造一个 user message，里面包含同一个 tool_use_id 对应的 tool_result，并且标记 is_error: true。

这点很重要：Anthropic API 要求 assistant 的 tool_use 后面必须有匹配的 tool_result。Claude Code 用错误结果把协议闭合，下一轮模型才能继续，而不是整个会话因为消息结构非法崩掉。

5. schema 通过后还有语义校验

safeParse 只管“形状对不对”。比如字段名、类型、是否多字段。每个工具自己的 validateInput() 继续检查“值能不能用”。

例子：Read 会检查文件路径和读取限制；Edit 会检查文件是否存在、是否读过、old_string 是否唯一匹配；Bash 会检查 timeout、后台任务、平台策略等。这些失败也会变成错误 tool_result 返回给模型。

6. strict tool 进一步约束模型

Tool 接口里有 strict?: boolean。如果 feature gate 开启、工具声明 strict: true、模型支持 structured outputs，toolToAPISchema() 会给 API schema 加 strict: true。

源码里 Bash、Read、Write、Edit、TodoWrite、Grep、PowerShell 等都有 strict 倾向。作用是让模型在生成参数时更贴近 schema，而不是等本地报错再重试。

7. 流式 tool input 也会归一化

开启 fine-grained tool streaming 时，API 可能以 input_json_delta 形式逐步返回工具参数。messages.ts 会把字符串形式的 tool input 解析成对象；如果 JSON 解析失败，会记录 tengu_tool_input_json_parse_fail，并退化成空对象，让后续 schema 校验给出明确缺参错误。

这比“半截 JSON 直接执行”安全得多：解析不出来就不执行，最终还是落到统一的 safeParse → InputValidationError 路径。

8. 工具输入会做有限 normalize

normalizeToolInput() 会对少数工具做兼容修正：比如 Bash 去掉重复的 cd cwd && 前缀；FileEdit 统一旧格式；TaskOutput 兼容历史参数名。

但这不是放任模型乱写参数。源码注释也写了 TODO: Generalize this to all tools，说明 normalize 是少量兼容层；真正的安全边界仍然是 schema parse 和工具级 validate。

9. 动态工具没 schema 时会提示先加载

ToolSearch / deferred tool 场景下，有些 MCP 或延迟加载工具的完整 schema 可能还没发给模型。buildSchemaNotSentHint() 会检测这种情况。

如果因为没拿到 schema 导致数组、数字、布尔值被模型当字符串输出，错误信息会追加提示：先调用 ToolSearch 加载该工具 schema，再重试。这样避免模型在不知道完整参数结构时盲猜。

10. UI 渲染也不信任未解析输入

AssistantToolUseMessage.tsx 渲染工具调用时也会 tool.inputSchema.safeParse(param.input)。如果 parse 不过，就不把错误输入当成正常工具 UI 展示。

这属于防御性设计：执行层不信任模型输入，展示层也不信任模型输入，避免 UI 因为半成品参数或错误字段崩掉。

所以参数格式错误的恢复过程不是“Claude Code 帮模型偷偷改对”，而是更工程化的闭环：

第一次：模型错调
Read({ "path": "src/index.ts" })

本地：schema 拒绝
InputValidationError:
- required `file_path` missing
- unexpected `path` provided

第二次：模型读错误结果后修正
Read({ "file_path": "src/index.ts" })

本地：schema 通过 → validateInput 通过 → 权限通过 → 执行 Read
最短总结：Claude Code 防参数格式错误靠四件事：工具 schema 前置给模型、本地 Zod 二次校验、错误 tool_result 反馈可修正原因、下一轮模型按错误重试。 它不假设模型永远会写对参数，而是把“写错了也能安全纠正”做进工具协议。
