OpenClaw 的网关到底是干什么的

OpenClaw Gateway 不是“模型网关”这么简单。它更像 OpenClaw 的常驻入口层 + 控制面 + 会话路由器 + 协议适配层：外部客户端、网页 Control UI、CLI、手机端、Telegram / Synology Chat 等 channel 插件，都可以通过它把一条消息变成一次 OpenClaw agent run。

一句话：Agent runtime 是真正干活的大脑和手；Gateway 是门口的前台、安检、分诊台和事件总线。它负责“谁能进来、要找哪个 agent / session、用什么协议进来、结果怎么流回去”。

1. 它首先是一个常驻服务

openclaw gateway run 会走 src/cli/gateway-cli/run.ts，解析端口、bind 地址、认证、Tailscale、日志等配置，然后懒加载 src/gateway/server.ts，最终进入 startGatewayServer()。

默认连接地址在客户端里能看到：ws://127.0.0.1:18789。也就是说，它默认是本机 WebSocket/RPC 服务；如果配置成非 loopback 或远程暴露，就必须处理认证和安全策略。

2. 它把外部协议统一成 Gateway RPC

CLI 侧的 callGateway() 会创建 GatewayClient，通过 WebSocket 发送形如 { type: "req", id, method, params } 的请求帧。服务端用 handleGatewayRequest() 根据 method 分发到对应 handler。

所以外部入口不需要直接知道 agent 内部主循环怎么跑，只要调用 agent、chat.send、sessions.send、tools.invoke 这类方法。

3. 它维护“控制面”能力

server-methods-list.ts 里列了很多 Gateway 方法：agents.*、sessions.*、chat.*、tools.*、skills.*、artifacts.*、cron.*、nodes.*、exec.approval.* 等。

这说明 Gateway 不只是转发一句 prompt，而是把“创建 agent、列会话、发消息、查历史、调工具、看产物、做审批、跑定时任务、管理远端节点”都做成统一控制 API。

4. 它负责安全入口

server-runtime-config.ts 会解析 gateway.bind、auth token / password / trusted proxy、Control UI allowed origins、Tailscale serve / funnel 等。源码里明确拒绝“非 loopback bind 但没有认证”的配置。

这就是 Gateway 的“安检”职责：如果只在本机跑，可以是本地 RPC；如果要给手机、网页或公网入口用，就必须做认证、来源限制、rate limit、TLS / Tailscale 等保护。

最典型的一次请求链路可以这样理解：

用户从 CLI、Control UI、移动端或 channel 插件发来消息。
Gateway 先处理连接、认证、scope / role 权限、请求大小和来源安全。
请求被统一成 Gateway RPC：例如 method = "agent"，参数里带 message、agentId、sessionKey、channel、idempotencyKey。
handleGatewayRequest() 分发到 server-methods/agent.ts 的 agent handler。
agent handler 做 session 解析、附件处理、模型覆盖权限判断、去重、超时/abort 注册、必要的 startup context 注入。
真正执行时调用 agentCommandFromIngress()，进入 OpenClaw 的 agent runtime：模型思考、工具调用、写 transcript、产出回复。
Gateway 把运行状态、chat/session 事件、最终回复、artifact / media 链接再流回客户端或交给 channel 做外发。
外部入口
  ├─ CLI: openclaw agent --message ...
  ├─ Control UI / WebChat
  ├─ 手机端 / 远程节点
  └─ Telegram / Synology Chat / Webhook 等插件
        ↓
Gateway HTTP / WebSocket / RPC
  ├─ auth / role / scope / rate limit
  ├─ method dispatch: agent, chat.send, sessions.*, tools.invoke ...
  ├─ session / agent / channel routing
  └─ event streaming / result delivery
        ↓
OpenClaw Agent Runtime
  ├─ LLM 调用
  ├─ tools / sandbox / approvals
  ├─ transcript / artifacts / memory
  └─ reply payloads

为什么不让每个入口直接调 agent？

如果 Telegram、网页、CLI、手机端都各自直接接 agent runtime，就会重复实现认证、session 绑定、附件处理、错误恢复、事件流、权限和审计。Gateway 把这些横切逻辑集中起来，入口只要适配 Gateway 协议。

它和普通反向代理的区别

普通反向代理主要做 HTTP 转发；OpenClaw Gateway 里面有业务语义：它认识 agent、session、channel、tool、artifact、skill、approval、node、cron。它不是“把请求转到另一个服务”就结束，而是直接参与任务生命周期管理。

它和模型 API 网关的区别

模型 API 网关通常只负责模型路由、限流、计费、兼容 OpenAI API。OpenClaw Gateway 虽然也能暴露 OpenAI-compatible 的 /v1/chat/completions、/v1/responses、models、embeddings 等 HTTP 入口，但更核心的是 agent 应用控制面。

失败时怎么处理

agent-via-gateway.ts 里能看到 CLI 通过 Gateway 发 agent 请求；如果 Gateway 超时或传输失败，可以 fallback 到 embedded agent。本质上 Gateway 是推荐的统一入口，但本地 CLI 仍保留直接跑 agent 的兜底路径。

最容易记的说法：OpenClaw Gateway = OpenClaw 的“外部接入层 + 远程控制面”。 它不负责替模型思考；它负责让各种外部入口安全、统一、可观测地驱动同一套 agent runtime。
