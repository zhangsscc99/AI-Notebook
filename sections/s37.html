OpenClaw memory 的 sync 机制是什么，第一次没索引怎么建，session transcript 是什么

这个问题要分成两部分：sync 不是“读文件”本身，而是把可检索语料同步进索引库；session transcript 不是 Markdown，而是每个会话的 JSONL 日志。

一句话：第一次 memory_search 如果发现 SQLite/QMD 里没有任何 indexed content，会触发一次强制 sync；sync 只索引配置允许的来源，不会扫描整个项目。默认主要是 MEMORY.md + memory/，如果启用 sources: ["sessions"] 才会把 session transcript 历史也纳入检索。

1. sync 到底干什么

sync 的职责是把源数据变成检索索引：列文件、读文件元信息、算 hash、切 chunks、生成 embedding、写 SQLite 的 files / chunks / chunks_fts / chunks_vec，或写入 QMD collection。

所以 sync 不是把内容塞进模型上下文，也不是让模型重新读一遍；它是索引维护流程。

2. 第一次没索引怎么处理

MemoryIndexManager.search() 先调用 hasIndexedContent() 检查 chunks 或 FTS 表是否有内容。如果没有，就执行 sync({ reason: "search", force: true })，强制先建一次索引。

这保证 fresh process / 新库第一次问历史记忆时，不会因为后台 watcher 还没跑就直接返回空。

3. 是不是对所有东西建索引

不是。OpenClaw 只索引 memorySearch 配置允许的 sources：memory 代表 MEMORY.md、memory/*.md 和 extraPaths；sessions 代表会话 transcript。源码帮助文档也建议默认保持 ["memory"]，除非确实需要从历史聊天里召回。

4. 首次 force sync 会不会全量

对当前配置范围来说，首次通常接近全量：因为索引库没有旧 hash 可对比，所有 active memory files 都需要建索引；如果 sessions source 启用，force 也会让 session files 进入同步判断。注意这个“全量”仍然只是配置语料范围内的全量，不是 repo 全量。

一次 builtin sync 的核心流程可以这样记：

memory_search 进入 MemoryIndexManager.search()。
检查索引是否已有内容；没有就 sync({ reason: "search", force: true })。
runSync() 检查 vector extension、读取 index meta、判断是否需要 full reindex。provider、chunk 参数、sources、workspace/extraPaths 范围变化，都会触发 full reindex。
如果是 full reindex，走安全重建：临时库里重新建索引，成功后原子替换正式库，避免半成品索引污染线上检索。
如果不是 full reindex，就看 dirty / force / targeted session files：memory 文件走 syncMemoryFiles()，session 文件走 syncSessionFiles()。
syncMemoryFiles() 调 listMemoryFiles()，只列 MEMORY.md、memory/、extraPaths 中允许的 .md / multimodal 文件。
每个文件算 hash；hash 没变就跳过，hash 变了才重新 indexFile()。删除的文件会从 files/chunks/vector/FTS 表里 prune。

watch sync

ensureWatcher() 监听 MEMORY.md、memory/ 和 extraPaths。add/change/unlink 后标记 dirty = true，再按 debounce 延迟触发 sync({ reason: "watch" })。

interval sync

如果配置了 sync.intervalMinutes，会定时跑 sync({ reason: "interval" })，用于补偿 watcher 失效或外部批量修改。

search sync

搜索时如果索引为空，会同步建索引；如果已有索引但 dirty，startAsyncSearchSync() 可异步刷新，当前搜索不一定阻塞等待全部重建。

session delta sync

session transcript 更新不会每追加一行都立刻重建索引。它通过 onSessionTranscriptUpdate()、5 秒 debounce、deltaBytes / deltaMessages 阈值来批量同步。

session transcript 本质是什么？

1. 它不是 Markdown

session transcript 是 JSONL 文件，常见路径类似 ~/.openclaw/agents/<agentId>/sessions/<sessionId>.jsonl。每一行是一条 JSON 记录。

2. 第一行是 session header

新 transcript 会写入 { type: "session", version, id, timestamp, cwd }。这里的 timestamp 是 ISO 字符串，记录会话文件创建时间。

3. 后续行是 message record

每条消息通常是 { type: "message", id, parentId, timestamp, message }。外层 timestamp 也是 ISO 字符串；message 里可能还有 role、content、provider、model、usage、stopReason、message.timestamp 等字段。

4. session store 也记录生命周期时间

sessions.json / session store 里的 entry 会记录 updatedAt、sessionStartedAt、lastInteractionAt 等毫秒时间戳，用于 reset、prune、路由和活跃度判断。

一个简化 transcript 长这样：

{"type":"session","version":1,"id":"sess_abc","timestamp":"2026-05-21T10:00:00.000Z","cwd":"/repo"}
{"type":"message","id":"m1","parentId":null,"timestamp":"2026-05-21T10:00:05.000Z","message":{"role":"user","content":"记住 repo 是 zhangsscc00/knowledge_management"}}
{"type":"message","id":"m2","parentId":"m1","timestamp":"2026-05-21T10:00:08.000Z","message":{"role":"assistant","content":[{"type":"text","text":"已记录。"}],"provider":"openclaw","model":"..."}}

但它进入 memory index 时，不是原封不动把 JSONL 当 Markdown 切块。源码里的 buildSessionEntry() 会做一层转换：

读取 *.jsonl，逐行 JSON.parse。
只保留 type = "message" 且 role 是 user / assistant 的内容。
过滤 inter-session provenance、dreaming narrative、cron run、silent reply、内部包装等噪声。
抽取文本、redact 工具敏感信息，把它渲染成 User: ... / Assistant: ... 这种可检索纯文本。
保留 lineMap，把检索文本行映射回原 JSONL 行号；同时保留 messageTimestampsMs，把消息时间转成 epoch ms。
最后按普通内容进入 indexFile()：chunk、embedding、FTS/vector/QMD。
关键区别：session transcript 是原始会话日志；session-memory hook 生成的 memory/YYYY-MM-DD-HHMM.md 才是 Markdown 记忆文件。前者是 JSONL，偏完整、偏日志；后者是 Markdown，偏长期、偏可读、偏可维护。是否检索 transcript，取决于 memorySearch sources 是否包含 sessions。
