FastApply 数据怎么洗、怎么构建：再完整回答一遍

这套数据不是“随便拿一段代码让模型改”。FastApply / GRPO 数据构建的核心目标是：从真实代码变更里构造 old_source + patch + new_source 三元组，再把它变成可验证的 prompt / ground truth。清洗的核心目标是：只留下可重放、可解析、长度合适、非重复、适合训练“应用补丁”的样本。

一句话：数据构建 = 从 Git commit 抽 old/new/diff → 解析 diff hunks → 生成 SEARCH/REPLACE patch → 得到 update/new_source → 转成 GRPO prompt；数据清洗 = 过滤无效语言、空内容、超长样本、diff 不可重放、语法错误、非功能性修改、重复/近重复。

完整 pipeline 可以按这个顺序讲：

抽原始样本。build/extract.py 遍历 Git repo 的 single-parent commits，针对源码文件取 commit^:path 作为 old_source，取 commit:path 作为 new_source，再保存 unified diff。
语言和文件过滤。只保留 .py / .java / .js / .ts / .go / .rs / .c / .cpp 等源码扩展名；无法 detect_language 的文件直接跳过。
解析 diff。build/parse.py 按 @@ -a,b +c,d @@ 拆 hunks，把每个 hunk 分成 old SEARCH 片段和 new REPLACE 片段。
构造 patch。build/make.py 把 changes 组装成 <<<<<<< SEARCH ... ======= ... >>>>>>> REPLACE 的补丁格式；如果已有 new_source，就用确定性路径直接作为 update。
规则清洗。build/filter.py / generate.py 检查 AST、修改范围、import / functional modification、hunk 数量、长度等。
去重。deduplicate.py 对 update/new_source 做 normalize signature；大规模版本应该替换成 AST-normalized MinHash + LSH 近重复过滤。
转训练格式。convert.py 生成 data_source=apply、prompt、ability、reward_model.ground_truth、extra_info、response。

原始数据长什么样

{
  "id": "...",
  "repo": "xxx",
  "file": "src/a.py",
  "commit": "abc123",
  "language": "python",
  "old_source": "旧文件完整内容",
  "new_source": "新文件完整内容",
  "diff": "git diff 输出"
}

这一步还不是训练数据，只是从真实 commit 抽出来的可追溯原料。

训练 prompt 长什么样

Please apply all changes from <patch> to <source>.
- Preserve code structure...
- Output only the updated source code within <updated> tags.

<language>python</language>
<source>旧代码</source>
<patch>SEARCH/REPLACE patch</patch>

ground truth 是 new_source，response 模板是 <updated>...</updated>。

清洗到底清什么？

1. 基础有效性

过滤 old_source / new_source / diff 为空的样本；过滤非源码后缀；过滤 language 不在支持列表的样本；过滤 old_source == new_source 的无变化样本。

2. 长度控制

小复刻版用字符阈值；RL-master 版用近似 token：len(text)/4 + 1，默认不超过 max_seq_len=32768。太长会导致训练成本高、截断、reward 无法可靠判断。

3. patch 可重放

fastapply_pipeline/filters.py 会把 patch 应用到 old_source，要求结果 normalize 后等于 new_source。不能重放的样本说明 patch / old / new 三者不一致，必须丢。

4. 语法 / AST 可解析

对 new_source 做语言解析。Python 用 AST，其他语言可走对应 checker。语法坏的样本会让模型学到不可运行输出，也会干扰 reward。

5. 修改类型过滤

RL-master 的 filter 会把 diff hunk 映射到 AST Unit，要求至少有 functional modification；可选要求 import modification；可选只允许 function/class/statement 这类功能性范围。

6. 去重 / 近重复

小复刻版用 normalize 后 hash；更完整方案应该用 AST-normalized MinHash + LSH。目的不是只去完全重复，而是去掉变量名不同但结构几乎一样的近重复。

最后构建出来的 GRPO 行大概是：

{
  "data_source": "apply",
  "prompt": "...old source + patch...",
  "ability": "fast_apply",
  "reward_model": {
    "style": "rule",
    "ground_truth": "new_source / update"
  },
  "extra_info": {
    "id": "...",
    "repo": "...",
    "file": "...",
    "language": "python"
  },
  "response": "<updated>\n...new source...\n</updated>"
}
最容易讲给别人听的版本：FastApply 数据构建是在真实 commit 里挖“旧代码 + 变更补丁 → 新代码”的监督/强化样本；数据清洗是在确保这个样本可重放、可解析、不过长、不是重复题、reward 能判。清洗越严格，训练越不会学到脏格式、无效补丁和投机输出。
