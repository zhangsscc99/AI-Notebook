Claude Code 的沙箱怎么做的

Claude Code 的沙箱不是“把整个项目复制进一个 Docker 容器再改完拷回来”。从源码看，它主要是给 Bash / PowerShell 这类命令执行工具 加一层 OS 级运行时隔离：命令还是在当前工作目录语义下执行，但真正 spawn 前会被 @anthropic-ai/sandbox-runtime 包一层，限制它能读写哪些路径、能连哪些网络主机。

一句话：Claude Code 沙箱 = 应用层权限判断 + 命令级 OS sandbox wrapper。模型仍然发起 Bash / PowerShell 工具调用；真正危险的 shell 进程被放进受限环境里跑。

1. 沙箱管的是谁

核心覆盖对象是 shell 命令：BashTool.tsx 和 PowerShellTool.tsx 都会把 shouldUseSandbox 传给 src/utils/Shell.ts。

文件读写工具不是靠这个 shell wrapper 执行，而是走 Claude Code 自己的工具权限、路径权限、schema 校验。也就是说：沙箱不是替代所有权限系统，而是专门给“命令进程”兜底。

2. 两层安全模型

应用层：checkPermissions()、Bash 规则、allow/deny/ask、用户确认、企业策略，决定这个工具调用能不能发起。

运行时层：SandboxManager.wrapWithSandbox() 把命令变成受限命令，由外部 sandbox-runtime 在 macOS / Linux / WSL2 上做文件系统和网络隔离。

主链路可以按这个顺序记：

启动时读取 settings / permissions，SandboxManager.initialize() 初始化沙箱运行时。
convertToSandboxRuntimeConfig() 把 Claude Code 配置转换成 runtime 能理解的 filesystem / network 限制。
模型发起 Bash 或 PowerShell 工具调用。
shouldUseSandbox(input) 判断这一条命令是否需要进沙箱。
Shell.exec() 调用 SandboxManager.wrapWithSandbox(command)，拿到被包装后的命令字符串。
Node spawn() 启动包装后的命令；OS 沙箱实际拦截越权读写和网络连接。
命令结束后 cleanupAfterCommand() 清理沙箱副作用，并把 sandbox violation 信息回传到工具结果。
用户/模型: Bash({ command: "npm test && curl example.com" })
   ↓
BashTool.call()
   ↓
shouldUseSandbox(input)
   ↓ true
Shell.exec(command, { shouldUseSandbox: true })
   ↓
SandboxManager.wrapWithSandbox(command, binShell)
   ↓
@anthropic-ai/sandbox-runtime 生成平台相关 wrapper
   ↓
spawn(wrapperCommand)
   ↓
文件系统 / 网络访问被 runtime 限制
   ↓

   ↓
tool_result 返回给 Claude

3. 配置怎么变成沙箱规则

sandbox-adapter.ts 里的 convertToSandboxRuntimeConfig() 会收集两类信息：一类来自 settings.sandbox，一类来自普通权限规则，比如 Edit(path)、Read(path)、WebFetch(domain:...)。

它默认允许写当前目录 . 和 Claude 临时目录；额外目录来自 permissions.additionalDirectories 和 Claude.md 相关附加目录。

网络规则会合并 sandbox.network.allowedDomains / deniedDomains，以及 WebFetch(domain:...) 规则，还支持 Unix socket、本地 binding、HTTP/SOCKS proxy 等配置。

4. 哪些东西默认不让写

源码里有几个明显的防逃逸点：禁止写 settings 文件，防止命令偷偷改权限；禁止写 .claude/skills，防止命令植入自动加载的高权限 skill；对裸 git repo 相关的 HEAD、objects、refs、hooks、config 做 deny/scrub，防止利用 git 机制绕过沙箱。

所以它防的不是“模型想不想作恶”，而是“shell 进程即使执行了危险命令，也尽量不能改到权限配置、skills、git 逃逸点、未授权目录”。

5. 一条命令什么时候进沙箱

shouldUseSandbox() 的判断很直接：沙箱必须启用、平台和依赖可用、命令存在、没有被配置为 excluded command。

模型可以传 dangerouslyDisableSandbox: true，但只有 allowUnsandboxedCommands 允许时才会生效。否则企业策略要求沙箱时，不能靠这个字段绕过。

excludedCommands 是用户便利功能，不是安全边界；源码还会拆 compound command，避免 docker ps && curl evil.com 因为前半段命中 excluded 就整体逃出沙箱。

6. 平台和底层实现

这个仓库没有直接把 bubblewrap / sandbox-exec 的完整实现写在源码里，而是通过 @anthropic-ai/sandbox-runtime 委托出去。Claude Code 适配层负责配置转换、初始化、权限提示、清理和 UI 展示。

源码注释能看到支持平台是 macOS、Linux、WSL2；Linux 依赖提示里提到 bubblewrap、socat；PowerShell 在 Linux/macOS/WSL2 可走同一套 wrapper，原生 Windows 不支持该沙箱。

7. 网络权限怎么问用户

如果命令访问未明确允许的网络主机，sandbox runtime 可以触发 ask callback。structuredIO.createSandboxAskCallback() 会把它包装成一个合成工具权限请求：SandboxNetworkAccess。

这样 VS Code、CCR、SDK host 看到的仍然是熟悉的 can_use_tool 权限协议，而不是单独发明一套网络弹窗协议。

8. 为什么沙箱会减少弹窗

bashPermissions.ts 支持 sandbox.autoAllowBashIfSandboxed。含义是：如果命令会在沙箱里跑，并且没有显式 deny/ask 规则拦住，就可以自动允许 Bash。

这不是“完全信任命令”，而是把信任转移成“我允许你跑，但你只能在沙箱授予的目录和网络范围里跑”。

9. 失败后怎么反馈给模型

BashTool.tsx 会用 SandboxManager.annotateStderrWithSandboxFailures() 标注 stderr；结果展示组件会识别 <sandbox_violations> 标签。

Bash prompt 里也专门告诉模型：默认用沙箱；只有用户明确要求，或者命令失败且有证据表明是 sandbox restriction，才考虑 dangerouslyDisableSandbox，并且还要看策略是否允许。

10. 启动和不可用处理

print.ts 启动时会检查 getSandboxUnavailableReason()。如果用户启用了沙箱但平台/依赖不满足，会给出警告；如果设置了 sandbox.failIfUnavailable，则不能静默降级成无沙箱执行。

/sandbox 命令用于查看和配置状态，也能添加 excluded command；企业高优先级配置可以锁定本地设置。

一个具体例子：模型想执行 npm test，测试脚本里某个恶意 postinstall 或测试用例试图写 ~/.ssh/config、改 .claude/settings.local.json、偷偷往 .claude/skills 塞文件、再 curl 到未知域名。没有沙箱时，这些风险主要靠权限弹窗和用户判断；有沙箱时，命令进程本身会被限制在允许写路径和允许网络范围内，越界访问会失败并形成 sandbox violation。Claude Code 再把失败原因回到工具结果里，让模型换方案，比如只改项目内文件、请求用户授权某个域名，或者在策略允许时解释为什么需要非沙箱执行。

最短总结：Claude Code 的沙箱是“命令执行沙箱”，不是“模型沙箱”也不是“整仓库复制容器”。它把 shell 进程包进受限运行时，用 settings / permissions 生成文件系统和网络边界，再把 violation、网络授权、清理、UI 提示接回 Claude Code 的 agent 循环。
