怎么防止 FastApply reward 被 hack

防 reward hacking 的核心不是把某个 reward 权重调到很大，而是做多层验证：文本正确性、结构正确性、语义正确性、执行正确性都要覆盖。

exact 仍然主导。 保持 exact 权重最高，避免 similarity 变成主要目标。
降低低保风险。 validity / tag_format 只能是小分，不能让模型靠格式吃饭。
加入 patch replay 检查。 验证修改点是否真的覆盖 SEARCH/REPLACE hunk。
加入执行验证。 能跑单测就跑单测，能跑 type checker / lint / build 就跑。

训练层防护

  • group 内加入 hard negative：格式正确但漏改、相似度高但错、syntax 过但逻辑错。
  • reward 分项都记录日志，不只看 total reward。
  • 对 judge PASS 的样本抽样人工或规则复核。
  • 不要只在 tiny fixture 上调权重，必须有 held-out repo / held-out patch 类型。

工程层防护

  • 部署时只接受唯一一个 updated 标签块。
  • 标签外有任何文本直接拒绝或降级处理。
  • 多语言 syntax 检查要标记 checked / unchecked，不能把 heuristic 当真 parser。
  • 最终以真实 apply + test pass rate 作为主评估，而不是只看 reward。
一句话：FastApply 的 reward 要防 hack，就不能只看“像不像答案”，还要看“patch 是否真的被应用、代码是否能跑、输出是否能被下游稳定消费”。
