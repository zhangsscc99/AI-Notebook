CT8

Claude Code 的权限机制有几层，操作是怎么一层层通过权限的

我读的是服务器里的 Claude Code 源码：核心链路在 src/services/tools/toolExecution.ts、src/utils/permissions/permissions.ts、src/hooks/useCanUseTool.tsx。结论先说：Claude Code 的权限不是一个简单 if，而是工具执行前的多级闸门。

怎么数层？如果只数“真正决定能不能执行 tool.call() 的执行前闸门”，可以记成 8 层。如果把“工具是否暴露给模型”和“执行后审计/Hook”也算进完整生命周期，就是 10 个阶段。
工具暴露层：会话组装工具池时先决定模型能看到哪些工具 schema。看不到的工具，模型通常就不会发起对应 tool_use。
Schema 层：checkPermissionsAndCallTool() 先执行 tool.inputSchema.safeParse(input)。字段名、类型、未知字段不对，直接返回 InputValidationError，还没进入权限判断。
工具语义校验层：每个工具自己的 validateInput() 检查业务前提，例如 Edit 的 old_string 不能等于 new_string、文件不能太大、Write/Edit 不能写入被 deny 的目录。
PreToolUse Hook 层：runPreToolUseHooks() 可以追加上下文、修改输入、阻止继续，甚至给出 hook permission result。随后 resolveHookPermissionDecision() 把 Hook 决策合并进正常权限流。
工具专属权限层：tool.checkPermissions()。Bash 会解析命令、拆 subcommand、检查 deny/ask/allow 规则、路径约束、注入风险、sandbox auto allow；Read/Edit/Write 会走读写路径规则、工作目录、敏感文件检查。
通用规则层：hasPermissionsToUseToolInner() 统一处理整工具 deny、整工具 ask、工具专属结果、bypass 免疫的 safety check、allow rules。核心返回只有三种：allow、deny、ask。
权限模式层：default、acceptEdits、plan、dontAsk、bypassPermissions、内部 auto 改变 ask/allow 的策略。例如 dontAsk 会把 ask 转 deny；bypassPermissions 也不能绕过显式 deny 和安全检查。
自动化增强层：auto mode / Bash classifier / speculative classifier / sandbox auto allow / denial tracking。它们用于减少弹窗，但高风险 safety check、PowerShell 等场景仍会保守地要求显式批准或拒绝。
决策执行层：useCanUseTool() 处理 allow/deny/ask。allow 才进入 tool.call()；deny 或未批准的 ask 会生成 error tool_result；ask 可能进入本地交互、Bridge、Channel、Coordinator、Swarm worker leader approval。
执行后层：工具执行成功/失败后还有 PostToolUse、failure hook、PermissionDenied hook、telemetry。这不是执行前授权，但属于完整安全生命周期。

源码里的主入口

toolExecution.ts 的 checkPermissionsAndCallTool() 是工具调用总门卫：先 schema，再 validateInput()，再 PreToolUse，之后调用 canUseTool，最后只有 permissionDecision.behavior === 'allow' 才会继续执行工具。

真正的权限判断函数

permissions.ts 的 hasPermissionsToUseToolInner() 做规则优先级：deny 最前；整工具 ask 次之；工具自己的 checkPermissions() 再判断内容级规则；safety check 对 bypass 免疫；然后才看 bypass / allow rule；最后 passthrough 变成 ask。

ask 不是一个结果，而是一组审批通道

useCanUseTool.tsx 收到 ask 后，会按上下文选择处理器：coordinator worker 先跑自动检查；swarm worker 可以把权限请求通过 mailbox 发给 leader；主交互路径会进入 handleInteractivePermission()，本地 UI、CCR bridge、外部 channel、PermissionRequest hook、Bash classifier 谁先决策谁赢。

权限规则从哪里来

规则源包括 userSettings、projectSettings、localSettings、flagSettings、policySettings、cliArg、command、session。用户点“本次允许 / 总是允许”时，本质是在生成 PermissionUpdate 并写回对应目的地。

// src/services/tools/toolExecution.ts，简化后的执行前主链路
const parsedInput = tool.inputSchema.safeParse(input)
if (!parsedInput.success) return InputValidationError

const valid = await tool.validateInput?.(parsedInput.data, context)
if (valid?.result === false) return tool_result_error

for await (const r of runPreToolUseHooks(context, tool, parsedInput.data, toolUseID)) {
  // hook 可以 stop、追加上下文、更新 input、返回 hookPermissionResult
}

const resolved = await resolveHookPermissionDecision(
  hookPermissionResult,
  tool,
  processedInput,
  context,
  canUseTool,
  assistantMessage,
  toolUseID,
)

if (resolved.decision.behavior !== 'allow') {
  return permission_denied_tool_result
}

return await tool.call(resolved.input, context)
// src/utils/permissions/permissions.ts，简化后的权限优先级
if (denyRuleForWholeTool) return deny
if (askRuleForWholeTool && !sandboxAutoAllow) return ask

const toolPermissionResult = await tool.checkPermissions(parsedInput, context)
if (toolPermissionResult.behavior === 'deny') return deny
if (tool.requiresUserInteraction?.() && toolPermissionResult.behavior === 'ask') return ask
if (contentAskRule || safetyCheck) return ask   // bypass 也不能绕过

if (mode === 'bypassPermissions') return allow
if (alwaysAllowedRule) return allow

return toolPermissionResult.behavior === 'passthrough'
  ? ask
  : toolPermissionResult

案例 1：Bash(rm -rf build) 怎么过权限

Schema：确认 input 有 command 字符串；模型如果传错字段，直接失败。
PreToolUse：项目 Hook 可以先拦截或改写命令。
Bash 专属检查：bashToolHasPermission() 解析 AST / legacy parser，检查命令注入、operator、subcommand、输出重定向、cd + git 这类特殊风险。
规则匹配：如果有 Bash(rm:*) deny，直接 deny；如果 ask，则进入审批；如果 allow 且没有更高优先级风险，才可能放行。
自动化：开启 sandbox auto allow 时，沙箱内命令可以减少确认；但显式 deny/ask 仍优先，复杂或危险命令仍会问。
最后决策：ask 进入 UI / bridge / channel / swarm leader；用户允许后可能生成 session 或 settings 规则，下次同类命令可直接通过。

案例 2：Edit 文件怎么过权限

Schema + validateInput：检查 file_path、old_string、new_string；拒绝 old/new 一样、超大文件、密钥写入、被 deny 的路径。
读前置状态：Edit/Write 还会依赖 readFileState，避免模型没读过文件或基于旧 mtime 覆盖用户新改动。
写权限：checkWritePermissionForTool() 先查 edit deny；再查 internal editable path；再做 .claude、.git、shell config、Windows 可疑路径等 safety check。
工作目录与规则：acceptEdits 且路径在 allowed working dir 内可自动 allow；否则看 edit allow/ask rule；没有规则就 ask。
执行：只有 allow 后才真正写磁盘；写完会更新 readFileState，否则返回拒绝信息给模型重新规划。

为什么要这么多层

不同层防的问题不同：Schema 防模型参数乱写；validateInput 防明显业务错误；Hook 给企业/项目策略插入口；工具专属权限懂 Bash/File 的真实风险；通用规则保证用户设置统一生效；模式层决定交互策略；classifier/sandbox 降低频繁确认；审批层把最终控制权交给人或上级 agent。

最容易误解的点

bypassPermissions 不是“所有安全都关闭”。源码在 deny、工具专属 deny、content ask rule、safety check 之后才处理 bypass，所以显式 deny 和部分安全检查仍然比 bypass 更高优先级。

最短记忆法：Claude Code 权限链路 = 先挡格式，再挡业务，再过 Hook，再问工具自己，再过全局规则和模式，最后进入人/自动化审批；只有 allow 才能 tool.call()。
