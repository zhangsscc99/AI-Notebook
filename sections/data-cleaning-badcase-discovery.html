badcase 是怎么找到的，项目里提供了哪些技巧技术

Data-Juicer 里 badcase 发现主要体现在 Agent 交互数据质量分析这条 demo pipeline：demos/agent/agent_interaction_quality_analysis.yaml。它不是只靠一个“用户不满意”标签，而是把工具调用、token 成本、延迟、LLM 质量评分、对话质量、轨迹连贯性等多源信号融合成一个保守的 badcase tier。

一句话：badcase 是通过“规范化 Agent 轨迹 → 统计工具/成本/质量信号 → 多个 LLM/规则质检算子打分 → agent_bad_case_signal_mapper 融合信号 → high_precision/watchlist/none 分层 → 报告和切片脚本辅助人工复核”找到的。

1. 先把 Agent 数据规范化，否则 badcase 会误判

Agent 数据不是普通问答，经常是：

user
  → assistant(tool_calls)
  → tool
  → assistant
  → tool
  → assistant final

agent_dialog_normalize_mapper 会把 messages / choices 规范化成 text、dialog_history、query、response，还会写入血缘字段，例如 agent_request_model、agent_pt、agent_total_cost_time_ms。

这一步很关键。否则下游 LLM 评估可能只看到最后一小段 assistant 文本，误以为模型“没干活”或“答非所问”。

2. badcase 信号来源有哪些

工具调用失败

tool_success_tagger_mapper 统计 tool_success_count、tool_fail_count、tool_success_ratio。如果工具返回 error、No such file、失败模式，就会成为强证据或中等证据。

token 成本和延迟异常

usage_counter_mapper 统计 prompt/completion/total tokens；normalize 写入 total_cost_time。过高 token 或过高 latency 会成为 watchlist 信号，特别适合发现“绕圈、冗长、成本爆炸”的样本。

LLM 综合质量低

llm_analysis_filter 和 llm_quality_score_filter 产生分数和 recommendation。如果是低分并且 recommendation 是 discard，会触发 llm_agent_analysis_eval_low 或 llm_reply_quality_eval_low。

对话/轨迹质量低

多个 dialog/agent mapper 会给 1–5 分：记忆一致性、指代消解、话题漂移、错误恢复、澄清质量、主动性、非重复性、轨迹连贯性、工具任务相关性。低分轴会触发 dialog_turn_quality_meta_low。

负面情绪和用户不满

dialog_sentiment_detection_mapper 可以提供负面情绪标签。但项目文档强调不强依赖用户不满意单一视角，因为这类信号噪声大，只适合作为弱证据。

高困惑度和长 query 短回复

可选用 perplexity_filter 的 stats.perplexity，也有“长 query + 极短 response”的启发式，用于发现乱码、异常回复、空回复、敷衍回复。

3. agent_bad_case_signal_mapper 怎么融合信号

核心源码是 data_juicer/ops/mapper/agent_bad_case_signal_mapper.py。它读取上游写入的 meta 和 stats，输出两个字段：

meta.agent_bad_case_signals = [
  {"code": "tool_message_error_pattern", "detail": "tool_fail_count=2", "weight": "high"},
  {"code": "high_token_usage", "detail": "total_tokens=...", "weight": "medium"}
]

meta.agent_bad_case_tier = "high_precision" | "watchlist" | "none"

它的设计目标是 precision over recall：强怀疑档宁可少抓一点，也要证据更硬。默认逻辑大概是：

  • high_precision：工具失败强证据，或 LLM 低分且 discard 的强证据。
  • watchlist：中等证据达到数量，或单个中等证据需要观察。
  • none：没有明显坏样本信号。

4. 项目提供的具体 badcase 技巧

技巧 1：硬证据优先

优先看工具 error pattern、tool fail count、LLM discard + 极低分。这些比“用户语气不爽”更可靠。

技巧 2：单次工具失败不要立刻判死

Agent 常常先试错再修正，所以配置里有 min_tool_fail_count_for_signal、high_precision_on_tool_fail_alone，避免把探索性失败误判成坏样本。

技巧 3：多弱证据 AND 更稳

文档建议优先组合多条独立证据，例如低工具成功率 + 高 token + 低对话质量，而不是单一弱信号就判坏。

技巧 4：P90/P95 分位数自动校准

compute_percentile_thresholds.py 可以按 agent_request_model 计算 token、延迟、perplexity 的 P90/P95，并写成 calibration JSON，供 agent_bad_case_signal_mapper 自动合并阈值。

技巧 5：按模型/时间桶 cohort 对比

normalize 写入 agent_request_model 和 agent_pt，后处理脚本 analyze_bad_case_cohorts.py 可以按模型、时间桶、tier 汇总，定位哪个模型或版本 badcase 比例异常。

技巧 6：slice 出高优先级样本人工复核

slice_export_by_tier.py 可以导出 high_precision 或 watchlist 子集，给人工复核或二次标注。

技巧 7：HTML 报告和字段归因

generate_bad_case_report.py 会生成单页 HTML，展示 tier、信号、字段归因表、cohort 图、case study，帮助你从“发现坏样本”走到“解释为什么坏”。

技巧 8：LLM insight 只跑高风险样本

agent_insight_llm_mapper 可选地只对 high_precision / watchlist 样本跑 LLM 总结，输出 root causes、human review priority、viz facets，控制成本。

5. 一条 badcase 发现流程怎么跑

原始 Agent JSONL
  → agent_dialog_normalize_mapper 规范化 messages / choices
  → pii_redaction_mapper / pii_llm_suspect_mapper 脱敏与隐私检查
  → clean_html_mapper / clean_copyright_mapper 基础清洗
  → dialog_* mapper 做意图、情绪、话题、质量打分
  → usage_counter_mapper 统计 token
  → tool_success_tagger_mapper 统计工具成功/失败
  → llm_analysis_filter / llm_quality_score_filter 打质量分
  → agent_bad_case_signal_mapper 融合信号并分层
  → agent_insight_llm_mapper 可选生成根因洞察
  → verify / compute_percentile / cohort / slice / HTML report 后处理

6. 它能发现哪些典型 badcase

  • 工具失败型：工具多次报错、路径不存在、API 调用失败、工具成功率过低。
  • 空回复/敷衍型：用户 query 很长，但最终 response 极短或为空。
  • 成本异常型：token 使用异常高、延迟异常高，可能是循环调用或冗长推理。
  • 质量低型：LLM 评分低且建议 discard。
  • 对话能力差型：记忆不一致、指代没解析、话题漂移、错误恢复差、主动性差、重复啰嗦。
  • 工具不相关型：工具调用和用户任务不匹配，Agent 看似行动了但方向错。
  • 安全/隐私型：PII 残留、敏感信息疑似泄露、NSFW/水印等多模态安全问题。
结论：Data-Juicer 找 badcase 的关键不是一个神奇模型，而是多源信号工程：规则信号抓硬错误，LLM/VLM 信号抓语义质量，分位数校准抓异常成本，cohort 分析抓模型/版本漂移，HTML 报告帮助人工复核。
