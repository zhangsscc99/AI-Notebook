详解 Claude Code 的 query.ts 主循环文件

src/query.ts 是 Claude Code 最核心的 agent runtime 文件。它不是 UI 层，也不是单个工具实现，而是把消息上下文、模型流式调用、tool_use 解析、工具执行、压缩恢复、stop hook、附件注入、下一轮递归串起来的主循环。

一句话：query.ts 的核心是一个 async generator + while(true) 状态机：每轮把消息整理成可发给 Claude 的上下文，调用模型流式产出；如果没有工具调用就收尾返回，如果有工具调用就执行工具、把 tool_result 追加进 messages，然后更新 state 进入下一轮。
query(params)
  -> queryLoop(params)
      while true:
        1. 从 State 取 messages / toolUseContext / compact 状态
        2. 构造 messagesForQuery
        3. 执行 tool-result budget / snip / microcompact / context collapse / autocompact
        4. deps.callModel(...) 流式调用 Claude
        5. 收集 assistantMessages 和 toolUseBlocks
        6. 如果没有 tool_use: stop hooks / token budget / completed
        7. 如果有 tool_use: runTools 或 StreamingToolExecutor
        8. 注入 attachments / memory / skills / queued commands
        9. state.messages = old + assistant + tool_results
       10. continue 下一轮

1. query() 是 async generator，不是普通函数

query() 返回的是 AsyncGenerator。这意味着它一边运行一边 yield 事件：stream start、assistant message、tool result、attachment、tombstone、tool summary 等。外层 QueryEngine / SDK / UI 不是等它全部结束才拿结果，而是边跑边消费这些事件。

query() 自己只是薄包装：创建 consumedCommandUuids，把真正工作交给 queryLoop()，正常结束后通知 command lifecycle completed。

2. State 是主循环的内存寄存器

State 保存跨轮状态：messages、toolUseContext、auto compact 状态、max output recovery 次数、是否尝试过 reactive compact、pending tool summary、stop hook 状态、turnCount、上一轮 transition。

每个 continue 分支不会到处改散变量，而是构造一个新的 state = next。这让主循环看起来像一个显式状态机：不同异常/恢复路径只是把 state 改成不同 transition，然后回到 while 顶部。

3. 每轮开始先做上下文整理

主循环不是直接把全量历史塞给模型。它先取 getMessagesAfterCompactBoundary(messages)，再按顺序处理几类上下文压力：

  • tool result budget：大工具结果可能被替换成引用，避免单条 tool result 过大。
  • snip compact：按 feature flag 裁剪历史。
  • microcompact：更小粒度地压缩或编辑缓存。
  • context collapse：把可折叠上下文投影成更短视图。
  • autocompact：真正超上下文风险时生成 summary messages。

所以 query loop 的第一职责其实是维持模型可继续推理的上下文窗口。

4. callModel 是模型流式输出入口

整理完上下文后，它调用 deps.callModel(...)。传进去的不只是 messages，还有 system prompt、thinkingConfig、tools、abort signal、当前模型、fallbackModel、MCP tools、agent definitions、taskBudget、queryTracking 等。

模型返回是流式的：每来一个 message 就处理一次。如果是 assistant message，就扫描 content 里的 tool_use block，追加到 toolUseBlocks，并把 needsFollowUp 标成 true。

5. 为什么不用 stop_reason 判断是否有工具

源码注释明确说 stop_reason === 'tool_use' 不可靠。所以主循环真正的退出信号不是 stop_reason，而是：流式过程中有没有看到 tool_use block。

const toolUseBlocks: ToolUseBlock[] = []
let needsFollowUp = false

if assistant content has tool_use:
  toolUseBlocks.push(...)
  needsFollowUp = true

if !needsFollowUp:
  finish current turn
else:
  execute tools and continue

这是理解 Claude Code agent loop 的关键：它按内容块判断下一步，不依赖 provider 的 stop_reason 字段。

6. StreamingToolExecutor：边生成边执行工具

如果 streamingToolExecution gate 打开，query loop 会创建 StreamingToolExecutor。当流式 assistant message 中刚出现 tool_use block，它就可以 addTool()，并在模型还没完全结束时收集已完成结果。

这能降低延迟：比如模型连续生成多个只读工具调用，系统不必等整段 assistant 输出结束才开始执行。关闭时则走传统 runTools(toolUseBlocks, assistantMessages, ...)。

7. 没有 tool_use 时怎么收尾

如果 needsFollowUp 为 false，说明模型已经给出了最终回答或 API 错误。此时主循环会依次处理：

  • prompt too long / media too large 的 reactive compact 恢复。
  • max_output_tokens 的升级重试或续写恢复。
  • API error 时跳过 stop hooks，避免错误循环。
  • handleStopHooks()，如果 hook 阻止继续或返回 blocking error，就停止或带着错误继续一轮。
  • token budget continuation：如果预算策略要求继续，就注入 meta user message 再跑一轮。
  • 最终 return { reason: 'completed' }。

8. 有 tool_use 时怎么执行工具

如果有 tool_use，query loop 进入工具执行段。它选择：

const toolUpdates = streamingToolExecutor
  ? streamingToolExecutor.getRemainingResults()
  : runTools(toolUseBlocks, assistantMessages, canUseTool, toolUseContext)

每个工具 update 可能包含 message 和 newContext。message 会被 yield 给外层，同时用 normalizeMessagesForAPI() 转成 API 需要的 user/tool_result 形态，加入 toolResults。newContext 则更新 toolUseContext，例如工具执行后改变 readFileState、权限状态、MCP/tool 状态等。

9. 工具后为什么还要注入 attachments

工具执行完后，Claude Code 还会把一些“非模型直接请求但对下一轮有用”的信息作为 attachment 放进下一轮上下文：

  • queued commands / task notifications：主线程只消费发给主线程的，subagent 只消费发给自己的。
  • memory prefetch：如果后台 memory 检索已经完成，就注入相关 memory attachment。
  • skill discovery prefetch：如果发现相关 skill，就注入 skill attachment。
  • file change attachment：记录 edited_text_file 这类文件变化。

这层设计说明 query loop 不只是“模型→工具→模型”，它还负责把运行时事件合并成下一轮可见上下文。

10. 下一轮递归其实是更新 state 后 continue

源码里有 queryCheckpoint('query_recursive_call')，但不是函数递归调用自己，而是构造新的 State：

state = {
  messages: [...messagesForQuery, ...assistantMessages, ...toolResults],
  toolUseContext: toolUseContextWithQueryTracking,
  turnCount: nextTurnCount,
  transition: { reason: 'next_turn' },
  ...recoveryState
}

然后回到 while(true) 顶部。也就是说，“递归”在工程上是状态机循环，不是调用栈递归。

11. query.ts 处理了哪些异常恢复

这个文件很长，主要因为它把大量生产级恢复路径放进主循环：

  • 模型 fallback：流式中触发 fallback 时 tombstone 掉孤儿 assistant messages，丢弃旧工具结果，切 fallback model 重试。
  • prompt too long：先尝试 context collapse drain，再 reactive compact；仍失败才把错误暴露出去。
  • max_output_tokens：先尝试提高 max output token，再最多做几次 resume continuation。
  • abort：如果用户中断，要为已经发出的 tool_use 生成缺失 tool_result 或 interruption message，避免 API 消息结构不闭合。
  • maxTurns：超过最大轮数时返回 max_turns，并发出 attachment。

12. query.ts 和 QueryEngine 的边界

QueryEngine 更像“会话外壳”：接收用户输入、初始化工具/MCP/skills/permissions、维护 transcript 和 SDK 输出。query.ts 更像“单次 agent turn 的发动机”：拿到已经准备好的 params 后，负责跑到 completed / aborted / max_turns / prompt_too_long 等 terminal reason。

所以读源码时不要把它们混在一起：QueryEngine 管生命周期，query.ts 管模型-工具闭环。

入口：query(params) 创建 command lifecycle 跟踪，然后委托给 queryLoop()。
状态：State 保存 messages、toolUseContext、压缩/恢复/turn 计数。
上下文：从 compact boundary 后取消息，做 tool result budget、snip、microcompact、collapse、autocompact。
模型：deps.callModel() 流式产出 assistant messages，发现 tool_use 就收集。
分叉：没有 tool_use 就 stop hooks / token budget / completed；有 tool_use 就执行工具。
工具：StreamingToolExecutor 或 runTools 执行，结果转成 user tool_result。
补充上下文：注入 queued commands、memory prefetch、skill discovery、file change attachment。
继续：更新 state.messages 和 turnCount，回到 while 顶部。
最小心智模型：

messages/state
  -> prepare context window
  -> call Claude with tools
  -> stream assistant blocks
  -> if no tool_use:
       stop hooks / recovery / completed
     else:
       execute tool_use
       normalize tool_result as user message
       inject runtime attachments
       update state
       loop again

query.ts 的本质：
  production-grade ReAct loop
  + streaming events
  + context compaction
  + tool orchestration handoff
  + recovery state machine
  + attachment/memory/skill injection
  + terminal reason return
最重要的结论：Claude Code 的 query.ts 不是“调用模型的函数”，而是完整的 agent 主循环状态机。 它把模型输出的 tool_use 当成控制流，把工具结果当成下一轮 user message，把压缩、恢复、hook、中断、附件注入都纳入同一个 while loop，这就是 Claude Code 工作流编排的核心。
