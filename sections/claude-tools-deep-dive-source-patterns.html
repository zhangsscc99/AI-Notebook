Claude Code 十几个工具源码详解：怎么写、怎么优化

先给结论：Claude Code 的工具不是一堆随手写的函数，而是一组遵守同一接口的协议对象。每个工具都要声明 name、inputSchema、call()、validateInput()、checkPermissions()、mapToolResultToToolResultBlockParam()、是否只读、是否可并发、是否延迟加载等。这样主循环可以统一调度、统一校验、统一权限、统一把结果塞回下一轮模型。

一句话：Claude Code 写工具的核心套路是：强 schema 控输入，validateInput 防低级错，checkPermissions 防越权，call 做真实动作，mapToolResult 把结果变成模型可继续推理的 tool_result。

源码里的统一工具接口大概长这样：

// src/Tool.ts，简化版
export type Tool = {
  name: string
  inputSchema: z.ZodType
  call(args, context, canUseTool, parentMessage, onProgress?): Promise<ToolResult>
  validateInput?(input, context): Promise<ValidationResult>
  checkPermissions(input, context): Promise<PermissionResult>
  isConcurrencySafe(input): boolean
  isReadOnly(input): boolean
  shouldDefer?: boolean
  searchHint?: string
  maxResultSizeChars: number
  mapToolResultToToolResultBlockParam(output, toolUseID): ToolResultBlockParam
}

下面挑十几个关键工具，按“源码位置 → 怎么写的 → 优化窍门”来记。

1. Read / FileReadTool：读文件、图片、PDF、notebook

源码：src/tools/FileReadTool/FileReadTool.ts。输入是 file_path、offset、limit、pages。输出用 discriminated union 区分 text / image / notebook / pdf / file_unchanged。

窍门：它是只读、可并发工具，maxResultSizeChars = Infinity，因为 Read 自己已经按 token/size 限制输出；再把大结果持久化成文件会形成“Read 读出文件路径再 Read”的循环。

2. Edit / FileEditTool：精确替换，而不是模糊 patch

源码：src/tools/FileEditTool/FileEditTool.ts。输入通常是 file_path、old_string、new_string、replace_all。

窍门：先要求 Read，再校验 mtime，避免模型基于过期内容改文件；old_string 必须能唯一命中，否则返回错误让模型补更多上下文。它还处理 quote normalization、超大文件限制、notebook 改用 NotebookEdit、settings 文件安全校验。

3. Write / FileWriteTool：创建或覆盖文件

源码：src/tools/FileWriteTool/FileWriteTool.ts。输入是绝对路径和完整 content；输出包括 create/update、原文件、structuredPatch、gitDiff。

窍门：对已存在文件仍要求先 Read，并检查 read timestamp，防止覆盖用户或 linter 刚改过的内容。源码里还复用 stat 结果，避免重复 filesystem call。

4. NotebookEdit：notebook 专用编辑

源码：src/tools/NotebookEditTool/NotebookEditTool.ts。它把 notebook 当 JSON 结构处理，支持 replace / insert / delete cell。

窍门：普通 Edit 遇到 .ipynb 会拒绝，提示用 NotebookEdit。NotebookEdit 也要求 Read-before-Edit 和 mtime 校验，避免 notebook JSON 被盲改。

5. BashTool：shell 执行器，但带语义安全层

源码：src/tools/BashTool/BashTool.tsx、bashPermissions.ts、shouldUseSandbox.ts。它不是直接 spawn(command) 就完事，而是做 read-only 判断、权限、sandbox、后台任务、进度输出、结果截断和 git 操作跟踪。

窍门：isConcurrencySafe() 只在命令被判定只读时返回 true；复合命令会拆成子命令做 hook matcher，避免 ls && git push 绕过 Bash(git *) hook。

6. GrepTool：ripgrep 包装器

源码：src/tools/GrepTool/GrepTool.ts。输入支持 pattern、path、glob、type、output_mode、上下文行、head_limit、offset、multiline。

窍门：默认排除 .git/.svn/.hg/.jj 等 VCS 目录，限制 max columns，默认 head_limit=250，避免一次 grep 把上下文塞爆。结果路径会相对 cwd，省 token。

7. GlobTool：按文件名找文件

源码：src/tools/GlobTool/GlobTool.ts。输入是 pattern 和可选 path，输出 filenames、durationMs、numFiles、truncated。

窍门：默认最多 100 个结果；只读、可并发；路径不存在会返回带 cwd suggestion 的错误，让模型自己修正路径，而不是直接崩。

8. LSPTool：代码智能查询

源码：src/tools/LSPTool/LSPTool.ts。它支持 definitions、references、symbols、hover 等 LSP 操作，只有 isLspConnected() 时才启用。

窍门：调用前等待 LSP 初始化；文件太大直接返回“too large”；调用 LSP 前确保文件 didOpen。它是 shouldDefer 工具，避免把复杂 schema 过早塞进首轮 prompt。

// BashTool 关键优化，简化版
isConcurrencySafe(input) {
  return this.isReadOnly?.(input) ?? false
}
preparePermissionMatcher({ command }) {
  const parsed = await parseForSecurity(command)
  if (parsed.kind !== 'simple') return () => true // 复杂命令 fail-safe
  const subcommands = parsed.commands.map(c => c.argv.join(' '))
  return pattern => subcommands.some(cmd => matchWildcardPattern(pattern, cmd))
}

9. ToolSearchTool：工具太多时的“工具发现器”

源码：src/tools/ToolSearchTool/ToolSearchTool.ts。当工具过多或 MCP 工具 deferred 时，模型先调用 ToolSearch，返回 tool_reference，再加载真正工具 schema。

窍门：它支持 select:Read,Edit 直选，也支持关键词打分。优化目标不是“替模型选最终工具”，而是减少首轮 prompt 里的工具 schema 体积，保护 prompt cache。

10. AgentTool：启动子 agent / teammate

源码：src/tools/AgentTool/AgentTool.tsx。它会根据 agent definitions、MCP requirements、permission rules 过滤可用 agent；支持普通 subagent、fork subagent、background、team teammate。

窍门：源码里有递归 fork guard、teammate 不能再 spawn teammate、in-process teammate 不能开 background agent 等限制。不是“无限套娃”，而是受团队结构和生命周期约束。

11. SendMessageTool：Agent Team 的消息工具

源码：src/tools/SendMessageTool/SendMessageTool.ts。它给 teammate 发消息，支持 plain message、broadcast、shutdown_request、plan_approval_response 等结构化消息。

窍门：plain message 要求 summary；cross-machine bridge 必须显式 ask，且不允许 structured message 跨 session。目标 agent 如果 stopped，可以从 transcript 自动 resume。

12. TodoWrite / TaskCreate / TaskList：计划状态工具

源码：TodoWriteTool.ts 和 TaskCreateTool.ts、TaskListTool.ts。旧版 TodoWrite 直接更新 appState.todos；TodoV2 用任务表 create/list/update/get。

窍门：TodoWrite 在 3 个以上任务全部完成且没有验证项时，会注入 verification nudge，防止模型刚完成 todo 就草率总结。TaskCreate 还会跑 task-created hooks，hook 阻断则回滚创建。

13. WebFetchTool：抓 URL 并转 Markdown

源码：src/tools/WebFetchTool/WebFetchTool.ts。它校验 URL，按 hostname 做权限规则，预批准 host 可直接 allow，抓取后提取 Markdown。

窍门：遇到 redirect 不直接偷偷跟跳，而是返回“请用新 URL 再调一次”的 tool_result；prompt 里固定加入“私有/认证 URL 会失败，优先找 MCP”的提醒，避免 ToolSearch 开关导致 prompt cache 抖动。

14. WebSearchTool：服务端 web search 包装

源码：src/tools/WebSearchTool/WebSearchTool.ts。它根据 provider / model 判断是否启用，然后内部发起一次模型调用，并挂一个 web_search tool schema。

窍门：有 feature flag 时可用小快模型做搜索；它流式解析 server_tool_use 进度，但 UI 搜索结果不直接进入 transcript search，避免“屏幕上没显示却被索引”的 phantom match。

15. SkillTool：把技能变成工具调用

源码：src/tools/SkillTool/SkillTool.ts。输入只是 skill 名和可选 args；validate 阶段确认 skill 存在、不是 disableModelInvocation、类型是 prompt。

窍门：skill 可以 inline 展开成下一轮 prompt，也可以 context: fork 跑成 forked sub-agent。源码还记录 skill usage，给后续排序/推荐用。

16. MCPTool / MCP resources：外部工具接入壳

源码：src/tools/MCPTool/MCPTool.ts、ListMcpResourcesTool、ReadMcpResourceTool。基础 MCPTool 是模板，真实 name、description、schema、call 会在 MCP client 连接后按服务端工具覆盖。

窍门：MCP 权限默认 passthrough，交给统一权限系统处理；MCP 工具会和 built-in tools 在 assembleToolPool() 合并、过滤、按名称排序，并用 built-in 优先去重。

从这些工具可以总结出 Claude Code 写工具的工程窍门：

工具 schema 要窄。优先 z.strictObject，不要让模型传任意参数；参数错就返回可读错误，让下一轮模型修。
读写分离。Read/Grep/Glob/LSP/WebFetch/WebSearch 标成 read-only + concurrency safe；Edit/Write/Bash 这类风险操作默认串行或受权限控制。
写文件必须防 stale。Read-before-Edit、mtime、唯一 old_string、文件大小限制、UNC 路径保护，是避免数据损坏的关键。
结果要控 token。Grep 默认 head_limit，Glob 默认 100，Bash 大输出持久化并只给 preview，Read 用 offset/limit。
工具太多要 deferred。ToolSearch + shouldDefer 让首轮 prompt 不被 MCP/LSP/Web 工具 schema 淹没。
权限和 hook matcher 要能解释。每个工具实现 getPath、preparePermissionMatcher、toAutoClassifierInput，让权限系统、hooks、auto classifier 都能理解这个动作。
// 写一个 Claude Code 风格工具的骨架
export const MyTool = buildTool({
  name: 'my_tool',
  searchHint: 'short capability phrase',
  maxResultSizeChars: 100_000,
  shouldDefer: true,              // schema 大或低频工具建议 deferred
  strict: true,
  get inputSchema() { return z.strictObject({ path: z.string() }) },
  isReadOnly() { return true },
  isConcurrencySafe() { return true },
  async validateInput(input, context) { /* 低级错误、路径、大小、状态 */ },
  async checkPermissions(input, context) { /* allow / ask / deny */ },
  async call(input, context, canUseTool, parentMessage, onProgress) {
    return { data: await doWork(input) }
  },
  mapToolResultToToolResultBlockParam(output, toolUseID) {
    return { type: 'tool_result', tool_use_id: toolUseID, content: serialize(output) }
  }
})
最短记法：Claude Code 的好工具 = schema 小而硬、执行前校验足、权限边界清楚、结果可压缩、错误可回传、只读工具可并发、重工具 deferred。这就是它工具系统稳定的主要原因。
