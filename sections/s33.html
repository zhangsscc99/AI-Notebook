search 如何映射回原始 Markdown

核心机制是：索引里的每个 chunk 都保留了原始 Markdown 文件坐标。RAG 找到的不是一段“失去来源的向量文本”，而是一条带 path、startLine、endLine 的搜索结果。模型拿到这些字段后，就能构造 memory_get 调用去读原始 Markdown。

sync 阶段读取 MEMORY.md / memory/*.md，生成 file entry：包含绝对路径、相对路径、hash、mtime、size。
chunking 阶段把文件切块，每个 chunk 记录 startLine、endLine、text、hash。
写索引时，builtin 后端把这些坐标写进 chunks 表，也同步写进 chunks_fts 和可选 chunks_vec。
search 阶段无论命中 FTS 还是 vector，SQL 都会取回 path、start_line、end_line、text。
memory_search 输出 JSON，把这些字段交给模型：path、startLine、endLine、snippet、score。
模型如果需要更多上下文，就用这些坐标构造 memory_get({ path, from, lines })。

builtin 后端的数据链路可以简化成：

Markdown file: memory/2026-05-13.md
  line 40..65
    ↓ chunkMarkdown()
chunk {
  path: "memory/2026-05-13.md",
  startLine: 40,
  endLine: 65,
  text: "...",
  hash: "..."
}
    ↓ writeChunks()
SQLite chunks / chunks_fts / chunks_vec
    ↓ memory_search()
result {
  path: "memory/2026-05-13.md",
  startLine: 40,
  endLine: 65,
  snippet: "...",
  score: 0.82
}
    ↓ model decides to verify
memory_get({
  path: "memory/2026-05-13.md",
  from: 36,
  lines: 45
})

模型怎么“知道”下一步调 get

工具结果本身给了可读坐标；memory_get 工具描述又说明它是安全读取 memory 文件 excerpt 的工具。所以模型可以把 search result 的 path/startLine/endLine 直接转成 get 参数。

OpenClaw 是否硬编码自动连调

通常不是后端强制自动“search 后立刻 get”。后端负责提供结构化 search 结果和 get 工具。是否继续 get 是模型根据任务判断；但对于需要准确性的回答，正确行为就是 search 后 get。

QMD 怎么映射

QMD 返回 docid / collection / file 等信息。QmdMemoryManager 会把它解析成 doc.rel，如果文件在 workspace 内就返回正常相对路径；如果在 extra collection 里，就返回 qmd/<collection>/... 虚拟路径，保证 search → readFile 能 roundtrip。

为什么不是直接读全文

因为 search result 已经有定位信息，读全文通常浪费 token。更稳的做法是从命中行附近扩展读取，比如 from = startLine - 5、lines = 40。

一句话：索引不是只存 embedding；它还存“这个 embedding 来自哪个 Markdown 文件的哪几行”。RAG 命中后，模型拿到 path + line range，再用 memory_get 回读 Markdown 原文。
