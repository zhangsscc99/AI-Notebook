Claude Code 的记忆用了 RAG 吗，什么索引方式，用了什么 embedding 模型

结论：Claude Code 的记忆不是传统 embedding + vector DB 的 RAG。更准确地说，它是文件型记忆 + Markdown 索引 + 轻量检索/LLM 选择器 + 上下文注入。源码里没有看到给记忆建立向量库、调用 embedding 模型、做 ANN 相似度搜索或 reranker 的主路径。

一句话：Claude Code 有 RAG-like 的“从外部记忆取回再塞进上下文”，但检索方式不是向量检索；核心索引是 CLAUDE.md 层级、MEMORY.md 人写/模型维护的 Markdown 目录、memory 文件 frontmatter manifest，再用 Claude/Sonnet 做相关记忆选择。

1. CLAUDE.md：确定性加载，不是 RAG

src/utils/claudemd.ts 的 getMemoryFiles() 会按顺序加载 Managed、User、Project、Local 记忆文件：例如 /etc/claude-code/CLAUDE.md、~/.claude/CLAUDE.md、项目里的 CLAUDE.md、.claude/CLAUDE.md、.claude/rules/*.md、CLAUDE.local.md。

这一步不是“搜索最相关文档”，而是按目录层级和优先级直接注入指令。它支持 @include，但 include 也是路径解析，不是 embedding 检索。

2. Auto Memory：MEMORY.md 是 Markdown 目录

src/memdir/memdir.ts 定义 ENTRYPOINT_NAME = 'MEMORY.md'，并在 prompt 里明确要求：每条记忆写到自己的 .md 文件，再把指针加到 MEMORY.md；MEMORY.md 是 index，不是正文记忆。

src/utils/claudemd.ts 会把 auto memory 的 MEMORY.md 当作 AutoMem 读取，截断到 MAX_ENTRYPOINT_LINES = 200 和 MAX_ENTRYPOINT_BYTES = 25000。所以这里的“索引”是人类可读 Markdown 目录，不是倒排索引或向量索引。

3. Relevant Memories：像 RAG，但用 LLM 选择，不用 embedding

真正像 RAG 的路径在 src/utils/attachments.ts 和 src/memdir/findRelevantMemories.ts：每个用户回合启动 startRelevantMemoryPrefetch()，后台调用 findRelevantMemories() 找相关记忆，选中后作为 relevant_memories attachment 注入下一轮上下文。

但它不是向量召回。scanMemoryFiles() 只扫描 memory 目录里的 .md，排除 MEMORY.md，读取每个文件前 30 行 frontmatter，提取 description、type、mtime，按 mtime 新到旧排序，最多保留 200 个候选。

4. 相关性判断：Sonnet sideQuery，而不是 embedding model

findRelevantMemories.ts 里 selectRelevantMemories() 会把候选 manifest 发给 sideQuery()，模型参数是 getDefaultSonnetModel()，要求返回 JSON：selected_memories。系统提示里明确要求最多选 5 个。

所以如果问“用了什么 embedding 模型”，答案是：这条记忆检索主路径没有 embedding 模型。它用的是 Claude/Sonnet 作为小型相关性选择器，相当于 LLM rerank/selector over metadata，不是 embedding 相似度。

源码层面的检索流程可以这样记：

用户输入新问题
  → query.ts 每个用户 turn 调 startRelevantMemoryPrefetch()
  → attachments.ts 取最后一个真实 user message
  → findRelevantMemories(input, memoryDir)
  → memoryScan.ts 扫描 memoryDir 下 .md 文件，排除 MEMORY.md
  → 每个文件只读前 30 行，解析 frontmatter.description / type / mtime
  → 最多 200 个候选，按 mtime 新到旧排序
  → sideQuery(model=getDefaultSonnetModel()) 让 Sonnet 从 manifest 里选最多 5 个文件
  → readMemoriesForSurfacing() 读取选中文件，单文件最多 200 行 / 4096 bytes
  → 包成 relevant_memories attachment
  → messages.ts 渲染成 <system-reminder> 注入模型上下文

Session Memory 也不是向量 RAG

src/services/SessionMemory/sessionMemory.ts 是会话内自动摘要：当上下文 token 数和工具调用数达到阈值后，注册的 post-sampling hook 会启动 forked agent，读取 ~/.claude/session-memory 下的 Markdown 笔记文件，然后只允许它用 Edit 更新这个文件。

默认阈值在 sessionMemoryUtils.ts：初始化约 10000 tokens，之后每增长 5000 tokens 且工具调用达到 3 次左右再更新。它服务于 compact/连续性，不是 embedding 检索系统。

历史会话搜索：也是 LLM/关键词，不是 embedding

src/utils/agenticSessionSearch.ts 里历史 session 搜索先做字符串包含预过滤：title、tag、branch、summary、first prompt、transcript excerpt；再把最多 100 个 session 发给 sideQuery()，用 getSmallFastModel() 做语义选择。

这更像“关键词预筛 + 小模型语义排序”，不是 vector store。它主要服务 /resume 一类会话查找，不等同于 auto memory 的长期记忆检索。

和 OpenClaw 这类更典型 memory RAG 的区别：

OpenClaw 风格：文档切分 → embedding → 向量/全文索引 → query embedding → 相似召回 → rerank/拼上下文。
Claude Code 风格：Markdown 文件 → frontmatter/目录索引 → LLM 看 manifest 选择文件 → 文件片段注入上下文。
核心取舍：Claude Code 少了 embedding 基建，简单、可解释、可手改；但大规模语义召回能力弱于真正向量 RAG。
最终回答：Claude Code 的记忆有“RAG-like 检索注入”，但不是 embedding RAG；索引方式主要是文件路径层级、MEMORY.md Markdown 目录、frontmatter manifest、mtime 排序和 LLM 选择；没有专门的 memory embedding 模型，相关性选择调用的是 getDefaultSonnetModel() 的 sideQuery()。
