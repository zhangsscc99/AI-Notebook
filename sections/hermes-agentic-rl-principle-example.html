Hermes agentic RL 具体原理是什么：拿一个任务举例

这里说的“内层真正 agentic RL”，不是 skills 那种应用层经验沉淀，而是让模型在任务环境里真实 rollout，用结果 reward 反向更新 LoRA 权重。Hermes 这套源码里，实际是通过 Tinker + Atropos 做：环境负责出题、采样、打分；trainer 负责把轨迹变成带 advantage 的训练样本；Tinker API 负责 LoRA forward/backward 和 optimizer step。

一句话：同一个任务 prompt 让模型采样多条解法 → 环境 verifier 给每条解法打 reward → 组内 reward 均值做 baseline 得到 advantage → 只对生成 token 施加带 advantage 的 importance-sampling loss → Tinker 更新 LoRA 权重 → 新权重再作为下一轮 sampler。

先看 Hermes/Tinker-Atropos 的真实链路：

agent 选择环境。Hermes 的 RL 工具扫描 tinker_atropos/environments/，例如 gsm8k 环境。
生成训练配置。rl_start_training() 用 locked config 写 configs/run_*.yaml，固定基础设施参数，例如 Qwen3-8B、LoRA rank 32、learning rate 4e-5、sglang inference server。
启动三进程。Hermes 依次启动 run-api、launch_training.py trainer、environment.py serve。Atropos API 在中间接环境和 trainer。
trainer 创建 LoRA 训练客户端。create_lora_training_client_async(base_model, rank) 创建可训练 LoRA；随后 save_weights_for_sampler(step_0) 生成初始 sampling client。
环境 rollout。环境拿一道题，调用当前 sampling server，用 n = group_size 一次采多条 completion，并保存 tokens、masked_tokens、logprobs。
环境打分。verifier 比较模型答案和 gold answer。GSM8K 示例是 parse LaTeX boxed answer，然后 verify(answer_parsed, gold_parsed)，正确给 1，错误给 0。
trainer 转训练 Datum。每组 rollout 计算 advantage = score - group_mean；prompt token 的 advantage 置 0，只让生成 token 产生梯度。
Tinker 更新权重。调用 forward_backward_async(data, loss_fn="importance_sampling")，再 optim_step_async(AdamParams(...)) 更新 LoRA。
新权重部署到采样。每 step 后 save_weights_for_sampler(step_i)，再 create_sampling_client(model_path=new_path)，下一批 rollout 用更新后的模型。

拿一个具体任务举例：训练模型做 GSM8K 数学题。

题目：A store has 12 apples. It sells 5 and buys 8 more. How many apples now?
正确答案：15

group_size = 4 时，同一个 prompt 采样 4 条：
A: "12 - 5 + 8 = 15, boxed{15}"  reward=1
B: "12 + 5 + 8 = 25, boxed{25}"  reward=0
C: "12 - 5 = 7, boxed{7}"        reward=0
D: "It has 15 apples, boxed{15}" reward=1

group_mean = (1 + 0 + 0 + 1) / 4 = 0.5
advantage:
A = +0.5
B = -0.5
C = -0.5
D = +0.5

正 advantage 在干什么

A 和 D 的生成 token 会被增强：以后遇到类似状态，模型更倾向于生成这种推理和答案格式。它不是只记住“15”，而是把导致正确答案的 token 分布概率推高。

负 advantage 在干什么

B 和 C 的生成 token 会被压低：例如把“12 + 5 + 8”这种错误路径、漏掉买入步骤的路径概率降低。这样模型行为会从错误策略向正确策略偏移。

为什么要同题采多条

同题多采样可以形成组内相对比较。不是简单“答对就加分”，而是看这组里哪些 trajectory 比平均好，哪些比平均差。GRPO / group baseline 的直觉就在这里。

为什么只训生成 token

trainer 里 prompt token 的 logprob / advantage 被 padding 成无梯度位置。因为 prompt 是题目，不是模型动作；RL 要优化的是模型自己生成的 action token。

如果换成真正 agentic 任务，比如“在一个 repo 里修 bug 并通过测试”，原理完全一样，只是 environment 和 reward 更复杂：

环境给任务：修复 pytest 失败的项目
模型 rollout：
  - 读文件
  - edit_file 改代码
  - terminal 跑 pytest
  - 继续修
  - 最终提交答案
环境 reward：
  tests all pass -> 1.0
  部分测试 pass -> 0.3
  没跑通 / 改坏格式 -> 0.0
trainer：
  同一任务采多条 agent trajectory
  reward - group_mean = advantage
  对成功轨迹里的决策 token 增强
  对失败轨迹里的决策 token 压低
Tinker：
  更新 LoRA 权重
  保存 sampler weights
  下一轮 rollout 用新策略

它和 skills 的差异

skills 是外层提示/文件机制：下次 prompt 里多一段经验。agentic RL 是内层权重机制：即使不给那段 skill，模型本身的 token 分布也被训练改过。

它到底“学会”了什么

不是把某个案例硬存进去，而是把“哪些中间行为更可能拿高 reward”压进 LoRA 参数。比如先读测试、定位失败、最小改动、跑验证、避免乱改这些策略，会通过大量任务统计进入权重。

LoRA 改的是哪里

源码里 Hermes 通过 Tinker 的 create_lora_training_client_async(base_model, rank) 创建 LoRA 训练客户端。具体插在哪些 transformer module 由 Tinker 服务侧封装；Hermes 侧控制 rank、learning rate、训练数据和 rollout/reward。

训练后怎么用

每 step 保存 sampler weights，并创建新的 sampling client；最终输出类似 tinker://.../sampler_weights/final 的权重路径。工程上再把这个 sampling endpoint / model path 包成模型 API 给 agent 调用。

最清楚的理解：Hermes agentic RL 的“agentic”在于 reward 来自完整任务执行结果，而不是单句答案；“RL”在于用 group reward advantage 更新 LoRA 权重，而不是只写一条 skill。具体到任务，就是奖励成功轨迹、惩罚失败轨迹，让模型下一次更倾向于走成功的行动序列。
