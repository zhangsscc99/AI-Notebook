论文主要的数据清洗技巧和技术是什么

ToolLLM 的“洗数据”不是传统 NLP 里只做去重、去脏词、去乱码。它的数据清洗核心是围绕真实 API 是否可用、API 返回是否适合进上下文、生成的 instruction 是否真的对应 API、solution path 是否真的能完成任务来做筛选。

一句话：ToolLLM 的数据清洗主线是：先过滤不可用 API，再压缩冗长 API response，再过滤 ChatGPT 生成 instruction 里的幻觉 API，最后只保留 DFSDT 找到并通过评估的 solution path。它清洗的是“工具调用链是否真实可执行”。

1. 第一层：RapidAPI 工具池过滤——先保证 API 真的能用

论文最早从 RapidAPI 抓到了 10,853 个 tools / 53,190 个 APIs，但真实 API 市场质量参差不齐：有的 API 失效，有的返回 404，有的响应很慢，有的返回 HTML 源码或错误信息。ToolLLM 没有直接全量使用，而是做了严格过滤，最后只保留 3,451 个 tools / 16,464 个 APIs。

原始 RapidAPI 抓取：10,853 tools / 53,190 APIs
  → 基础功能测试：API 是否能正常调用
  → 示例调用：拿 example response
  → 响应时间过滤：长期很慢的 API 丢弃
  → 返回质量过滤：HTML 源码、错误消息、低质量 response 丢弃
  → 最终保留：3,451 tools / 16,464 APIs

这是最关键的一步。因为训练工具调用模型时，如果 API 本身不可用，模型学到的不是“怎么调用工具”，而是大量噪声、错误和不可复现的失败路径。

2. 第二层：API response compression——把长返回压短，防止污染上下文

真实 API response 经常很长，而且包含大量无关字段。如果完整塞进 LLM 上下文，会挤占 token，甚至干扰后续推理。论文在 Appendix A.2 里专门做了 API Response Compression。

怎么压缩

因为每个 API 的 response format 基本固定，论文让 ChatGPT 看该 API 的 tool documentation、参数、example response，再结合 3 个专家写的 in-context examples，判断哪些 key 是重要字段、哪些 key 可以删。

压缩规则

推理时，如果 API response 超过 1024 tokens，就按该 API 的压缩策略删除不重要信息；如果压缩后仍超过 1024 tokens，就只保留前 1024 tokens。

这个技巧很实用：它不是粗暴截断所有返回，而是先让 LLM 为每个 API 学一个“保留关键字段、删除噪声字段”的 schema 级压缩策略。

3. 第三层：过滤 instruction 里的 hallucinated relevant APIs

ToolBench 的 instruction 是 ChatGPT 根据采样 API 文档生成的。ChatGPT 可能会幻觉：生成了一个任务，同时声称某个 API 是 relevant，但这个 API 并不在本次采样集合 Ssub_N 里，甚至可能不存在。

论文的做法很直接：生成初始 instruction 后，检查它标注的 relevant APIs 是否确实存在于采样 API 集合里；如果相关 API 是 hallucinated，就过滤掉。

ChatGPT 输出：instruction + relevant APIs
检查：relevant APIs ⊂ Ssub_N ?
  是：保留为 qualified instruction/API pair
  否：过滤，因为它引用了幻觉 API

这一步保证训练 API retriever 的正样本是可信的。否则 retriever 会被训练成把问题匹配到不存在或不相关的 API。

4. 第四层：利用 RapidAPI 层级采样，避免随机组合造成脏多工具任务

多工具任务最容易造脏数据。如果完全随机抽几个 API，可能一个查天气、一个查股票、一个查星座，硬让 ChatGPT 编一个任务，得到的 instruction 会很牵强。

论文用了 RapidAPI 的 category 和 collection 层级来采样：

  • I1：单工具任务，遍历每个 tool 生成。
  • I2：同一个 category 里抽 2-5 个 tools，每个 tool 最多抽 3 个 APIs。
  • I3：同一个 collection 里抽 tools，构造跨工具但目标相关的任务。

这其实也是一种数据清洗/数据构造技巧：不是生成后再全靠过滤，而是在采样阶段就减少不相关工具组合，从源头降低脏 instruction 的比例。

5. 第五层：solution path 只保留 passed 路径

ToolLLM 不只是要 instruction，还要模型真实调用 API 后形成的 solution path。论文用 DFSDT 搜索多条工具调用路径，但最终只保留 passed solution paths 作为训练数据。

instruction
  → ChatGPT + available APIs
  → DFSDT 搜索调用路径
  → 执行真实 API，拿 observation
  → 如果路径能完成任务：保留
  → 如果路径失败 / 一直报错 / 不能完成：丢弃

这比普通 ReAct 轨迹更干净。因为 ReAct 可能一条路走错到底；DFSDT 可以回退、换节点、探索新路径。最终保留的是通过搜索找到的有效调用链，训练信号质量更高。

6. 第六层：ToolEval 多次评估 + majority vote，减少评估噪声

Appendix A.5 里，ToolEval 对 pass rate / win rate 都不是只问 ChatGPT 一次，而是让 evaluator 生成多次预测，通常 ≥ 4 次，然后 majority vote 得到最终判断。

这也是一种清洗思想：工具任务没有唯一标准答案，API 返回还可能随时间变化，单次 LLM 判断有随机性。多次评估取多数，可以降低误判。

7. 最值得借鉴的技术点

可执行性优先

不是看文本是否漂亮，而是看 API 是否真的能调用、路径是否真的能执行、返回是否真的有用。

源头采样约束

用 category / collection 约束多工具组合，避免随机拼工具导致任务天然不合理。

结构化字段校验

检查 relevant APIs 是否属于采样集合，过滤 ChatGPT 幻觉出来的 API 名称。

长上下文压缩

对 API response 做 schema-aware compression，减少无关字段进入训练和推理上下文。

搜索式轨迹清洗

用 DFSDT 多路径搜索，失败路径可以回退，最后只保留 passed solution path。

多数投票评估

ToolEval 多次判断后 majority vote，降低 LLM evaluator 的随机性。

如果你要复用 ToolLLM 的数据清洗方法，最核心不是“去重”，而是这套标准：工具真实可用、任务引用的工具真实存在、API 返回足够短且保留关键信息、调用轨迹真实执行过并能完成任务。
