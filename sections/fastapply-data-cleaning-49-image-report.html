49 张微信图 FastApply 数据清洗流程复刻报告

这次新增的 49 张微信图片主要不是 GRPO loss 本身，而是 GRPO 训练前的数据清洗 / 构建 pipeline。我已经把截图里的文件和源码结构迁移到训练项目：rl_master/applications/fastapply/data 与 rl_master/applications/fastapply/build。

extract：从 Git 仓库单父 commit 抽取 source 文件 diff，同时取 old_source 和 new_source。
parse：把 unified diff 切成 Hunk，生成每个 hunk 的 SEARCH/REPLACE changes。
AST：把 old/new 代码解析成 Unit 树，Unit 有 type、span、parent、children。
context：ChangeContext 把 hunk 的 +/- 行号映射到 Unit，定位到底改了 import、function、class 还是 statement。
filter：过滤空源码、非源码后缀、hunk 太多、样本太长、语法失败、没有 functional 修改的样本；截图规则也支持要求 import 修改。
convert：最后转成 GRPO 行：prompt、reward_model.ground_truth、extra_info、response 的 <updated>。

复刻的核心数据结构

  • Span：1-based inclusive 行范围，支持 overlap / union / subtract / merge。
  • Hunk：解析 @@ -old +new @@，精确记录删除行和新增行。
  • Unit：AST 单元，表示 import、class、function、statement 等。
  • UnitState：标记某个 Unit 是否被修改、是否部分修改。
  • ChangeContext：把 hunk changes 映射回 Unit。

复刻的文件模块

  • data/types.py、data/utils.py、data/ops.py
  • data/ast/ast_base.py、ast_python.py、ast_java.py
  • build/extract.py、parse.py、filter.py、generate.py
  • build/make.py、deduplicate.py、convert.py、analyze.py、archive.py

清洗精髓

不是随便拿 diff 训练，而是先用 hunk 行号和 AST scope 对齐：只有知道“这几行属于哪个函数 / 类 / import”，才能过滤掉注释噪声、格式噪声、超长样本和不可解析样本。

本项目适配

截图原版依赖 tree-sitter、datasets、datasketch、LLM 服务。本项目保留同名类和调用链，但加了轻量 fallback，所以当前服务器可直接跑 tiny 数据。
