详解：项目里的 reward 是怎么做的

这个项目里 reward 分两层：训练用 verifier reward 和 RL-master 环境 reward。两者目标一致：不奖励聊天能力，只奖励模型能否严格把 patch 合并成正确代码，并且输出格式干净。

1）FastApply 训练 reward

位置：/root/rlhf/fastapply_pipeline/rewards.py。

total = 0.55 * exact
      + 0.20 * similarity
      + 0.10 * tag_format
      + 0.05 * no_extra_prose
      + 0.10 * syntax
  • exact：抽取 <updated>...</updated> 后，和 gold updated source 归一化比较，完全一致给 1。
  • similarity：用 difflib.SequenceMatcher 算相似度，避免只有 0/1 导致信号太稀疏。
  • tag_format：必须能抽到 <updated> 标签，格式对才给分。
  • no_extra_prose：输出要从 <updated> 开始、以 </updated> 结束，不能夹解释、Markdown fence、废话。
  • syntax：对 Python 用 AST parse；JS/TS 用轻量 regex 分析，保证代码结构基本可用。

2）RL-master 环境 reward

位置：/root/rlhf/rl_master/agent/environment/packages/fastapply/impl.py。

correctness = compare(reference, candidate)
is_valid = bool(candidate)
reward = correctness * 0.8 + is_valid * 0.2

这里更接近图片里的环境式 reward：正确性占 80%，输出是否有效占 20%。也就是说，完全正确且格式有效得 1.0；有输出但不正确通常只有 0.2；空输出是 0。

先抽取。用 extract_updated_tag / extract_tagged_content 只取 updated 标签内的代码。
再比较。训练 reward 做 exact + similarity；RL-master rule reward 用 difflib 忽略空白行后比较增删行。
再验格式。检查是否有标签、是否只有标签包裹的代码、是否没有多余解释。
最后做 judge fallback。rl_master/applications/fastapply/reward/score.py 里 rule compare 失败时，会构造 diff view 并用 judge.yaml 让 LLM 判等价。

为什么 exact 权重大

FastApply 是代码应用任务，不是开放问答。真正需要的是“补丁是否完整合并、代码是否和目标一致”。所以 exact 权重最高；similarity 只是为了 tiny / early stage 训练时提供平滑信号。

为什么要格式分

代码 agent 最怕模型输出解释、代码块围栏、冲突标记或半截代码。格式 reward 会把模型推向“只输出可被机器消费的 updated code”，这对后续自动 apply 很关键。

一句话：项目 reward 的核心是 正确合并 patch，其次是 输出可解析、无废话、语法合法。它不是偏好模型“说得好”，而是奖励模型“改得准”。
