JoyAgent 工作流编排怎么做，用了什么 Agent 框架；如果用 LangGraph 怎么设计

从源码看，JoyAgent-JDGenie 不是直接套 LangGraph、CrewAI、AutoGen 这类现成 Python agent 框架，而是自己在 Java/Spring Boot 后端里实现了一套轻量 agent runtime：Controller 接请求、AgentHandlerFactory 选模式、BaseAgent/ReActAgent 跑循环、ToolCollection 管工具、LLM 类做 function calling、SSEPrinter 做流式输出。

一句话：JoyAgent 的工作流编排是“自研 Java Agent 框架 + Spring Boot 服务化 + Python 工具服务”的组合；核心模式是 ReAct 和 Plan-Solve，不是 LangGraph 图编排，但可以很自然地用 LangGraph 重写成显式状态图。

1. 入口：前端请求进入 Spring Boot

前端调用后端流式接口，例如 /web/api/v1/gpt/queryAgentStreamIncr。后端 GptProcessServiceImpl 创建 SseEmitter，再交给 MultiAgentServiceImpl 或 /AutoAgent 处理。

所以 JoyAgent 的第一层编排是产品服务层：请求 id、trace id、SSE 长连接、心跳、输出样式、前端实时展示都在这里处理。

2. AgentContext：一次任务的共享状态

GenieController 会构造 AgentContext，里面包含 requestId、sessionId、query、printer、toolCollection、dateInfo、productFiles、taskProductFiles、sopPrompt、basePrompt、agentType、templateType 等。

这相当于 JoyAgent 的 run state。规划器、执行器、总结器、工具都通过这个 context 共享任务状态和交付物列表。

3. AgentHandlerFactory：按模式路由

AgentHandlerFactory 注入所有 AgentHandlerService 实现，然后调用每个 handler 的 support(context, request) 判断该走哪条处理路径。

目前能看到的核心处理器包括 PlanSolveHandlerImpl 和 ReactHandlerImpl。Agent 类型枚举包括 COMPREHENSIVE、WORKFLOW、PLAN_SOLVE、ROUTER、REACT。

4. ReAct 模式：单 agent 工具循环

ReactHandlerImpl 创建 ReactImplAgent 和 SummaryAgent。ReactImplAgent 继承 ReActAgent，每一步就是 think() + act()。

think() 调 LLM 的 askTool，让模型基于 tools schema 选择工具；act() 执行 tool calls，把 tool result 写回 memory。没有工具调用时进入 FINISHED，再由 SummaryAgent 汇总结果和文件。

5. Plan-Solve 模式：规划器 + 执行器 + 总结器

PlanSolveHandlerImpl 是更像多智能体的主流程：先做 SOP recall，再创建 PlanningAgent、ExecutorAgent、SummaryAgent。

规划器生成当前要执行的 task；执行器执行 task；执行结果再喂回规划器，规划器判断继续、更新计划、还是返回 finish。最后 SummaryAgent 根据 executor memory 汇总任务结果和交付文件。

6. 并发执行：多个子任务可并行

Plan-Solve 里如果规划结果用 <sep> 拆成多个任务，会创建多个 ExecutorAgent 副本，并用 ThreadUtil + CountDownLatch 并发执行。

执行完后，它把 slave executor 的 memory 合并回主 executor memory。这就是 JoyAgent 的一个关键编排点：规划器可以一次发出多个并行 task，执行器并行跑，然后汇总结果再继续规划。

7. 工具系统：ToolCollection + MCP

ToolCollection 管内置工具和 MCP 工具。内置工具包括 file、code interpreter、report、deep search、data analysis 等；MCP 工具通过 McpTool listTool 后动态加入。

LLM 的 askTool 会把这些工具转成 function calling schema；模型返回 tool_calls 后，BaseAgent.executeTools 可以并发执行多个工具调用。

8. 它用了什么 Agent 框架

严格说：它没有用 LangGraph 这类外部图框架。它的 agent 框架是项目内自研的 Java 类体系：

  • BaseAgent：状态、memory、maxSteps、run loop、工具执行。
  • ReActAgent：抽象 think() / act()。
  • PlanningAgent：计划创建和更新。
  • ExecutorAgent / ReactImplAgent：工具调用执行器。
  • SummaryAgent：最终结果汇总。
JoyAgent current workflow

UI request
  -> GenieController / GptProcessService
  -> SseEmitter + heartbeat
  -> build AgentContext
  -> build ToolCollection
  -> AgentHandlerFactory selects handler

REACT mode:
  ReactImplAgent.run(query)
    -> loop BaseAgent.run
      -> think(): LLM askTool
      -> act(): execute tools, append tool results
    -> SummaryAgent summarizes
    -> SSE result

PLAN_SOLVE mode:
  SOP recall
  -> PlanningAgent creates/updates plan
  -> current task(s)
  -> ExecutorAgent executes task(s)
      -> parallel executors if multiple <sep> tasks
  -> executor result back to planner
  -> repeat until finish / max steps / error
  -> SummaryAgent summarizes
  -> SSE result
所以它现在的编排风格：不是图引擎，而是 imperative loop：Java while loop + agent class + handler routing + tool function calling + SSE streaming。优点是直接、产品工程好接；缺点是状态机边界、恢复、checkpoint、可视化和复杂分支会比 LangGraph 难管理。

如果用 LangGraph 重新设计 JoyAgent

用 LangGraph 重做，不应该简单把 JoyAgent 包成一个大 node，而应该把它现有的关键角色提升为显式节点：入口节点、SOP 召回、工具构建、规划节点、执行节点、并行子任务、总结节点、文件产物节点、SSE 事件节点。

State 设计

定义 JoyAgentState：query、request_id、agent_type、messages、plan、current_tasks、task_results、tool_results、product_files、sop_prompt、base_prompt、output_style、stream_events、error、step_count。

这对应现在的 AgentContext + Memory + PlanningTool.plan + productFiles。

节点拆分

  • ingress_node：解析请求、创建初始 state。
  • sop_recall_node：召回 SOP 并注入 prompt。
  • tool_registry_node：构建 ToolCollection/MCP tools。
  • route_mode_node：按 agentType 分到 react 或 plan_solve。
  • planner_node：生成/更新 plan 和 current_tasks。
  • executor_node：执行单个 task 的 ReAct 工具循环。
  • summary_node：汇总任务和文件。

并行子任务怎么做

当前 JoyAgent 用 <sep> 拆任务并手写线程。LangGraph 里可以用 Send 把多个 current_tasks fan-out 到多个 executor 子图，再 fan-in 合并 task_results。

每个 executor 子图有自己的 messages/tool_results，最终只把 task summary 和 product_files 合回主 state，避免上下文互相污染。

ReAct 工具循环怎么做

可以用 LangGraph 的 StateGraph + 条件边：llm_node 产生 tool_calls；如果有 tool_calls 进入 ToolNode；工具结果回到 llm_node；如果没有 tool_calls，结束当前 task。

这对应现在 ReActAgent.step() 的 think() + act()。

SSE 流式输出怎么保留

LangGraph 节点执行时产生事件：plan_thought、tool_thought、tool_result、task_summary、result。后端把 LangGraph stream events 映射成现在前端已经理解的 SSE 消息类型。

这样前端不用大改，主要替换后端编排引擎。

比现在强在哪里

LangGraph 会让 checkpoint、resume、人审 interrupt、并行 fan-out/fan-in、状态可视化、错误恢复更清晰。尤其 JoyAgent 这种“规划-并行执行-汇总-再规划”的模式，本质上很适合图。

LangGraph version of JoyAgent

START
  -> ingress_node
  -> build_context_node
  -> sop_recall_node
  -> tool_registry_node
  -> route_mode_node

route_mode_node:
  if agent_type == REACT:
    -> react_subgraph
    -> summary_node
    -> END

  if agent_type == PLAN_SOLVE:
    -> planner_node
    -> conditional:
        finish -> summary_node -> END
        tasks  -> Send(task_i, executor_subgraph) in parallel
              -> merge_task_results_node
              -> planner_node
        error  -> error_node -> END

executor_subgraph:
  task_start
  -> llm_tool_node
  -> conditional:
       has_tool_calls -> ToolNode -> llm_tool_node
       no_tool_calls  -> task_summary_node -> END
设计结论：JoyAgent 当前是自研 Java agent loop；如果用 LangGraph，核心不是换语言炫技，而是把它已有的 PlanSolve、ReAct、并行 Executor、Summary、SSE 事件、productFiles 状态显式图化。这样复杂任务会更可恢复、更可观测，也更容易扩展成人审、失败重试和多工作流。
